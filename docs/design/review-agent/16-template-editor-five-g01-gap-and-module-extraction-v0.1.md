## 2. 五份完整模板首先暴露的结构差异

| 模板 | 完整审核目的与真正业务对象 | 无法丢失的专属差别 |
| --- | --- | --- |
| **I** | 在籍学生身份登记更正的材料和程序预审；一次申请可修改姓名、证号、出生日期等多个字段，并追踪旧值—新值—更正原因—权威原始登记源 | “合法更名事实”不等于字符串不相等；招生/录取原始数据差错与毕业后历史记录勘误不能归为普通账户资料修改；一份法定文书可覆盖多项更正事实（I §3、§6、§12.1） |
| **A** | 一份申请单 → 0–多主体/授权关系 → 1–多档案件 → 每件 1–多操作；`case_id + item_id + operation_id` 是可追溯键 | 查阅、摘录、复制、外借权限不能互相继承；档案已公布≠档案已开放；操作授权必须匹配对象和范围（A §2.1、§4–6） |
| **C** | 申请人、拟持卡人、关联教职工或责任单位形成一条资格与代办关系；`family` / `temporary_service` 是同一模板的两条分支 | 亲属关系已证不等于有权代办，服务事实已证不等于校方已批准卡资格；在职、离退休、已故等是分支内部条件（C §1、§4–6） |
| **S** | 一份专项用印申请可组合事实证明、制式申请材料、译文、复印/密封与骑缝等不同动作 | 申请阶段后续学校栏位可合理留空；批准稿版本与送印稿版本必须核对，章种/份数/批准范围需要独立绑定（S §1、§7–8） |
| **P** | 政审材料的程序性核验，区分组织出具、收件、签署阶段和责任主体 | 出具端起始材料不应被要求满足收件端完成态；材料形式核对不允许升级为政治、思想或组织实质认定（P §0–2、§5、§12、§14） |

**直接结论：** 目前只有 `case/subject` 的字段作用域不能天然表达 A 的“档案件×操作”，而 C 的“申请人→持卡人→资格关联人/单位”也不等于多个普通字段。短期可把每个 `(item, operation)` 映射到一个有稳定业务键的 `ReviewSubject(type='custom')`，但制作态必须保留原来的角色、对象和关系含义，不能只靠 title 文本。

## 3. 共性能力矩阵：哪些是基础设施，哪些可能是真模块

标记：**●** 源文档明确要求；**◇** 有相近场景但不能直接证明同一局部语义；**—** 现有材料不足以视为核心共同需求。下表是**需求对照**，不表示代码已实现。

| 审核表达能力 | I | A | C | S | P | 建议归属 |
| --- | :---: | :---: | :---: | :---: | :---: | --- |
| 明确审核目的、适用和排除边界 | ● | ● | ● | ● | ● | 完整模板及路由卡元数据 |
| 适用学校/身份/时间/阶段和政策确认状态 | ● | ● | ● | ● | ● | **基础规则治理** |
| 条件组合、互斥、三值 unknown | ● | ● | ● | ● | ● | **基础条件引擎** |
| 用户自述与可信系统/授权人事实分离 | ● | ● | ● | ● | ● | **基础事实来源** |
| 证据按“证明哪个事实”关联、AND/OR 与替代 | ● | ● | ● | ● | ● | 基础证据关系 + 局部业务模块候选 |
| 多主体、委托、代理与权限范围 | ◇ | ● | ● | ● | ● | **业务模块候选**，实体权限专属 |
| 有效期/请求期间/批准范围对照 | ◇ | ● | ● | ● | ◇ | 受控比较原语 + 业务模块候选 |
| 当前阶段是否要求某材料已存在 | ● | ● | ● | ● | ● | 基础责任与阶段条件 |
| 跨材料冲突、历史版本与原件来源 | ● | ● | ● | ● | ● | 基础比较/溯源能力 |
| 多对象/逐操作局部结果、主状态聚合 | ◇ | ● | ◇ | ● | ● | 基础对象/结果模型 |
| 人工正式决定与 AI 预审分离 | ● | ● | ● | ● | ● | 基础工作流及授权约束 |
| 独立测试预言、失败与反误杀覆盖 | ● | ● | ● | ● | ● | 制作工具测试能力 |

**重要防误抽：**
- “五份模板都要核对姓名”只能直接支持**字段/来源比较能力**，不能把姓名匹配抽成能够证明政审、查档、发卡或用印资格的万能业务模块。
- “五份都涉及政策版本”应先建立**政策适用性治理**，不是允许任意模块按严格程度求并集。
- “材料槽为空”不等于“该事实无法证明”；OCR 不可读也不等于未上传。
- 各文档自列的 `M01/Mxx` 多数是作者对**编辑器共性机制**的建议编号，并不都符合第 15 号规范对**可复用业务模块**的语义完整性要求。

对应证据：I §4–6、§12；A §2–5、§11–12；C §3–6、§11；S §2–4、§17；P §3–6、§16。

## 4. 分层不是把所有审核过程做成节点图

Blender 几何节点适合借鉴**节点组封装、稳定接口、版本化引用和组合可视化**，但我们的模块首先服务于**Agent 自主完成审核**。必须精准的是审核目的、必核事项、制度效力、证据依据、输出和权限边界；不必精准规定每步工具、阅读顺序或模型推理链。

| 层级 | 基本定位 | 不应成为强制负担 |
| --- | --- | --- |
| **L0 薄审核内核** | 每份审核默认拥有：输入及版本、审核目标与依据、取证/引用能力、应核事项覆盖记录、局部状态、输出与权限/审计边界 | 不应要求作者每次拖入“读取文件”“提交结果”等系统节点 |
| **L1 可选基础能力** | 平台提供提取、比较、集合/时间/数值计算、条件判断、事实/证据关联、专业解析器等工具或数据表达 | 简单文档审核不必配置主体关系图、Claim 或 AND/OR 证据树 |
| **L2 审核任务模块** | 一个可复用或本模板专属的**局部审核责任**：目标、要求、适用与禁区、完成标准 | 不要求每个模块是图，不要求把自然语言规则拆成节点 |
| **L3 完整业务模板** | 为一个独立审核目的组织 L2/专属规则、校本依据、结果边界和整体覆盖 | 不把模块简单求并集，不要求所有模板都先引用复用模块 |

### 4.1 哪些必须属于 L0，哪些应留在 L1

| v0.1 发现的共性 | 当前定位 | 判断依据 |
| --- | --- | --- |
| A01 稳定对象标识 | L0 有单次审核对象/范围；**多主体或逐操作关系是可选 L1** | A 的档案件×操作、C 的多主体关系需要精细结构，但单份文章格式审查不需要 |
| A02 可信来源与位置 | L0 对关键判断可追溯并区分用户声明、模型抽取、系统事实；取证手段属于 L1 | 不能把申请自述直接升级为学校登记真值 |
| A03 三值与条件树 | L0 保证未知/不适用不当假或通过；**复杂 AST 为 L1** | 不要求所有自然语言审核目标都写条件表达式 |
| A04 政策适用与版本 | L0 区分审核要求的性质；高校正式政策治理按需使用 L1 配置 | 普通文本审核可使用用户明确要求，不能凭空造“正式校规” |
| A05/A06 Claim、证据多对多、AND/OR、阶段性必需 | **L1 可选复杂能力**；业务启用时必须精确维护关系 | I 一证多用、C 替代证明、S 后置签章为典型需求 |
| A07 日期/金额/内容比较 | L1 受控工具 | 比较一致不等于法律效力成立 |
| A08 局部结果与异常聚合 | **L0 必需** | 不能把待核、未执行、失败与已通过混为一类 |
| A09 版本、来源追溯与测试 | L0 版本/审计不变量；制作端另提供预览与回归 | 发布后不得静默改变历史运行 |

**最小可用性检验**：一份材料 + 一条明确审核要求 + 一个带出处的检查结果，必须不依赖任何业务关系图或复合模块即可完成。没有审核目标时，不能假装已完成有效审核；用户普通检查指令与有权政策来源必须区分。

### 4.2 模块表达方式应当开放且可混合

| 表达方式 | 表达主体 | 何时采用 |
| --- | --- | --- |
| **语义模块（默认）** | 可读自然语言：做什么、覆盖什么、依据什么、不能做什么 | 格式核查、身份一致性、专业文本或程序性审核 |
| **规则强化模块** | 上述语义 + 少量确定性条件、阈值、字段、来源/证据要求 | 金额计算、时效、明确制度条件、证据关系 |
| **复合模块** | 引用其他模块的固定版本，说明它们的局部责任和互相关系 | 代理授权、资格证据链、综合预审 |

三者是**表达方式，而非必须互斥的模块种类**。上层模块既可用 L1 工具组合，也可以由受控专业实现或单独语义定义。复杂模块可以有子模块；简单模块可以只有几段清楚的 Markdown。节点图只是复合关系的**可选视图**，而非实际必备存储形式或运行序列。

### 4.3 仍建议研究的四种局部业务模块

| 候选 | 共同局部审核目的 | 证据 | 不可随模块继承 |
| --- | --- | --- | --- |
| **B01 有权代办与授权范围核验** | 授权凭证是否覆盖当前代理人、对象、办理动作和期限 | A §2/§12；C §4/§11；S §17；P §2/§16 | 代理成立≠查档开放、校园卡资格、用印章权或政审批准 |
| **B02 待证事实与证据链覆盖** | 指定事实是否被允许来源与合理替代/互补证据所支持 | I §4/§6/§12；C §4/§11；A §4/§12 | OCR 识别一致≠合法证明有效 |
| B03 请求期限与生效资格区间 | 检查指定资格/批准能否覆盖请求期 | C §4–6；A §4/§6；S §8 | 续期申请中≠批准已生效 |
| B04 阶段性栏目责任核验 | 特定阶段、责任人下哪些栏目应完成 | S §1/§7；P §5/§12；A §4 | 出具初稿≠收件完成品 |

B01、B02 仍是首批**跨模板候选**，未经过模块抽取后回归，不是已发布模块。**允许模板专属局部模块先存在**；只有证明跨模板语义稳定且维护收益明确后才提升为共享库资产。不把“相近但不同”笼统当作不可复用：有的相似性止于机制，业务资格确实不同；有的仅是当前五份资料尚不足以证明等价。

### 4.4 G01 专属语义不得自动传播

I 的合法更名与原始登记归因；A 的档案开放限制及逐操作权限；C 的亲属范围/特殊卡资格；S 的批准稿与送印稿及实际章权；P 的组织意见与政审敏感判断，都留在相应模板和已确认的校本规则中。模块可复用下层取证和局部判断结构，**不得自动迁移其他业务的法定/行政结论**。

## 5. 对照当前代码：能力在哪里、真正缺什么

静态检查的是仓库 `main`，不是用户应用现场测试。

| 现有能力 | 已在代码中看到 | 五模板提出的缺口 / 危险假设 | 优先 |
| --- | --- | --- | --- |
| 模板身份与冻结 | `TemplateVersion.templateId/version/status`；`template-store.ts` 草稿、发布及校验 | 作者态缺模块实例版本、来源映射和变更影响；不能靠目录编码充当稳定主键 | P0 |
| 字段与条件 | `FieldSpec.scope='case'|'subject'`、`conditionRequired`；`ConditionAST` + `TriState` | A 的 relationship/item/operation，C 的资格多主体关系无法按有语义的对象角色完整建模；AST 没有自带权限范围/证据链运算 | P0 |
| 材料槽 | `MaterialSlotSpec.requiredWhen/requiredAt/minCount/maxCount/allowReuseAcrossSubjects` | 当前槽不能完整表达 `Claim ↔ (Evidence AND/OR) ↔ 业务对象/操作范围`；`requiredAt` 仅 `submission/decision`，不覆盖全部实际阶段 | P0 |
| 审核标准与规则 | `TemplateSectionSpec.criteria: TemplateCriterionSpec[]`；另有 `PolicyVersion.rules: RuleSpec[]` | **编辑器标准与完整规则能力不对等**：criterion 没有 `when`、权威政策引用和 `onUnknown` 等；需要明确编译/绑定关系，否则界面看到与运行生效可能不一致 | **P0 最高** |
| 运行对象 | `ReviewCaseV2.subjects`、`ReviewSubject(type='custom')` | 可临时把 A 每个 `(itemId,operationId)` 映射独立 subject，但需要结构化业务键，不能只存标题或合并操作授权 | P0 |
| 工作流 | `WorkflowStageSpec` 含阶段与 `enterWhen/exitWhen` | 编辑器 `linkedStages` 目前会按顺序生成 `nextStageId`；组合/回退与审批责任需要更精确的作者模型，不能视为全部完成 | P1 |
| 规则来源 | `policyRefs`、`RuleSpec.confirmation`、`sourceRefIds`、政策 hash 校验 | 须在作者界面把“校本已证/跨校参考/待核/设计/模拟”和适用范围及权限分开表达，不让模型自动升级为正式校规 | P0 |
| 静态校验 | `validateEditor` 和 `validateTemplate` 可查部分 ID、空值、字段/槽位引用、阶段、政策引用等 | 尚无模块版本/依赖/参数、业务冲突、跨校误继承、完整证据覆盖与源规则映射验证 | P0/P1 |
| 编辑 UI | `TemplateWizardPanel.tsx` 提供字段、分项、材料槽、规则文本、流程、输出、保存发布 | 不能把“有 GUI 编辑表单”误认成支持五套完整 MD；也不必推倒重写 | P1 |

**复杂 G01 的结构需求不等于所有模板的强制 Schema。** 对一般文本审核，允许清楚的自然语言任务直接生效；只有涉及确定性判定、规则冲突、跨对象授权和证据链等关键约束时，才要求足够明确的结构化表达。不能把不可验证的硬性规则藏在自由文本中假称已通过程序校验。

**必须单列两个风险：**

1. `TemplateCriterionSpec` 与 `RuleSpec` 是两种不同的数据表达面。首版作者态必须把每项**规范化审核命题**绑定到实际生效 `RuleSpec`/criterion、PolicyRef 和来源片段，防止“编辑器要求”与“运行中 Agent 收到的有效要求”分叉。
2. 现有空白模板初始化中 `outputs` 可能带 `approval` 输出类型，但五套文档主要是**材料/程序预审**。显示“审批结果”不应意味着 Agent 自动拥有学校审批权限；必须在编辑器中明确可输出意见和有权执行动作的区别。

这一判断不是要求立刻替换所有运行模型。相反，现有 `TemplateVersion`、`RuleSpec`、`PolicyVersion` 和 Pi 服务已提供宝贵基座，**先补足作者态所需的语义，再决定哪些运行结构确实需要向后兼容地扩展**。

## 6. 最小语义契约：组织 Agent 的检查责任

### 6.1 模块最低只要回答六个问题

1. **负责什么**（局部审核目标和审核对象）；
2. **何时适用**（范围、例外、不适用情形；简单任务一句话即可）；
3. **依据什么**（用户明确要求、模板要求或有权发布的制度，区分来源效力）；
4. **必须完成什么检查**（可用自然语言明确表达的审核义务）；
5. **交付什么**（局部结论、问题、证据位置、待核项）；
6. **不能做什么**（不能推断的事实、不能越过的授权和人工决定）。

机器维护的最低元数据建议有稳定 ID、版本以及引用/依赖标识。ClaimSpec、EvidenceRequirementSpec、ConditionAST、插口、工具步骤、规则表等**按需出现**，不是审核模块的入门考试。可采用 Markdown 主体加少量结构化元数据，但**D1 之前不锁定具体文件格式或 TypeScript Schema**。

示例（非固定 DSL）：

```yaml
moduleId: review.subject-consistency
version: 0.1.0
purpose: 核对本次材料中指向同一被审核人的关键信息
scope: 需要确认同一主体的材料审核
requirements:
  - 指出可以验证的不一致及具体材料位置
  - 不能确认时明确标记待核，不推定合格或不合格
outputs: 局部检查结果、冲突、证据及待确认项
limits: 一致性不等于已经取得业务资格或代理权限
# 只有确有需要才补充结构化条件、证据替代或子模块
```

### 6.2 Agent 可以自己规划，但系统必须检查覆盖

```text
完整模板 / 局部审核模块 / 适用制度
              ↓
解析为固定、版本化的“审核责任包”
              ↓
   Pi Agent 自主读取、推理与使用工具
              ↓
逐项完成状态 + 实际证据出处 + 异常/待核
              ↓
      审核覆盖与来源校验
              ↓
       合法的预审意见/待办
```

**依赖关系不等于工具调用顺序。** 模块可以说明“只有确认是委托代办，才核查委托授权”，但不能要求 Agent 第一轮读什么、第二轮调用什么模型。确定性计算及版本哈希等可以交受控工具处理，不能以模型声称“已经计算”取代执行证据。

保留一个轻量的 **审核覆盖记录（coverage ledger）**：每项**真正独立、必要**的检查目标固定 ID；Agent 对该目标记录已核实/不符合/待补/待确认/不适用/未执行/执行失败及材料来源或未完成原因。系统验证有无漏项、是否保留未知及证据，**不比较 Agent 的思考顺序、自由文本表述和工具调用轨迹是否逐字相同**。覆盖率本身不等于审核正确率，仍需独立金标对照。

简单任务可以只有一个检查目标；复杂模板可细分为少量有独立意义的目标。不能为了填满 ledger 而生成几百条机械检查。档案利用中的“查阅”与“复制”应保留各自作用范围，不能共享同一授权结果。

### 6.3 模块组合与发布只需明确语义与边界

制作态可引用语义模块、规则强化模块和复合模块，结合模板专属要求生成 Agent 可理解的固定任务包。仅向运行 Agent 载入**当前适用**的要求与必要依据，避免无差别塞入全部分支与嵌套模块文本导致上下文膨胀；不允许因压缩而遗漏例外、来源和必核项。

沿用第 15 号规范的三类受控变更：新增、参数化和有权显式替换；保持政策出处、权限、版本冻结与差异追踪。**制作态可画组合关系图，运行态不要求 Pi Agent 临场执行模块图。**

### 6.4 之前提出的数据模型应降为可选候选

`TemplateAuthoringSpec`、`BusinessObjectRole`、`ClaimSpec`、`EvidenceRequirementSpec` 和 `ApplicabilitySpec` 暂时是复杂业务可能用到的概念，**不要求每套模板必须拥有它们**。先用最小文本审核与 C/A 两个复杂情形验证粒度，D1 再决定哪些字段必须统一、哪些留在单个业务模块里。

## 7. Agent-first 模块编辑：一份语义定义，多种编辑视图

目标优先级：**Agent 能高效、可验证地编辑 > 人类能直接理解和操作 > 后续优化人类交互体验**。Blender Node Group 的封装思想可用，但不让画布布局、逐节点拖线、端口像素坐标参与业务定义。Agent 和人类始终修改**同一份可版本化、可追溯的语义源**，不是两套独立模板。

### 7.1 Agent 应能执行的事务性操作（非现有 API 声明）

| 动作 | 预期能力 | 安全和一致性 |
| --- | --- | --- |
| 发现与读取 | 按审核目的查找现有模块，读取 ID、版本、用途、适用/排除、来源与案例 | 不能仅凭显示名称或相似关键词覆盖模块 |
| 创建与组合 | 写入清晰的语义模块，引用固定版本模块，添加模板专属审核事项 | 不因引用关系静默引入其他学校政策或行政授权 |
| 批量编辑 | 更新多项任务说明、条件、模块引用和参数 | 原子提交、预期修订号、冲突检测；不依赖逐个拖动节点 |
| 校验和预览 | 展开适用检查、来源和权限，检查漏项/冲突，运行合成测试 | 仅程序可确定错误直接阻断，模型审计给出需人工确认的风险 |
| 差异与回滚 | 展示变更后的审核责任、例外、必核事项及影响测试 | 不修改已发布版本和历史案卷 |

**输入文件与引用模块中的任意文本不是制作 Agent 的系统指令**。导入 Markdown 和自动建议都要防止把不可信文本升级为有权规则或工具命令。模型可以自动改草稿，但有权审批/规则正式发布仍受权限与测试门控约束。

### 7.2 人类编辑器先“读懂审核责任”，再按需展开细节

| 首版视图 | 默认看到什么 | 何时进入高级配置 |
| --- | --- | --- |
| 业务模板概览 | 审核目的、适用/排除、版本、来源 | 始终可读 |
| 审核责任列表 | 应核事项、必要依据、当前适用条件、输出与限制 | 默认可直接编辑自然语言 |
| 模块引用/关系 | 可复用模块与本地模块，依赖/条件与版本 | 复合模块时按需展示节点组/关系图 |
| 高级规则与证据 | 条件 AST、阶段义务、Claim/证据替代、确定性校验 | **确实需要精确规则**才打开 |
| 生效预览与回归 | 某一情形下实际交给 Agent 的审核任务、来源、待确认项、覆盖状态 | 发布前必须能查看，编辑时按需执行 |

优先复用当前 `TemplateWizardPanel` 的草稿/发布、字段、分项与规则编辑基础。可视化节点是**辅助观察组合**，不是必需数据类型；位置、颜色和排版属于展示元数据，Agent 不需自行摆放节点才算修改成功。

**特别防止双重真相：** `TemplateCriterionSpec` 编辑区显示的目标与 `RuleSpec`/Pi Agent 最终收到的生效要求要能对照追溯；自然语言模块允许存在，但有硬性制度适用、确定性计算、角色权限要求时不能只靠未经校验的一段自由提示词。

## 8. Markdown 辅助导入不能变成“一键自动发布”

五份文档的章节顺序并不一致（I 的 §12、A 的 §12、S 的 §17、P 的 §16、C 的 §11 才是专门给编辑器的抽象建议）。首版不应假设每份 MD 第 N 章含相同数据。

应依次进行：标题/表格/规则 ID 和出处定位 → Agent 辅助候选映射 → 未映射内容单列 → 作者核实业务边界、政策适用和强制义务 → 生成草稿 → 静态审计 → 生效预览 → 测试 → 发布。

**导入率高不代表语义正确。** 保留源文件名、章节/行范围、原文摘录、判断状态；无法可靠映射的复杂关系必须报告出来，不能丢弃或擅自转换为“需要上传附件”。**也不要求把所有 Markdown 转换成字段或节点**：可审查的自然语言责任说明可以作为有效草稿保留；需精确机器处理的条件、计算与授权则按需结构化。输入中的指令不能覆盖制作 Agent 的系统权限。

## 9. 五套模板反向验证测试合同

以下是**需实现/执行**的验收点，不是本轮已跑通过的测试：

| 编号 | 样本 | 要求保持的语义 |
| --- | --- | --- |
| G01-01 | I：旧身份证合法收回，新旧姓名由权威文书关联 | 不机械强制旧证件扫描；合法替代可被核验 |
| G01-02 | I：一份文书同时证明更名及更号 | 两个 Claim 都有独立覆盖，不能重复索取证明 |
| G01-03 | A：同一档案件申请查阅和复制，委托只覆盖查阅 | 查阅与复制独立结果，禁止跨操作继承授权 |
| G01-04 | A：档案目录可见、真实开放状态未知 | 不把已公布当已开放，等待馆方可信来源 |
| G01-05 | C：关联教职工已故，申请人代理资格未知 | 不把非在职视为完全无资格；关系与代办权限分别判断 |
| G01-06 | C：派遣协议存在，但具体人员—接收单位链接不足 | 服务事实和个人资格不能因为有合同就自动通过 |
| G01-07 | S：申请阶段制式表后续签章栏留白 | 不把未来有权部门的签章当提交者缺件 |
| G01-08 | S：获批稿与待印稿版本不符 | 旧批准不自动覆盖变更的用印对象、章种和份数 |
| G01-09 | P：处于政审出具阶段，不是收件完成阶段 | 不提前要求接收端最终完成态签章 |
| G01-10 | P：材料仅支持形式检查或敏感事项无法确认 | 不做政治/思想实质裁决；需要有权人工复核 |
| G01-11 | 任一：校本细则未知，只有外校案例或模拟规则 | 不自动成为本校刚性拒件依据；保留政策待核 |
| G01-12 | 任一：材料 OCR 失败、几项问题并存 | 保留未读、冲突、缺证和局部检查；不汇总成“已通过” |
| G01-13 | 原模板 → 作者态 → 模块化 → 固定运行快照 | 逐条比较有效规则、触发、范围、出处、角色、人工边界和正反例 |
| G01-14 | 模块/校本规则版本变化、材料替换 | 历史快照及结论不被静默改写；新运行有影响范围和差异 |

测试预言必须与 Agent 待审材料**分开存放**。先建立可追溯的**必核事项、业务边界、制度适用、例外与预期行为**基线，再谈“模块化前后等价”；不要求模型输出同样的措辞、工具顺序或推理轨迹。比较的是是否覆盖同样的审核责任、误杀/漏放、未知/失败处理、证据出处和人工决定边界；不能直接拿模型对原 MD 的自由回答当金标。

## 10. 建议开发顺序

| 阶段 | 交付物 | 验收边界 |
| --- | --- | --- |
| **D0：横向分析（已完成）** | 五模板差异/共性、分层模块候选、代码缺口、验证合同 | 仅研究结论，不声称模块已可用 |
| **D0.5：轻量语义模块与 Agent 编辑试验（下一步）** | 定义最小责任契约；用普通文本审核和 C/A 高复杂度场景试写语义/规则/复合模块；检验批量编辑、预览及覆盖 | 验证可少量结构化且不遗漏审查责任；暂不锁死作者态 Schema |
| **D1：作者态数据契约（D0.5 后）** | 稳定 ID、版本、责任/来源、限制与组合引用的最小协议；按实测需要选择性支持业务角色、Claim 和证据关系 | 结构化内容不成为所有模块必填；强制规则不得只藏于不可校验的提示词 |
| **D2：最简与复杂双端映射** | 一份普通文本审核 + C 双分支 + A 的 `item×operation` 边界试点 | Agent 能自主核验且覆盖可验证；未知规则不被提升为已生效必交 |
| **D3：两模块抽取与反向重组** | B01、B02 模块实例，C/A/I 跨模板比较与回归 | 模块版本/参数/权限、反误杀、证据覆盖未退化 |
| **D4：其余模板覆盖测试** | S 的用印批准稿版本/阶段，P 的出具/收件和敏感边界 | 五套在统一有效快照与独立金标下可比 |
| **D5：编辑器增量 UI** | 审核责任列表、模块引用、来源、预览/测试优先；高级条件和证据图按需提供 | 复用 `TemplateWizardPanel`，节点图只是可选视图，不做平行审核引擎 |

**P0 工程风险仍是“规则的双重真相”：TemplateCriterionSpec 与 RuleSpec 如何映射为同一份真实生效要求。** 不强求每条自然语言任务填写 RuleSpec 全量字段，但对必核项、硬性条件、制度效力和权限必须能核对运行时真值。D0.5 验证行为与输出；D1 解决最小持久化和映射。

### D1 仍需专门讨论的选择

1. 作者态是否使用独立关系结构，怎样无损映射到现有 `ReviewSubject`；
2. Claim/Evidence 多对多及替代条件最终如何落在运行态，如何保留来源与作用对象；
3. `TemplateCriterionSpec` 与 `RuleSpec` 的唯一可信表示、规则版本与编译映射；
4. 阶段要求超出 `submission/decision` 时如何兼容扩展；
5. 模块参数的校本授权与冲突规则，何种不确定性禁止发布；
6. 各份 MD 的源段映射与已完成离线测试包是否能够实际拿到、运行。

## 11. 最终判断与未定项

五份 G01 Markdown 为复杂场景提供了可靠的设计压力测试，但**模板系统不应被 G01 的复杂行政证据链锁死**。普通文章格式检查、科研报告核对或其他轻量业务可以直接由完整自然语言审核要求组织 Agent 工作；复杂 G01 才按需组合来源版本、关系授权、证据替代和条件规则。

**推荐的产品原则：薄运行内核 + 灵活的语义审核模块 + 可组合的完整模板 + 按需结构化能力 + Agent 优先编辑接口。** Blender 的模块封装和可视化能力可以借鉴，几何计算式逐节点编程不是我们的目标。

在推进 D1 之前，先完成 **D0.5**，检验三类表达是否足够支撑实际 Agent 审核与跨模板复用；再讨论以下待定问题：

1. 一条“必核审核责任”的最小稳定 ID/粒度与覆盖状态应怎样表示，怎样避免拆得过碎；
2. 语义任务、可计算规则和专业执行器如何对应同一份运行约束，不产生不同版本的“真规则”；
3. 复合模块的引用、版本、可配置参数、部分失败与未知怎样向外汇总，不要求 Agent 固定执行路径；
4. Agent 事务性编辑的授权边界、差异预览、失败回滚、并发和审计细节；
5. 哪些场景必须升级 Claim/Evidence/对象关系等结构化能力，以及这是否确有测试收益；
6. 真实 Markdown + 合成案例如何形成独立的行为金标，而不是把自由文本相似度当作“等价”。

**本稿仍是设计分析：D0.5、D1、真实模板编译器、覆盖记录器、编辑 API 和 Pi 端到端回归均尚未实现。** 第 15 号规范关于发布权限、已证校规、版本隔离和审核/正式决定分离的底线继续适用。
