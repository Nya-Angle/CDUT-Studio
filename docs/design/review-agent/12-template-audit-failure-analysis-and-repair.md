# 模板实测问题分析与可用性修复方案

日期：2026-10-08。代码与材料基线：`50cc7839`。本文是问题诊断和下一轮实施方案，本次没有修改业务代码；“建议”“应当”不代表功能已经实现。

用户标准：**目前先做到功能能用、好用。修复要减少漏检、等待和重复操作，不以架构完整或界面精美作为交付条件。** 保留现有三栏、案卷、文件编排、模板版本和项目 Pi 运行时，在审核插件内逐项补通链路。

实测依据：[逐模板报告](../../../outputs/template-review-suite-2026-10-08/RESULTS.md)、[真实模型运行记录](../../../outputs/template-review-suite-2026-10-08/run-results-glm-final/results.json)和各案卷保存的状态、节点产物。模型经项目 Pi Adapter 调用，审核工具由插件提供。

## 1. 对上一轮结果的进一步校准

上一轮解决了“遇到模型故障整案无法收尾”的问题，但收尾时把缺失结论转成人工待办，只保证流程有结果可交接，不能据此认定自动审核已完整可用。

34 项模型待确认/补件中包含刻意缺少正式制度、审批或材料的测试场景，不能全部归为软件故障。应优先修复软件未完成的 9 项，再衡量可自动处理的范围是否确实减轻了人工工作。

## 2. 原因与最小修复

### 2.1 批量工具过早结束，模型没有机会修正被拒绝的检查

**已确认的代码缺陷。** `submit_checks` 的外层 `ok: true` 只表示批次被处理，其中每一项仍可能 `ok: false`。`buildPiReviewToolDefinitions` 和模型客户端看到非空 `results` 就认为可以结束；没有核对逐项是否成功，也没有核对当前任务是否还缺规则或目标。单条 `submit_check` 成功后也会结束整轮，即使还有其他规则未提交。

因此“批量调用完成”可能变成“只收到部分检查，甚至全部被拒绝”，随后执行器为缺项生成待人工确认。完整模型回执没有持久保存，现有产物主要记录工具名字，**不能证明这 9 项分别是引用被拒、漏提交还是服务异常；过早结束是已确认的风险和修复点，不能把全部漏项直接归因于它。**

最小修复：

1. 批量返回逐项 `ruleId + target + ok + errorCode`，并汇总 accepted/rejected/missing。结束条件使用当前任务的规则与目标清单，不能使用“调用过写工具”。
2. 已提交且有效的项目保留；只把被拒绝项和漏项交给模型作一次定向修正。仍失败时如实结束，不启动不限次数的搜索或整案重跑。
3. 允许主动提交有依据的待确认/补件作为一项已执行检查；服务失败、未提交、引用无效使用已有 `execution-failed` / `not-executed`，不要伪装成业务待确认。
4. 摘要由系统按已保存的检查结果生成。检查完整后可以结束 Pi，省去额外模型总结；不能要求每次为了生成一段总结再调用模型。
5. 写入按本次运行的规则、目标和输入版本去重。失败后只补缺项，不能重新追加已接受的结果。

当前批量工具会截取前 50 项；超过上限时应明确返回未处理范围并拆批，不能静默截断后触发整轮结束。

用户应看到：“5 项已核对，1 项因引用校验失败未完成”，并能点击“重试未完成项”或自行处理那一项。

### 2.2 数字核对没有进入确定性路径，分项模板也表达不了计算

**模板设计缺口与接线缺口同时存在。** 现有 `deterministic-engine.ts` 已有条件和组级计分，但本轮检查没有一项由它产出。`TemplateCriterionSpec.execution` 只允许 `semantic | manual`，分项要求编译时没有计算定义；预算、重复票号和工作量核对都只是自然语言要求。

当前提取节点又只提取确定性规则需要的事项字段；没有这种规则就跳过提取。案卷级字段和工作簿行数据也没有形成可直接计算的统一输入。数字存在于材料里，并不等于系统有两组已绑定的数值可供比较。

最小修复先做两个常用操作：**金额/数量合计一致性、重复编号检查**。

- 扩展现有分项要求，使它能选择确定性操作及输入；先提供这两个预设，不做任意脚本、通用公式语言或新的计算平台。
- 为操作绑定“申报值”和“明细行值/编号”，保留材料版本、块或单元格位置。工作簿优先使用现有单元格解析；DOCX 文本由 Pi 提取为有出处的候选事实，审核员可在现有界面纠正。
- 数字必须可从引用内容规范化验证，不能仅因存在引用就接受模型提交的任意数值。OCR 有歧义时先确认具体候选，人工已确认值优先保留。
- 提取工具支持本操作所需的案卷级数值，不能为了录一个总额虚构新的事项。已有值有争议时保留各来源，不能把申请数额覆盖成明细合计来消除差异。
- 程序计算逐行合计、与申报值比较，并输出每个操作数、结果、差额、单位和来源。金额用“分”等整数单位，避免浮点误差。
- 明细行范围须明确，排除表头、合计行和申报总额行；不能直接对整列所有数字求和。公式缓存缺失、单位不同、解析截断或行范围不明确时，要求确认具体输入，不输出完整合计。
- 缺少经费限额政策只影响“是否超限/能否资助”，不影响已经有证据的 1,680 与 1,480 一致性检查。真实性、计算一致性和最终批准分别处理。

不要只把预算要求改成 `execution: deterministic` 就认为接好了；现有组级计分也不能直接替代跨文件比较。需要为上述两个操作补明确的检查判定和输入绑定。`when` 表示适用条件，不应把“两个金额相等”塞进 `when`，否则不相等可能被跳过成“不适用”。

第一项验收就是本轮活动样例：必须稳定输出差额 **200 元**，引用申报材料和工作簿相应位置；不能再次留下“请人工自行算一下”。随后接报销金额、重复票号和教师学时，再逐个迁移其他模板。

### 2.3 图片失败被误诊为“不支持视觉”，已有 OCR 没有覆盖 PDF 页图

**已经观察到请求失败；上游真实原因尚未确定。** 本地代码把 500、502 和超时等也归入视觉兼容失败，降级提示直接写“模型无法接收图像”。这些错误也可能来自网关负载、传输、请求大小或服务中断，不能据此断言 GLM 本身不支持视觉。

当前公共模型注册对未命中目录的模型默认设置 `input: ['text', 'image']`，这也只是本地声明，不是当前渠道已经可用的证明。原设计 [07 §4.4](07-application-and-execution-design.md#44-pi-执行器合同) 已要求区分能力声明、实测与未知；这部分尚未完整接入。

另一个独立缺口：V2 OCR 节点只选择文件名为 PNG/JPG 等的材料，没有处理 PDF 和 DOCX 中已提取的 `imageAssetPath`。当前 OCR 产物主要记录识别块数量，没有把全部识别文本及坐标装入审核工具使用的材料索引。系统 Tesseract 探测还在异步子进程返回前读取结果，可能把实际不可用记录为 available。

最小修复：

1. 错误提示改为本次事实，例如“本次图片识别请求超时，第 1 页未完成”；仅有明确的能力拒绝或探测结果，才能显示不支持图片。
2. 首次使用未知渠道视觉能力时，通过同一个 Pi 适配器作一次小图片识别验证；按渠道、模型和相关配置缓存结果，不在每个案卷重复验证。文本/工具可用也不等于图片可用。
3. 优先按当前分项或检查发送相关页图。超过现有 8 张上限时分批处理，保存逐页结果；不能只取前 8 张后结束整个视觉审核。
4. 将 OCR 的输入改为实际图像块，覆盖独立图片、PDF 页图和 DOCX 内嵌图片。把识别出的文本、页位置和坐标写入现有材料解析索引；引用保留 OCR 来源，不冒充 PDF 原生文字。
5. Tesseract 探测等待真实退出和语言包结果；现有引擎可用就复用。视觉请求失败后可对相关页使用本机已有 OCR；两条路径都失败时，只留下具体页的人工待办。
6. 图文混排材料保留原件和页图，按相关页交视觉模型识别；文字层仍用于检索与定位。不要把全部文档只压成纯文本，也不要把所有表格数值只保留成图片。

首版不引入新的付费 OCR 平台或大型服务。若目标机没有 OCR，引导用户使用已验证的视觉渠道或人工看图，并保留其他已完成检查。图片位置引用只有在识别记录确实成功时，才可支撑图片中的事实。

### 2.4 请求任务过大，超时与降级预算也不够明确

当前模型调用可进行 24 轮，单次默认 150 秒；图片失败后的纯文本请求重新取得一份预算。一次视觉检查可能先等待 150 秒，再等一次文本请求。上下文按每份材料截取前 6,000 字，仍把全案材料和规则一次发送；图片也是按整个案卷收集。材料增加后，总请求成本没有被同一个任务预算控制。

超时定时器只置标记并调用 `abort(sessionId)`，`for await` 要收到下一条消息才会检查标记。如果中止路径没有让迭代器退出，不能仅凭设置了定时器就保证调用按时结束。这是代码合同风险；目前的记录不足以断言所有挂起都来自这里。

最小修复：

- 每次按一个分项或少量规则执行，保留同一个案卷和同一次审核；结果按规则目标合并。失败重试只针对失败批次。
- 初版沿用现有 150 秒作为一项任务的总预算，首次请求、文本降级和一次修正共享预算，不叠成无限等待。需要增加预算时必须有实测依据。
- 保留 Pi abort，并增加可结束等待的 deadline。超时/取消后关闭本次执行代次，拒绝迟到写入；不能只用 `Promise.race` 提前返回，却让后台工具继续修改案卷。
- 已有解析块直接复用。执行器装配和 parse 节点重复读 PDF/Office 的工作应合并，避免运行还未进入可见节点就长时间解析。
- 显示实际阶段、正在处理的分项/页及等待时间；不猜百分比。用户可取消，失败后可重试未完成范围，已完成结果继续可见。

关闭 Pi 原生重试是避免写入重放的必要止损，但不能等同于“此后永远不重试”。应在审核执行层统一作有限、可定位的重试，并明确哪些写入已经接受。

### 2.5 综测没有规则仍能进入自动流程，模板可选与可审核混为一谈

完整综测模板无有效规则时，检查计划为 0；发布校验主要给出 warning，用户仍可进入自动审核。上传一个 `rules.md` 也不等于它已经编译、确认并成为本案的有效规则。

最小修复是让缺口提前可见，而不是一刀切禁止使用模板：

- 选择模板时显示它能做什么。综测未配置积分规则时标为“可整理材料，计分依据待配置”，提供“补充审核依据”和“仅整理材料”。不要承诺能自动计分。
- 开始前按现有有效规则集显示计划数量和缺失依赖；0 条规则直接进入材料整理结果，不再浪费模型调用生成“暂无规则”的摘要。
- 利用已有模板/政策编辑和确认服务接入规则。发布新版本、明确批次与适用范围，旧案卷继续引用原版本，不静默改写历史模板。
- 姓名、日期、附件完整性、金额一致性等检查可以先做；涉及本校积分、名额和财务限额的判断才等待对应制度。不能为了缺一份政策阻断全案所有工作。
- 内置模板提供清楚的分项和已实现操作；缺少地方制度时说明需要补什么。不要为了“开箱即用”虚构积分或审批标准。

“没有规则安全返回”可作为正确的失败路径验收；要把综测称为可用的审核模板，还须验证用户能在现有入口补规则、确认、执行并查看逐项计算。

### 2.6 覆盖和出处接线不完整，导致既有误报，也有可绕过的校验

当前文件登记后 `usage` 为 registered，实际搜索和上下文发送没有完整维护使用账本。因此已产生正确局部引用的文件仍统一报“未完整读取”。另一方面，把已解析全部当“已审查”也会造成反向误报。

组级覆盖存在具体不一致：结果按 `subjectIds` 建键，账本按展开的组值寻找；V2 节点又没有为这些检查输出一致的 group values。最终 7 条组级检查记录被记成未执行，这是 76 条记录与 69 项覆盖完成数不一致的来源。

出处验证也有缺口：`ref()` 在没有 blockId 时不会核实 quote 是否属于该文件；`submit_check` 只要求至少一条能解析的引用。V2 的 `verify` 节点仍返回空的 done 产物。本轮外部测试脚本做了来源审计，不能把它当成产品已有同等审核能力。

最小修复：

- 各检查用同一个规则与目标键。已经有 `target.groupKey`，应接通实际分组；没有 groupBy 的全组检查使用明确的全组键，不补一套新分组系统。
- `completedChecks` 不计 `not-executed` 和 `execution-failed`。系统生成的失败占位记录也不计自动执行成功。
- 维护实际提供/读取的文本块与图片页；少量关键词命中只记局部覆盖，不宣称整份审完。对计划实际不需要的材料说明用途，不让所有额外附件一律阻断无关检查。
- 修正读取状态时同时核对输入哈希：`computeRunInputHash` 目前包含 `usage/unusedReason`，但这两项是执行输出。更新“已读取”不应让同一运行自己变成过期；审核输入仍由原件内容、解析修订、字段和规则等决定，历史运行原记录保留。
- 把已有引用和计划核对放入真正的 verify 处理：新的语义符合/不符合结论要求 blockId 或等价精确位置，验证归属、解析修订和引文；只给文档 ID 的任意 quote 不能过关。
- 检索输出明确命中总数、返回范围和截断情况；当前每块只提供前 400 字，`truncated` 标记也没有实际分页处理，不能用它冒充完整读取。
- 旧引用保留兼容展示，并如实标注定位精度。有效出处不等于理由成立；数字结论由程序和具体操作数校验，语义判断在结果中展示所用段落，不再加一轮大模型来“替前一轮盖章”。

### 2.7 测试材料泄露答案，当前结果不能证明稳定比对能力

合成申报材料的摘要直接写了“申报总额与附件不一致”“96 与 90”“1,680 与 1,480”。模型识别到差异，可能只是复述摘要，并不能证明它读取两份材料完成独立计算。合成声明又使模型把多项数据真实性统一转人工，这掩盖了单纯一致性检查能完成多少。

下一轮仍使用合成材料，明确禁止用于真实审批；但把预期结果放在不送给模型的 `expected-behavior.json` 中，申报材料只包含自身申报值，附件只包含独立记录。按同一检查准备正常、冲突、缺输入三个场景。真实性待人工不应妨碍程序报告样例数字是否一致。

重新记录“可执行检查是否真正产生有效结果”“已设置差异是否检出”“引用是否定位到操作数”“失败后能否继续”。不追求所有案卷为符合，也不以导出成功代替审核验收。保留首次失败，按当前版本新跑一轮，不能从历史成功尝试拼出一份看起来全通过的结果。

## 3. 用户可直接完成的操作闭环

以活动预算为第一条完整链路，尽量沿用现在的页面和业务服务：

1. 用户选活动模板，把申请书放待审材料，把预算表放对应分项；文件可排序、删除或折叠，引用以稳定版本/块 ID 保存。
2. 开始前显示“可核对预算计算；经费额度需补制度”。用户无需先配置新平台或读技术文档。
3. 系统取申报总额、明细行数值并显示来源；绑定不确定时让用户只确认这两个输入，复用现有字段纠正入口。
4. 程序输出“申请 1,680 元，明细 1,480 元，相差 200 元”，两侧引用可打开。模型继续处理活动方案等语义项目。
5. 图片、政策或服务有缺口时，右侧分别显示具体问题和动作：查看/重试这一页、补充这一项依据、重试未完成检查。已经完成的预算检查保留。
6. 用户纠正输入或补材料后，重新核对受影响的范围；变更输入产生关联新运行，旧结果保留可查。

通用 Agent 操作仍经过已有审核业务服务和授权范围，与用户点击共用同一链路。调试也调用这些服务/工具，不靠反复操作屏幕完成上传。内部审核 Pi 继续只使用插件受控工具，不能为了解决读材料困难给它开放通用 shell 或任意文件写入。

## 4. 下一轮按可用收益交付

| 顺序 | 最小交付 | 主要代码落点 | 完成条件 |
| --- | --- | --- | --- |
| 第一批：修漏检和失实完成 | 批量逐项回执、只修正漏项；使用现有失败状态；组级账本正确匹配；活动预算与重复编号两个确定操作；重试范围能定位 | `review-tools.ts`、`pi-review-executor.ts`、`pi-review-agent-client.ts`、`v2-executor-factory.ts`、`coverage-ledger.ts`、shared 模板类型及现有编辑入口 | 预算差额 200 元稳定检出；单项被拒可修正；组级记录不再误报；系统失败可见且可重试 |
| 第二批：图片与等待能用 | 逐页视觉验证和错误分类；PDF/DOCX 页图进入现有 OCR 和索引；统一 deadline、取消和迟到写入保护 | `pi-review-agent-client.ts`、`v2-executor-factory.ts`、`system-tesseract-ocr-adapter.ts`、现有运行管理及结果界面 | 图文混排样例能识别相关页并引用；不支持/超时有具体范围；取消与重试不丢已完成结果 |
| 第三批：模板真正开箱可用 | 开始前说明规则/政策缺口；把已实现数值操作接入相关模板；无答案提示的 11 模板实测 | `builtin-templates.ts`、`effective-rules.ts`、`template-store.ts`、模板/案卷现有页面、材料套件 | 每个模板的检查、补件、人工处理和继续入口可操作；综测补规则后能出计算结果，未补时清楚显示整理范围 |

第一批内部先完成批量回执和失败显示，再接预算计算，每一步用同一个活动案卷验证，避免同时重构所有模板。分项拆请求只调整执行范围和结果合并，不把一个综测拆成多份案卷。第三批完成前不能宣称所有模板已经全功能完成。

公共 Pi 适配器属于项目共同基座。审核先在客户端侧修正预算、错误分类和诊断；只有需要取消/工具回执等公共合同支持时才作小范围适配修改，不重写通用 Agent 和模型传输层。

## 5. 功能验收标准

本轮不安排压测、性能排行榜、界面视觉重做或大范围重构测试。必要的失败路径、取消和恢复属于功能验证，要做。

| 场景 | 必须观察到的行为 |
| --- | --- |
| 批量 3 项中 1 项引用错误 | 2 项有效结果保存；错误项返回具体原因并可修正；不在第一次批次调用后把错误项永久转人工 |
| 第一次只提交 1 条规则 | 任务剩余规则继续处理或明确未执行；不得宣称整批完整 |
| 活动申请 1,680、明细 1,480 | 程序给出差额 200 和可打开的数值来源；无资助政策也能完成这个一致性检查 |
| 合计一致、重复票号、缺一行值 | 分别产出一致、重复位置、具体缺输入；缺值不当 0，合计行不重复计入 |
| 同一检查执行失败后重试 | 已成功部分不重复写入；仅失败范围重新运行；输入已变时不沿用旧判定 |
| 同案组级检查 | 计划、结果、账本使用相同组键，已有检查不再误报“未执行” |
| 文本正常、图片失败 | 文本结果保留；具体页标明未识别；500/超时不自动写成模型永久不支持视觉 |
| 图文混排 PDF / DOCX | 文字块与相关页图均进入所需检查；图片事实有真实识别记录和页定位，不能仅靠页图存在判符合 |
| 长材料/工作簿超当前解析上限 | 未覆盖范围明确；可继续处理所需部分；不得用前 100 行当完整明细总额 |
| 模型不再发送事件、用户取消 | 总预算结束或取消后等待能结束，状态可查询；迟到工具结果不修改已结束运行 |
| 综测未配规则，随后补规则 | 先明确提供整理功能和补规则入口；确认规则后实际出逐项检查/计算；无依据时不出积分和全符合结论 |
| 11 模板当前版本实测 | 不读取答案文件；正例、冲突、缺输入按可执行范围验收；报告区分模型检查、程序检查、原定人工和系统失败 |

“能用”要同时满足：**应由程序完成的核对确实完成；模型未完成的范围说清楚；用户能纠错、补材料或重试并继续；已完成结果和原件保留。** 待人工的审批可以继续待人工，软件应该完成的基础核对不能长期以转人工替代。

## 6. 不再重复的坑

- 不把 `completed`、有 PDF 页图、有精确引文当作审核成功；它们分别证明不同范围。
- 不为了避免异常把全部结果涂成“待确认”；失败原因要能定位到规则、页或输入。
- 不依靠更长 Prompt、更大的超时或换模型修复模板不能表达计算的问题。
- 不再增加一份只有架构名词的总设计。本轮验收直接使用活动预算、图片识别和失败继续三个用户场景；既有 [07 应用与执行设计](07-application-and-execution-design.md)中未接入的能力按上述最小路径落实。
- 不因为一个分项失败清空整案，不把补件后继续做成从零上传，不为模型摘要重做已经成功的核对。
- 不静默迁移用户模板和历史案卷；内置模板升级有明确版本，自定义顺序、材料归属和人工纠正保留。
- 不先安装新的 OCR/数据库/队列服务；复用现有本地存储、解析器、Pi 和审核插件，把端到端功能先打通。

## 7. 只保留排查需要的诊断

目前临时 Pi transcript 在结束时删除，节点主要保留工具名与最终产物。这减小了临时数据，却使批量拒绝和上游失败的归因不够充分。下轮在现有运行产物中增加简短诊断：实际模型/渠道标识、请求开始结束时间、文本或图片路径、发送页数/字节数、工具逐项接受/拒绝及错误码、终止原因、重试范围。

诊断不保存 API Key、Authorization 或完整请求头，不把思考过程当验收证据；原文证据按案卷现有存储保存。正常结果和失败结果都能从同一案卷复查。上游视觉故障只有在获得明确错误响应或小请求实测后才进一步定性，本轮不虚构服务端根因。

## 8. 已落地修复与复验

本轮按“审核先能可靠完成、错误能回到具体材料、未核内容不冒充已核”的顺序修复：

- `submit_checks` 按每条结果校验并返回接受/拒绝原因；只接受当前计划中的语义规则和完整适用目标，校验来源块、原文引用、数字原文与重复目标。部分失败不再触发提前结束；成功项按稳定检查 ID 更新，失败项仍可修正重提。
- 将预算明细核对和票据编号唯一性做成模板可配置的确定性检查。预算逐行按分求和、检查数量乘单价并排除合计行，和申请书申报金额比较；缺行、金额缺失或解析不完整会要求补充/确认，不按零算。活动预算与报销模板发布为版本 2，新案卷采用新规则，已有案卷继续固定在旧版本。
- V1 案卷首次迁移改为读取最新已落盘模板版本，写入 V2 后固定版本；重跑时没有新抽取字段也会把现存事实（包括人工确认值）保留在运行产物中。
- 修正覆盖统计的目标范围与状态计算；文件级引用不能再充当具体检查事实的依据，图片证据必须指向实际图像块。材料输入指纹也不再因界面上的使用/未使用状态变化而无效重跑。
- PDF、DOCX 和单独图片中的图像页都会进入本机 OCR。超过单次视觉请求上限时改为逐批送 Pi；每页识别文字关联回原图块及其位置，失败批次会标出具体页面并继续后续批次。连续两批都无法读取时停止重复等待，并把剩余页面交人工核对。视觉请求失败会说明实际错误并降级到文本路径；取消及请求超时会中止 Pi 运行，不把网关错误写成模型不支持视觉。
- 模板编辑器可创建数值合计与唯一值检查；结果面板显示确定性、语义和人工检查数量，并标明缺少的材料槽或正式规则。

功能验证包括批次逐项拒绝/恢复、数值引用、预算差额、重复编号、缺失金额、分组覆盖、案例字段、OCR 页面坐标、8 页以上视觉分批及失败继续、Pi 超时/取消、Tesseract 语言包探测、V1 案卷使用最新模板版本迁移、版本 2 模板规则结构校验，以及两条单案运行旅程。审核功能相关 10 个测试文件合计 83 项通过、0 项失败；全仓 `bun run typecheck` 在收尾复跑中通过。

本轮没有再次调用在线模型重跑 11 个模板，也没有把旧的 GLM 实测结果写成新版本复验结果。视觉识别失败页和规则缺少正式政策/人工判定的模板仍须由审核人处理；程序不会用样例或生成式文字替代审批结论。
