# 21｜批量审核离线入口与桌面 UI 补验

日期：2026-10-11。测试分支为 `feat/batch-review-triage-v1`，代码基线 `71d2dfba`（其审核代码与 `1032ef0e` 相同，仅新增验收文档），Electron 版本 `0.15.148`。环境为 Linux/Xvfb、独立配置目录和合成申请数据。

## 1. 更正离线登录前提

上一轮未查到内置离线演示账户，错误地把 CDUT 专区登录页记为批量审核 UI 的阻塞。本轮已通过真实页面表单验证：登录后可以进入材料审核与批次管理，重启后重新登录也成功。

演示账号和密码已按使用者授权写入 [B 阶段验收说明](16-batch-review-stage-b-local-acceptance.md#离线桌面验收入口)。页面路径是 **CDUT 专区 → 演示账户登录 → 材料审核卡片 → 批次管理**。

主进程先调用 `cdutDemoService.tryLogin()`，命中演示凭据后直接返回内存画像；没有进入真实 CAS、没有启动保活。两次启动/登录后，隔离目录里没有生成 `cdut-account.json`。演示登录用于打开页面；批量业务操作仍记录本地 reviewer 或经过批次授权的 system 来源。

学校正式身份和生产端口接入属于后续校方部署范围，不是本地 B+C demo 的验收前提。

## 2. 验收方法与证据范围

- 使用五个合成 V2 案卷：A 符合、B/C 缺少证明要素、D 需要人工核实、E 技术异常；使用同一已发布合成模板、政策版本和受控证明文本。
- 为了独立验收批量面板、分流与业务事务，通过现有仓库服务预置合成运行结果，运行结束时间早于本轮 UI 操作。完成队列状态和中断状态也是显式构造的测试前置数据。
- 批次创建、选案、问题组预览/确认、策略确认、自动处理、补件回复/满足、定向重试、中断恢复与定稿通过实际 Electron renderer 页面操作；随后通过只读 API 核对聚合、审计来源、回执与批次状态。
- 新配置目录没有模型渠道。本轮实际点击队列执行时验证了未配置模型的逐案失败路径；预置完成运行的场景不能作为真实模型推理已验收的证据。
- 本轮没有修改审核功能代码。上一轮该代码基线上的专项 132 项、全仓 3626 项通过（5 项平台跳过），以及类型检查/边界/皮肤/构建结果继续对应 [20 号报告](20-batch-review-qa-round3.md)。

## 3. 实际桌面操作结果

| 场景 | 实际结果 |
| --- | --- |
| 离线登录与入口 | 两次启动均能以演示账户登录并进入批量审核面板；不需要校方 CAS |
| 页面创建批次与默认辅助 | 创建五案批次成功；显示“自动化：辅助”；五案 `decisions` 均为 0 |
| 混合分流与保守归组 | 显示 1 案可通过候选、2 案可退回候选、1 案待人工、1 案技术异常；两案相同缺证明问题归为一组 |
| 人工子集操作 | 在两案问题组中只选 B，预览显示可处理 1/1；确认前执行按钮禁用；确认后成功 1 案。B 新增一条 disposition 和本地 reviewer 回执，C 没有产生同类写入 |
| 自动补件逐批授权 | 未勾选确认时启用按钮禁用。确认 auto-return 后仅 B/C 写入 `return` 与 open 补件请求，要求来自已发布规则的 requirement；A/D/E 不产生决定 |
| 全局代批关闭 | 勾选批次 auto-approve 仍被主进程拒绝，显示“全局 AI 代批授权未开启”；原 auto-return 策略保留 |
| 自动通过三层授权 | 在 V2 案卷的 Agent 指派高级区，经风险弹窗开启全局开关，再逐批确认 auto-approve。只有 A 新增最终 pass 决定，审计为 `actorSource='system'`；D/E 保留给人工或技术处理 |
| 重复执行 | 再次点击自动处理报告执行 0 案；A 的决定仍只有 1 条，B/C 也没有重复创建退回或补件 |
| 补件回复与满足 | C 回复后仍为 awaiting-supplement，批次条目仍为 done；审核员判定满足后才回到 reviewing 并变为 queued。旧运行被判为 stale，再次自动处理没有产生新批准 |
| 定向重试与队列失败 | 点击 E 的“重试本案”只把 E 入队，其他条目不变。实际执行队列因缺少模型渠道把 E 标为 failed，记录具体错误，A 的既有决定没有重复执行 |
| 中断恢复 | 合成前置状态为批次 running/E running。点击“恢复中断批次”后批次回到 queued，E 为待核查 failed，其他案卷状态与决定保持一致 |
| 定稿门槛与冻结 | 五案混合批次因未完成案卷而拒绝定稿。单独把已审批 A 纳入已完成批次后，核验定稿成功，生成快照 hash，执行按钮禁用；直接调用运行 IPC 也拒绝已定稿批次 |
| 重启恢复 | 重启、重新演示登录后仍可读到 5 案、2 批次、原混合批次的 3 条自动处理回执；A 决定 1 条、B 人工 disposition 1 条，均未重复 |

## 4. 本轮观察到的界面问题

1. **补件回流后的历史动作容易误读**：C 已满足补件并重新入队时，“状态”列显示“排队中”，但“分流建议”列继续显示上轮“已自动退回补件（业务已写入）”。历史事务确实存在，建议把这条文案明确标为“上次动作”，同时显示本轮待审核状态。
2. **队列完成提示缺少失败统计**：E 因模型未配置而失败后，页面仍弹出通用的“本轮审核及已启用的自动处理完成”成功提示。逐案状态正确，建议完成提示直接列出成功、失败和待人工数量。
3. **拒绝消息带有 Electron 调用细节**：全局授权和定稿被拒时，用户会看到 `Error invoking remote method 'review-v2:batch-action'` 前缀。业务原因已经清楚，建议页面只呈现该原因。

上述属于实际观察到的 UI 可读性问题。核心业务门槛在本轮操作中生效，没有出现把技术异常、待补件或待人工案卷自动通过的情况。

## 5. 当前结论与待验收项

离线登录阻塞结论已撤回。本地批量审核的主要桌面业务动作已补验；真实模型完成队列、Windows/macOS 发布包，以及全部证据/版本/角色负例的桌面矩阵仍需在对应环境补齐，已有服务级回归不能替代这些证据。

[20 号报告](20-batch-review-qa-round3.md)中实际复现的 V2 案卷 ID 路径越界写入仍未修复，继续阻断合并。本轮只做验收和文档更正；没有把学校真实认证或生产端口接入列为本地 B+C 模块合并的前提。
