# 批量审核自动化与相似问题聚类规范（v1）

> 日期：2026-10-10  
> 状态：**产品设计定稿，按切片实现；本文描述目标与约束，不代表所有功能已上线。**  
> 范围：审核模块的批次执行、自动分流、可授权业务动作、问题聚类、人工集中处置、恢复与验收。  
> 对照：[06 用户闭环](06-workflows-and-usability-design.md)、[07 应用与执行](07-application-and-execution-design.md)、[14 Pi 原生审核](14-pi-native-review-and-simple-workspace-design.md)、[15 模板模块化](15-template-modules-and-runtime-boundary-spec.md)。

## 1. 目标与基本决策

批量审核应当显著减少审核员逐案打开和重复处理的工作量。主流程为：

1. 同一模板/适用政策版本下，对每案独立执行已有审核 Agent，取得**可追溯且有覆盖记录**的结构化结果。
2. 批次编排层按明确规则对结果分流：可自动通过、可自动退回补正、需人工、技术异常、等待执行或补件。
3. 对异常和可重复处理的问题**先按结构化条件归组，再可选择性使用 AI 提炼相近根因**；汇总不改变原始审核结果。
4. 人工以问题组为入口查看差异和出处，确认可适用的处理策略；系统**逐案重校验并留痕执行**，允许排除少数案卷。
5. 材料补齐或人工修正后，仅对失效的案卷重新审核；历史运行、处理记录及版本保留。

**批量审核负责调度、分流、归组与业务动作编排，不重复实现单案的业务检查。** 主 Pi Agent 仍由单案服务执行。聚类不替代审核。**跨案审核本轮仅预留检查器接口，不实现跨案材料关联和联合推理。**

## 2. 三种语义绝不能混淆

- **运行状态**：未执行、队列中、执行中、完成、部分完成、失败、取消等；“运行完成”不是“业务通过”。
- **分流建议**：符合自动化条件、建议退回补件、需人工确认、技术异常等；建议本身不修改案卷。
- **业务决定与生效动作**：已授权并由 `RecordWorkspaceBusinessDecision`、阶段决定或补件事务服务成功记录的通过、退回、驳回及办理状态。必须有操作者身份、请求幂等键、有效输入哈希与修订号。

UI 将“已审完”和“已通过”分开统计。技术失败不能被计入业务不合格；未知/未执行不能被当作“没有问题”。

## 3. 批次组成与版本约束

- 批次创建时固定模板 ID/版本与政策版本；每案的当前模板版本必须一致。项目与批次引用相同版本仍要核对**实际适用输入哈希与规则**。
- 每案必须有可追溯的 `runId`、`inputManifest.hash`、`CheckResult`、`coverage`、证据来源及阶段。
- 运行后材料、事实、规则、政策或证明关联变化，旧结果只作为历史参考，不能继续用于自动决定。
- 重新进入队列的动作必须有明确原因；避免补件回流无限循环，记录轮次及最大自动重试次数。
- 不能将已定稿批次原地重写。重开新轮次保留来源、旧审批/报告和差异说明。
- 不把外部学校审批接口视作已经接入；外部写入必须使用授权的 `SchoolPort` 与可恢复的 outbox。

## 4. 自动分流规范

### 4.1 结果类别

| 类别 | 判定条件（示意） | 默认处理 |
| --- | --- | --- |
| `pending` | 未运行、仍在执行、等待申报人补件 | 队列/等待，不作新决定 |
| `technical-exception` | 失败/取消、缺检查结果、材料未读或版本失效 | 限次重试，持续异常转人工技术队列 |
| `manual-review` | 规则未确认、证据冲突、人工判断项、不可自动处理的违规/不确定结果 | 人工处理；不静默放行 |
| `auto-return-candidate` | 只有明确可补正问题，出处可靠、补正要素明确，策略允许退回 | 生成可执行草稿；授权且校验通过后事务执行 |
| `auto-pass-candidate` | 全部适用检查完成且合规、没有待处理事实/证据/补件、模板支持自动审批 | 满足事务门控和授权后执行；否则留人工 |

类别为**候选分流**，而不是 `BusinessDecision`。已经完成正式决定的案卷单独显示决定，不重复下发动作。一个案卷如果存在两种性质的问题，以要求更谨慎的类别为准。

### 4.2 强制前置校验

自动通过须同时满足：当前运行与本案输入一致；全部要求的材料已读且有效；有效检查数非零、计划检查全部有结果、没有未执行或执行失败；所有适用的硬性检查均符合；证据出处能定位到当前材料；无未解决的候选事实、证据绑定、人工事项认定、补件、冲突及必须执行的批次级检查；业务角色/阶段允许自动审批；启用策略并记录授权。

**严禁以模型自报置信度单独决定自动通过。** 现有 `assessDecisionReadiness` 是最终通过门控的一部分；第一版不绕过它、也不伪造人工确认。只有符合现有权限和认定要求的案卷才可能真正自动通过。

自动退回须区分**可补正问题**、**不可补正不合格**和**未知问题**。要求填写可核验的来源、具体原因、需要补充的材料或要素、接收方以及规则依据。 `non-compliant` 本身不等于可退回；`RuleSpec.onFail`、适用范围和检查结果综合决定可补正性。未知/歧义/未核对完的案卷转人工，不能生成“确定不符合”通知。

永久不符合资格的项目默认**不自动最终驳回**。涉及排名、名额或全批配额的模板，个别案卷检查通过不等于可以直接定稿；还需要全批计算与组织审批。

### 4.3 策略与授权

提供三档批次策略：

- `assist`：只执行、归组和准备业务动作草稿；正式决定均由人确认。
- `auto-return`：可自动提交满足条件的补件请求，正式通过仍人工确认。
- `auto-approve`：允许满足**完整自动准入门槛**的案卷自动通过，并包含可授权的自动补件。

创建批次时显式选择，默认 `assist`；保存操作者、角色、授权时间、模板适用范围和策略快照，展示即将作用的案卷数。开关不等于权限：每一次写事务在提交当时重新检查授权、角色、`expectedRevision`、`inputHash`、当前阶段与业务可用性；撤销时未执行动作必须停止。支持结果预演和逐案排除。

**第一阶段实施**可以先上线确定性的分流候选和聚类，再加入事务写入；页面和文档不得把候选数标记成已自动批准数。

## 5. 相似问题聚类与批量处理

### 5.1 先结构归组、后语义辅助

聚类输入为当前有效运行的 `CheckResult` / `AiOpinion`，至少保留 `caseId`、`runId`、`inputHash`、`checkId`、`ruleId`、`status`、`target`、问题描述、建议动作和 `sourceRefs`。

第一层用稳定规则标识、处理类型、适用范围和**保守的原因键**归组；同一案卷的重复表述可作为一组显示，但仍保留每一条检查的 ID。原因不充分或分组键冲突时宁可分开。

第二层可用模型找出语义相近的组，生成**建议合并**、组标题和摘要；模型不得改写原检查结果，也不得自行将组判定为可统一处理。所有合并支持撤销、追踪来源和人工确认。

### 5.2 三种不同的“相似”

1. **同类展示**：可放同一个列表；不保证处理方式相同。
2. **相同处理建议**：可共用文案或推荐操作；仍需要逐案核验。
3. **允许批量执行**：按案卷和规则条件逐一重新校验后，可以在一次用户操作下调用多笔合法事务。

问题组是**视图**，不是替代性的业务决定，也不能借聚类消除未处理检查或补件。若一案有多个问题，可能出现在多个问题组中，统计必须按不同案卷去重。

### 5.3 集中处置契约

人工打开问题组后能看到：影响案卷数、各案对应检查、材料与规则定位、差异和例外、建议补件要素、已处理/待处理数。可选择处理范围、排除个别案卷、预览动作后逐案提交。提交结果分别记录成功、冲突、失败和跳过；部分失败不得宣称全组成功。

同一问题组的“确认一个规则”不是对所有案卷做统一事实认定。处理前需逐案确认适用对象、必要材料、当前修订号和事项级差异。缺乏根据的组只能用于浏览，不能一键批量审批。

## 6. 队列、恢复与审计

- 批次逐案独立处理，坏案不阻塞其他案。默认小并发或串行，未来可配置并发、速率与预算。
- 队列启动、重试、暂停、恢复与取消都需要明确 API 和 UI；重启后修复遗留的 `running`，不得永久卡住。
- 任务执行完成后进行分流，不因 `run.status='completed'` 写入通过业务决定。
- 失败重试有上限、错误原因和告警；输入变化使用新运行，旧 `runId` 不复用作当前审批凭证。
- 动作落库使用稳定的 action ID、审计主体、事务幂等、版本 CAS 和必要的外部回执。技术错误与业务问题分别统计。
- 人工复核、模板发布及普通 Agent 均使用已有权限模型；任何手写 `actorSource='school'` 或假冒人工确认不可作为权限来源。

## 7. 页面呈现与操作次序

保留当前 `BatchPanel` 的四卡片 + 列表骨架，但从“进度看板”演化为“异常处理台”：

1. 首屏展示**待执行/进行中、自动通过（真实已写业务决定）、待退回/已退回、待人工、技术异常**，运行完成数可另列但不称为通过。
2. 批次名称、固定模板/政策和自动化策略常驻页头；提供开始、停止、重试失败、刷新（按当前能力分阶段交付）。
3. 以相似问题组优先展示未解决的问题，显示影响案卷数量与典型原因；点击进入原有单案证据页面。
4. 保留逐案表格：案卷、申报人、运行进度、审核问题、分流类别、**真实业务决定**、更新时间。
5. 有效运行与审批归属分开展示，避免“已完成”造成误导；聚类只折叠问题，不隐藏未审核材料和证据。
6. 批量操作提交前展示数量和排除项，必须确认真实生效范围。

## 8. 与现有实现的连接和分期

本文定义产品行为和实施边界。**当前代码完成切片 A/B，并实现了受授权且严格门控的切片 C；准确代码基线、组件/服务映射和验证记录见[开发者交接](17-current-state-and-handoff.md)。** 当前分支的 `BatchPanel.tsx` 已接入队列、状态分流、相似问题组、人工处置和自动化策略入口；服务端重新校验后调用既有 V2 业务事务，并持久化幂等回执。C 阶段允许本地审核员逐批授权自动补件/自动通过，但全局和模板开关、材料读取、规则覆盖、证据、业务阶段等门槛均必须满足；它不是校方身份或远端审批接入。`ReviewRunV2` 检查、覆盖、意见与输入哈希，以及 `workspace-business-service-v2.ts` 和 `decision-readiness-v2.ts` 的正式业务门槛仍是权威边界。

按小切片分期：

- **切片 A（已实现）**：纯分流与保守聚类（只读，不改业务结论）；批次页启动队列、展示检查进度、分流和问题组，技术错误与人工问题分离。
- **切片 B（已实现）**：队列恢复/定向重试及逐案批次处置；动作经既有事务门控，并对选择范围和输入版本重新校验，提供幂等回执与部分失败结果。
- **切片 C（受限实现，手动 UI 验收待完成）**：按批次策略执行需审核员逐批授权的自动补件/自动通过；满足补件后重新入队、逐案回执及审核完成后的批次定稿。具体门槛见 [C 阶段验收](17-batch-review-stage-c-local-acceptance.md)。当前不支持自动最终驳回、跨案推断或替代校方身份签署。
- **扩展**：必要时接入可选的跨案检查器；仅在模板明确要求且得到可靠数据支持后，进入自动通过阻断条件。

这些切片共享当前审核结果与业务服务，不创建第二套审核推理引擎。

## 9. 测试与验收

最少覆盖：

- 全部符合且所有门槛满足的案卷；“模型说通过、材料却没读”必须被阻断。
- `run.status=completed` 却没有有效检查、检查缺结果、证据未读、运行旧版本等，**绝不能显示成已通过**。
- 可补正材料缺项、明确不可补正的资格错误、规则歧义、`awaiting-confirmation` 和 `not-executed` 的不同分流。
- 同一 `ruleId` 但不同原因不能盲目合并；不同措辞的同一类问题可生成建议归组而不自动执行相同决定。
- 一个案卷多条异常不重复统计为多个案卷；问题组成员保留全部原始检查/出处。
- 一个案卷失败不影响后续案卷；技术异常不误列业务违规；重试和中断恢复不重复写正式决定。
- 批次模板版本与运行实际版本不一致、更新输入后旧运行、权限撤销和并发修改都必须挡住自动动作。
- 补件回流正确触发重新审核；已定稿结果只能产生新轮次，不可原地覆盖。
- 没有权限或仅有候选建议时 UI 不得显示“已自动通过/已退回”。

**本文件定稿的是产品行为与工程边界。测试未覆盖的自动批准能力不能因为页面存在开关而默认启用。**
