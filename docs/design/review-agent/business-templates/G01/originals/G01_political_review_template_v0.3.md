# 政审材料程序审核｜完整模板需求与规则测试稿 v0.3

> **文档类型**：纯 Markdown；供模板设计、编辑器通用模块抽取、审核规则定稿和后续实现映射使用。  
> **唯一标准中文名称**：政审材料程序审核。  
> **内部稳定标识（建议）**：`g01-political-material-procedure`；仅技术标识，不显示为另一个模板。  
> **版本状态**：`draft / v0.3`，未正式发布；不是成都理工大学已批准的现行校规配置，不是行政裁决，不是生产系统端到端通过证明。  
> **基线**：G01 第一阶段调研、第二阶段 59 字段 / 22 条条件分支、v0.1—v0.2 测试稿、27 组合成案例与端到端模拟审计；2026-10-10 核对部分高校公开页面。  
> **原则**：两层调研、一套模板目录、按校配置规则；成都理工大学业务优先，外校的完整正式业务资料可支持先行通用建模；校别差异不可冒充本校现行要求。

## 0. 阅读与建模约定

### 0.1 本文出现的标记

| 标记 | 含义 | 编辑器/执行器建议 |
|---|---|---|
| **[通用]** | 跨校、跨情形都成立的流程原则或客观证据关系 | 放模板定义或共享能力模块 |
| **[校规]** | 由具体学校、学院、业务、年度及生效通知决定的要求 | 放可版本化的学校规则配置，不能写死在模板本体 |
| **[条件]** | 只有表达式成立时才生效的字段、槽位或规则 | 可视化分支条件组；unknown 不得当作 false |
| **[人工]** | 法律/学校授权、真实组织意见、印章真实性、敏感材料实质判断 | 生成有权责任人的待办，不作自动审批 |
| **[接口]** | 从可信校务、招生、档案、收件、签章或人员系统取得的事实 | 需服务端信任标识，不能由上传文书自证 |
| **[来源待核]** | 有业务存在或历史依据，但完整最新原件、字段或适用范围未确认 | 允许提问、转人工、留空；**不可生成刚性缺件/拒件规则** |
| **[测试模拟]** | 为离线验证而编造的规则、组织、人物或数据 | 仅测试沙盒；禁止进入真实学校策略 |

本模板的规则编号与模块编号仅供编辑器、测试和审计追踪；**不会产生更多用户可选模板**。全文中“形式通过”都不是“政审合格”，也不是录取、任用、调档或用印批准。

### 0.2 一个经常被忽略的结构差异

- **模板**：确定审核目的、共用材料概念、可复用检查方法、允许的输出范围。
- **条件分支**：由事实和校规匹配激活一部分字段、材料槽、规则和阶段，不新增模板。
- **学校规则配置**：确定哪所学校哪一批次接受何种表单、机关、签章及递交方式，并关联正式依据的原文与版本。
- **运行案卷**：保存具体办理目的、可信服务端受理身份、申请人提交文件、解析结果、补正记录和人工决定。
- **评测数据**：案例与独立预期答案；不得作为受审材料或正式规则加载。

## 1. 模板目的、价值、边界

### 1.1 申请人想办成什么

用户因升学、就业招聘或获正式授权的组织人事业务，需要**准备、申请出具或提交**政审表、思想政治素质和品德考核表、政审说明函等材料，希望提前知道文件格式、身份对应、受理机关、组织签署手续和递交环节是否符合**相应接收/出具单位的正式要求**。

### 1.2 模板真正审核的对象

**政审材料及其办理程序**，包括：

1. 本案实际适用的制度、学校、学院、用途、年度、材料阶段和表单版本；
2. 材料与申请人/考生/教职工的**客观身份关联**；
3. 当届规则要求的栏目、文书附件、组织意见栏的**存在性和签署状态**；
4. 出具单位是否属于当前接收方认可的单位类型，以及出具方是否具备本单位的正式签署权限；
5. 签字、公章、日期、原件、可验电子签章、密封、寄送或系统上传等**条件性程序**；
6. 已发起但尚未形成正式组织签署的申请，能否合规流转到下一有权节点。

### 1.3 不属于本模板（必须早分流）

- **不**分析、生成、重写、评价或打分个人政治倾向、党派立场、宗教信仰、思想品德、师德优劣；不作政审合格/不合格的实质决定。
- **不**代替党组织、学院、工作单位、人事部门、招生单位作意见、推荐、录用、录取决定。
- **不**自动批准查阅人事档案原卷、档案转递或函调取证权限；这些需其他业务及正式权限。
- **不**把复试报名整包的身份证、准考证、诚信复试承诺书全部复制为“政审子模板必交附件”；只在有合法关联的情况下调用已经授权的客观字段。
- **不**泛化成所有校内公章、科研合同、社会调查、刑事审查或企业背景调查的审核工具。
- **不**将某校某年的特殊形式（必须纸章、单位密封、工作单位和档案保管单位双份意见）写成所有学校的统一义务。

### 1.4 独立必要性

与「专项证明与用印审核」相比，本模板有**接收方当年政审表要求、被鉴定人与出具机构间的职责、组织意见及授权范围**等专门关系；与「档案利用申请审核」相比，本模板处理政审文件的程序合规，不授予档案阅览权限。因此保留为一套独立模板。

## 2. 审核对象、角色与责任

| 角色概念 | 行为与可审内容 | 不能替代的责任 | 对编辑器的意义 |
|---|---|---|---|
| 申请人/被鉴定人 | 申报事项、填写本人客观信息、提供申请材料 | 不得自签正式组织意见，不得指定系统校规 | 允许“申请主体”与“被鉴定人”分离，通常为同一人 |
| 代办人（条件） | 受学校允许时协助递交、补正 | 不因持有证件而获组织签章权 | 条件化的第二自然人关系 |
| 出具单位/原所在单位 | 在授权范围内核实事实、形成组织意见、履行签署 | 不得对无权覆盖时期或他人记录虚构结论 | 单位、经办人、有效期和权限四维核验 |
| 接收单位 | 发布当届接收清单和表格格式、核收件及处理 | 不能凭接受某格式自动授予出具方签章权 | 接收规则与出具规则分别加载 |
| 审核经办人 | 核对缺项、证据、授权请求、异常事项 | 不能把机器形式检查当最终审批 | 人工待办、签收/复核、回退补正 |
| 模板/校规管理员 | 发布、撤回、修订有效规则版本 | 不能在运行时由申请材料动态创建“正式政策” | 规则发布者与申请人权限隔离 |
| AI/规则执行器 | 抽取可核字段、对比差异、提示缺件、定位页码、生成程序性建议 | 不作政治思想鉴定、印章真伪断言和任何实体批准 | 三类规则执行：确定性、语义、人工 |

**允许同一模板服务不同办理方向，但不能把接收端的完成品要求施加到出具端起始材料上。**

## 4. 三层配置与信任边界

### 4.1 模板定义层（跨校不变）

- 只定义本模板目标、分项、可用字段类型、抽取方法、材料槽、通用证据规则、禁止的实质性结论、状态机和输出结构。
- **不**写死“所有政审表必须纸质红章”“所有往届无工作者必须街道盖章”“所有学校都有固定截止日”。
- 不预设评分表、加减分、政治/品德等级或AI自动通过。建议 `autoPassPolicy.enabled = false`。

### 4.2 学校／院系／年度规则配置层（可审计，可冻结）

每个规则包至少记载：

| 字段 | 说明 | 不可省略原因 |
|---|---|---|
| `policy_id`、`policy_version`、`content_hash` | 正式规则唯一版本身份 | 防止规则热更新造成同一案卷前后适用不同制度 |
| `issuing_authority` | 发文单位（学校、学院、招生办、人事部等） | 判断其是否有权规定这一审核事项 |
| `source_title`、`source_url` 或归档原文 | 来源及可追溯证据 | 不能用模型生成的总结作为唯一规则依据 |
| `published_at`、`effective_from/until` | 发布与生效时间 | 不按当前日期错误选择招生年度 |
| `recipient_school`、`recipient_unit` | 接收单位/二级学院的精确范围 | 不能跨院、跨校硬继承 |
| `issue_organization`、`issue_authority_scope` | 出具方的组织权限 | 不能把“被接收”理解为“有权出具” |
| `business_matter`、`cohort_year`、`stage` | 事项、招生/招聘届别、办理阶段 | 2026与2027及复试、拟录取、入职可能不同 |
| `accepted_forms`、`alternatives` | 官方表和正式认可替代件 | 防止“非制式”但被官方认可的函件被误拒 |
| `required_fields_by_stage` | 哪个阶段哪个栏目要求齐备 | 解决出具初始阶段空白意见栏问题 |
| `accepted_issuers_by_applicant_state` | 应届/往届/就业状态的机构资格 | 不能跨校认定单位章的有效性 |
| `delivery_policy` | PDF、纸件、实体章、验签、密封、邮寄方式、截止日、延期 | 条件性材料判断的关键 |
| `source_quality`、`confirmation` | 官方已确认/仅有外校实例/待核/冲突 | 未确认规则不能驱动自动否决 |
| `published_by`、`approved_by` | 谁编辑、谁发布、谁有权批准 | 申请人不能自行发布适用规则 |

**选择权归属**：服务端已授权受理入口、业务路由和管理员发布的规则决定最终适用 `policy_id`。申请人可以声明目标学校、年份与材料用途，但该声明仅用于检索/核对；它**不能指定或替换服务端规则包**。若受理权威上下文不存在，则只可提示“待匹配/人工确认”，不能任意选择更宽松规则。

### 4.3 运行案卷层（每次独立）

每个案卷至少绑定：`case_id`、`template_id/version`、可信接收单位ID、受理业务ID、方向、阶段、招录年度与批次、申请人客观标识、材料版本/hash、激活规则包ID/hash、文档读取覆盖、逐规则结果与引用、补正历史、最终人工责任人。输入和审核输出都不能覆盖原始文件；再次提交要产生新版本并使涉及的旧审核失效。

### 4.4 证据可信度（分层而非强行判真）

1. 管理员发布且经过确认的正式制度/办事通知（仅在适用范围内有规则效力）。
2. 经正式身份认证的校内学籍/招生/人事/组织/电子签章/收件服务所返回的**事实状态**。
3. 经申请人上传的官方表格、函件、证件扫描件：可以抽取和相互比对，但不因看见章图形就证明“真章”。
4. 用户自然语言说明和非官方教程：可作线索或补问依据，不能生成强制要求。
5. 测试合成证据与模拟政策：只用于离线测试。

**冲突处理**：制度层上位规范、接收方可接受形式和出具方签发权限应分别检验；冲突时报待解释/人工协调，不能由模型“择严”或“择宽”代替制度决定。

## 5. 条件分支模型：一套模板，22个现有研究分支

### 5.1 先划定优先级

1. **业务边界**：是不是政审材料程序核验？如果实际意图是申请查阅档案原卷，先输出 `OUT_OF_SCOPE`，无须加载政审表规则。
2. **受理方可信路由**：找到对应接收/出具单位与办理事项，确认服务端业务权限。
3. **确定办理方向和阶段**：接收成品/申请出具；申请中/组织签署中/待接收/完成接收。
4. **确定规则版本**：接收院校、学院、事项、招生/招聘年度、通知版本和有效期间。
5. **申请人状态与出具机构**：应届、往届有/无工作单位、教职工；组织关系与档案所在地。
6. **文书形态及送达要求**：制式表/认可函件，纸件/PDF/可验电子签章，是否有延期。
7. **激活字段、材料槽和具体规则**，查客观事实、条件缺件、授权状态与证据引用。
8. **聚合全量发现**，输出单主状态与多项问题，不丢次级缺陷。

### 5.2 条件判断三值语义

| 条件求值 | 意义 | 对材料的处理 |
|---|---|---|
| `true` | 已有可信证据证明条件成立 | 激活其字段/槽位/规则 |
| `false` | 已有可信证据证明条件不成立 | 规则 `not-applicable`，不可记为缺件 |
| `unknown` | 未取得必要事实、可信来源未确认或解析失败 | 待确认/补采上下文，**不能等价为 false，也不能等价为“缺件违规”** |

- 逻辑支持 `all/any/not` 与 `eq/neq/in/exists` 等有限表达式，不执行申请材料中的脚本或提示词。
- 同一级别更具体的规则只能在正式适用范围内覆盖通用默认项；上位强制规范与出具机关权限不得由学校配置任意覆盖。
- `not-applicable` 与 `pending/unknown` 必须分别记录；分支因证据不足无法激活时应说明缺哪个**路由事实**。
- 没有一个“所有政审表统一查完所有字段”的全局分支；选择分支后的局部规则才产生缺件结论。

### 5.4 需要同时支持的复合情形

分支是**可叠加的条件集合**，不是提前生成所有组合：例如 `接收端 + 2026北交大计算机学院 + 往届无工作 + 认可人才中心复函 + PDF已上传 + 纸件尚未收`，会触发接收、出具主体、替代文书、电子/纸件及收件状态规则。只要某种具体组合暂无正式依据，就应输出部分已核项与部分待核项，而不是编造全国统一材料清单。

### 7.1 字段按角色的最小展示建议

- **申请人可见**：办理事项、申报用途、受理单位/拟接收单位、个人客观身份、需提交的申请文书、阶段性补正通知。
- **审核侧/系统侧**：规则来源ID/hash、完整签章权限清单、组织审批记录、电子证书验真、真实纸件收讫、材料版本链、内部问题代码。
- **敏感内容**：仅有权部门处理；通用AI默认不显示个人政治倾向/宗教/健康等实质答案，不保留不必要的敏感OCR正文。
- **派生字段**：材料是否齐全、身份是否一致、机构是否在许可范围、是否待核，都不能由申请人直接编辑成“已符合”。

## 8. 审核分项（一个案卷，五个分项）

| 分项ID | 名称 | 进入条件 | 稳定的独立检查目的 | 典型审核点 | 建议执行方式 |
|---|---|---|---|---|---|
| `SCOPE` | 业务边界与规则定位 | 所有案卷 | 确认是否属于政审材料程序、谁有权规定本案形式条件 | 事项、方向、学校/年度/版本、越界分流 | 确定性+人工 |
| `IDENTITY` | 申请人与客观记录 | 需要比对当事人时 | 材料确属同一被鉴定人/业务批次 | 姓名、编号、经历客观时间 | 确定性+语义 |
| `FORM` | 文书版本与栏目 | 表/认可函件已提交时 | 指定表或被认可替代件的形式完整性 | 表版本、缺页、栏目存在性 | 语义+确定性 |
| `AUTH` | 出具单位、签署与权限 | 出具/接收端需审签时 | 签署流程与正式机构权限匹配 | 出具主体类型、经办签字、单位章、日期、权限 | 系统事实+人工 |
| `DELIVERY` | 递交、收讫与补正 | 接收方规定交付方式时 | 纸件、PDF、电子文书、密封及收件状态 | 电子上传、原件签收、指定渠道、延期 | 确定性+人工 |

审核分项是**同一个模板中的逻辑分组**；除越界外，不因为其中一个分项严重异常就省略其余已具备证据的检查。这也意味着报告可以有多个问题，而不仅一个“合格/不合格”。

## 9. 规则条款：可实施的检查单元（建议稳定编号）

> 每条规则的判定都依赖“触发条件 + 当前已确认校规 + 正确材料/字段来源 + 处理异常”。`D`=可由确定性验证，`S`=文件语义识别/人工确认，`H`=须有权人；某些规则跨多种执行方式。下面列的是**业务规则逻辑**，不是声称现有执行器全部已实现。

| 规则ID | 审核要求及生效条件 | 审核动作和可接受替代 | 无法满足或证据不明时 | 证据属性/责任 |
|---|---|---|---|---|
| R001 | **业务边界优先**：实际目的为政审材料程序核验 | 启用本模板；若请求档案原卷权限则先分流 | `OUT_OF_SCOPE`，禁止用错模板规则 | 通用/D |
| R002 | **可信规则路由**：必须有服务端受理事项与学校/年度匹配依据 | 由已发布政策源选择适用校规及hash，申请人声明仅核对 | 无可信映射→`FORM_VERSION_UNKNOWN`；申请人自选policy无效 | 通用/D/管理员 |
| R003 | **办理方向**：`receive` 或 `issue` | 分别启用成品收验或出具申请核验 | 方向冲突或未知→待核，不自动拒绝 | 通用/D |
| R004 | **阶段识别**：申请、组织签署、待收件、已收件 | 用受控工作流状态决定何时要求最终签署/交付 | 阶段未知→人工确认，不能把出具申请当成成品 | 通用/D |
| R005 | **当年规则有效**：接收单位、业务、届别、通知版本同时匹配 | 允许经确认的官方补充通知延期或调整材料 | 不明版本→`FORM_VERSION_UNKNOWN`；已知上传旧表→可提示`FORM_VERSION_MISMATCH` | 校规/D |
| R006 | **指定或替代文书**：当前通知规定格式 | 先检查指定表；若有明确认可的统一复函，按替代分支核验 | 无正式依据不能拒绝替代件；有依据且不满足时补正 | 校规/S |
| R007 | **材料页与版本**：拿到官方原件且规定制式表 | 比较页数、版式识别信息和适用年届；缺页时定位页 | DOCX/模板没核实→来源待核，不能自拟栏目 | 校规/S |
| R008 | **身份客观比对**：有申请人可信主数据和表格事实 | 姓名、报名号/校内ID与文书对应；姓名变更允许法定关联核实 | 已证实冲突→`OBJECTIVE_CONFLICT`；仅OCR不清→待核 | 通用/D+S |
| R009 | **唯一编号对应**：申请/表/报名或系统证明有同一编号 | 去空格标准化后精确匹配，同音姓名不能替代ID | 真实多来源编号冲突→`OBJECTIVE_CONFLICT`，不给造假判断 | 通用/D |
| R010 | **申请人状态**：应届/往届有工作/往届无工作/教工 | 根据已确认事实选择合适的出具机构候选 | 状态不明→补取可信事实；不得凭印章逆推身份 | 校规+D |
| R011 | **出具机构被接收**：仅在接收方明示出具单位范围时 | 核机构类型与通知匹配，允许官方认可的档案单位/统一复函 | 单位类型未获证实→`ISSUER_UNKNOWN`，不是伪造结论 | 校规/H |
| R012 | **出具方自身有权**：进入签署流程 | 核组织部门、任职期间、校内/人事签署权限与当前流程 | 权限待核→人工授权工单；接收方认可≠出具方有权 | 通用/H+接口 |
| R013 | **本人部分完整**：正式表要求哪些申请人填哪些栏 | 逐指定栏目查有无、字段关联，接收方内部复核栏不强制本人填写 | 仅空白指定栏补正，不分析敏感内容 | 校规/S |
| R014 | **组织意见存在**：`receive` 且必须交已签发文书 | 检查意见区域有无签署后的文字，不评价内容优劣 | 真实缺栏→`MISSING_CONDITIONAL`；`issue`阶段不触发 | 校规/S/H |
| R015 | **经办人/负责人签署**：相应通知要求 | 检查签署是否存在，手签/签字章是否符合正式形式 | 缺签署→补正；图片不能证明签署人真实身份 | 校规/S/H |
| R016 | **印章存在与主体对应**：相应通知要求 | 看章图是否出现、字面单位是否合理；有可信签章接口时验真 | 缺章→补正；看到章但无接口→真实性未验证 | 校规/S/H |
| R017 | **签署日期**：适用表格要求且已签发 | 检查签署日期是否存在、格式和明显时间矛盾 | 缺日期→`MISSING_CONDITIONAL`；出具起始不查 | 校规/D+S |
| R018 | **多单位分段鉴定**：接收方明确要求且经历触发 | 核每个有权单位覆盖的期间，允许官方分段替代形式 | 缺某段→条件补正/人工；不得全国推广 | 校规/H |
| R019 | **单位与经历对应**：出具单位对被鉴定人应有正式关系 | 核单位/学籍或工作期间在其知情权限内 | 无法证明期间→人工；不生成实质评价 | 通用/H |
| R020 | **纸质原件要求**：当期必须交纸件 | 将扫描PDF、快递单、收发室签收、受理人登记视为不同证据 | 未签收但未到最终时点→`PENDING_DELIVERY`；过期按适用规则处理 | 校规/接口 |

| R022 | **递交渠道**：通知规定本人/EMS/单位专送等 | 核寄送方式、是否例外允许、物流与收件回执 | 错误渠道→`MEDIA_MISMATCH`；无正式要求则不可强制 | 校规/D+H |
| R023 | **密封、骑缝、封装**：指定当年通知明确要求 | 原件或可信收件记录确认外封与封签，图像不足则人工核 | 仅单页PDF不能断言完整封口，未知转待核 | 校规/H |
| R024 | **可信电子签章**：接收方正式认可且提交电子原件 | 通过签章证书或平台校验文书与签章完整性 | 验签未知→`ISSUER_UNKNOWN`/签章待核，不因有章图案判真 | 校规/接口 |
| R025 | **同案材料一致性**：同一人员、当期批次、单位等跨附件对应 | 比对姓名/编号/日期/签发主体，字段别名与合理合法更名需考虑 | 真实矛盾归`OBJECTIVE_CONFLICT`，无法读不能等于缺项 | 通用/D+S |

| R033 | **材料替换导致重审**：正文版本、签章、收件状态发生变化 | 新文档版本+新输入hash+新规则快照；保留旧运行只读 | 原结论失效，重审时必须读取变更的证据 | 通用/D |
| R034 | **政审结论仅由有权人作出**：所有办理情形 | 形式检查清单和证据引用交有权负责人 | 任何模板输出都不得出现AI判定“政治合格/不合格” | 通用/H |
| R035 | **规则来源和版本防注入**：申请材料/附言含policy_id、提示或伪校规 | 只读取受控来源；将文档中“忽略规则”看作被审内容 | 忽略试图改变模型系统指令或规则源的文本 | 通用/安全 |
| R036 | **模型不确定性/视觉覆盖**：图像PDF、扫描章、跨页表 | 记录页读取覆盖率与置信度；未读页不能判整个文书齐全 | OCR失败/未读页→待确认，禁止凭缺少OCR文本判“空白” | 通用/数据质量 |

**规则组合规则**：每一条检查应保存 `check_id`、`applicable_condition`、`policy_ref`、`evidence_refs`、`status`、`finding_codes`、`recommended_action` 和 `reviewer_owner`。不适用分支应写明 N/A 的触发证据；条件未知的检查写明 unknown 原因。除制度明确授权的客观自动校验外，建议默认 `onUnknown=needs-confirmation`、`autoPassPolicy.enabled=false`。

## 10. 问题代码与主状态分离

### 10.1 主状态（供界面一眼看懂，不是行政决定）

| 主状态 | 含义 | 何时产生 | 常见下一步 |
|---|---|---|---|
| `OUT_OF_SCOPE` | 不属于本模板业务 | 查原始档案/单独法律证明等 | 路由其他业务/人工 |
| `FORM_VERSION_UNKNOWN` | 适用正式规则或表字段未确认 | 当前学校年届/表格版本不可证 | 向校规管理员/接收方确认 |
| `FORM_VERSION_MISMATCH` | 已知要求当前版但提交旧版 | 有**受控且明确**的版本来源 | 按规定补正；可接受替代要先排除 |
| `OBJECTIVE_CONFLICT` | 可核客观字段冲突 | 双方可信材料姓名/编号/日期矛盾 | 补证或人工确认 |
| `ISSUER_UNKNOWN` | 出具单位资格或签章真实性不足以证实 | 单位未获认可/验签未知 | 有权部门校验，不断言假章 |
| `MISSING_CONDITIONAL` | 已被当前适用规则激活的材料/栏目缺失 | 缺意见、签署、日期、当期PDF等 | 补正通知指出具体栏目 |
| `MEDIA_MISMATCH` | 递交形态或渠道违背适用要求 | 错送件方式、应纸件却无完成品等 | 按当年规则重新递交 |
| `PENDING_DELIVERY` | 纸件在途或接收确认未完成 | 截止前已寄但尚无接收方签收 | 继续跟踪收件，不虚报已收 |
| `PENDING_ORG_SIGN` | 正常处于组织签署流程 | 出具方向且尚未完成签署 | 转有权组织办理 |
| `FORM_OK_PENDING_AUTH` | 已验证的材料程序条件形式齐备 | 当前可检查项均无问题 | 提请有权部门决定，绝非政审合格 |

> 此表是在 v0.2 参考执行器状态上补齐交付媒介语义；第二阶段旧的 `ROUTED` 是**中间路由事件**，不是最终主状态。`SENSITIVE_RESTRICTED` 是**访问控制/转人工标记**，不与“材料形式是否齐备”互斥。现有系统 `compliant` 等检查状态与上述主状态属不同层级，不能强行一一映射。

### 10.2 重要问题代码

| 代码 | 原因 | 成立前提 |
|---|---|---|
| `NO_OPINION` | 必须有组织意见而没有 | 接收已签成品+当期明确要求 |
| `NO_HANDLER_SIGNATURE` | 缺经办签名/签字章 | 接收当期明确要求 |
| `NO_PHYSICAL_SEAL` | 缺规定的实体公章 | 当前规则必须实体章，且已到成品接收 |
| `NO_SIGN_DATE` | 缺正式签署日期 | 当前接收方指定日期 |
| `NAME_MISMATCH` / `ID_MISMATCH` | 客观身份冲突 | 两份可靠材料存在不可解释差异 |
| `OLD_FORM_VERSION` | 来件使用不认可的旧版 | 有官方当届版本和排除替代的依据 |
| `ISSUER_NOT_IN_ACCEPTED_LIST` | 签发机构不在当期接受范围 | 已确认接收方机构列表或明确排除 |
| `E_SIGNATURE_UNVERIFIED` | 电子签章尚未可信验签 | 接收方正式允许电子章且校验接口未通过/不可用 |
| `ORIGINAL_NOT_YET_RECEIVED` | 规定纸本原件尚未收妥 | 可证仍在途或未登记收件 |
| `PAPER_ORIGINAL_NOT_RECEIVED` | 到规定收件阶段仍无有效纸本收件 | 需纸质原件，且受理时间/补期确定 |
| `NO_SCAN_PDF` | 要求先行上传PDF而未上传 | 适用学校明确要求 |
| `DELIVERY_CHANNEL_NOT_ACCEPTED` | 递送方式不在许可范围 | 正式收件渠道可证 |
| `ISSUE_REQUEST_MISSING` | 出具申请前置手续未成立 | 有正式申请/OA要求，并非缺已签成品 |
| `ARCHIVE_ACCESS_SEPARATE` | 实际申请需要档案访问权 | 属独立查档业务 |
| `CDUT_FORM_FIELDS_UNVERIFIED` | 成都理工表名已知但字段全文未核实 | 不能由外校表格自动推定本校栏位 |
| `NO_2027_SCHOOL_POLICY` | 相应校方2027校本细则未确认 | 不直接套2026同校政策 |

**聚合原则**：输出 `primary_status` 仅一个，`findings[]` 可任意多条；每一条都必须有材料版本/页/块或可信系统事实依据。主状态优先序仅用于展示和业务排队，不能删除其他有效问题，也不能把“不确定”和“不符合”混同。


### 10.3 主状态的明确聚合算法（规范性草案）

1. 先检查 `OUT_OF_SCOPE`；越界后终止本模板的实质规则执行，但记录必要的业务分流原因。
2. 在本模板范围内，**逐条执行所有能依据适用且已确认政策启动的检查**；即使已经查到旧表或身份冲突，也不提前退出，确保其他独立错误仍能发现。
3. 为每条问题保留所属规则ID、文档来源与触发条件；没有明确适用依据的“疑似缺项”标为待核，不可写 `MISSING_CONDITIONAL`。
4. 先检查是否存在**足以阻断确定性主状态的规则来源缺口**，有则主状态 `FORM_VERSION_UNKNOWN`，但在 `findings[]` 中仍保留有充分依据的客观冲突等次级发现。
5. 若规则足够明确且已知文书版本不被接受，主状态 `FORM_VERSION_MISMATCH`；否则依次考虑 `OBJECTIVE_CONFLICT`、`ISSUER_UNKNOWN`、`MISSING_CONDITIONAL`、`MEDIA_MISMATCH`、`PENDING_DELIVERY`、`PENDING_ORG_SIGN`。
6. 只有**所有当前阶段必检项均有可核验结果，且不存在阻断性规则、解析、授权、版本与收件缺口**时，才允许得到 `FORM_OK_PENDING_AUTH`。全部检查都未执行或者文档未读完，绝对不能把“未发现问题”当作形式通过。
7. 上述先后次序是**离线案卷展示与测试兼容性规则**；实际接收单位可能另有紧急程度、办理期限排序，不可改变单项规则的事实判断，不可吞掉完整异常列表。

例：**已证实为旧版表 + 缺组织意见 + 缺签署日期**，主状态取 `FORM_VERSION_MISMATCH`，同时输出三条独立发现；**收件规则未知 + 姓名有可靠冲突**，主状态可为 `FORM_VERSION_UNKNOWN`，但仍报告姓名冲突并注明未套用未知收件规则；**出具申请待签署且未提交任何要求的申请书**，应报缺申请前置材料，而不是缺“已盖章政审表”。

## 11. 单条检查结果的数据契约（供编辑器设计）

| 属性 | 意义 | 示例或取值 | 可否由用户自行填写 |
|---|---|---|---|
| `rule_id` | 模板规则稳定标识 | `R017` | 否 |
| `policy_ref` | 适用规则版本、源文书位置/hash | `BJTU-CS-2026` + 引用段落 | 否，管理员维护 |
| `applicable` | `true / false / unknown` | 有无激活组织签章条件 | 否 |
| `check_status` | 单检查项结论 | `compliant/non-compliant/awaiting-supplement/awaiting-confirmation/not-applicable` | 否 |
| `reason` | 事实和程序理由 | “本批次要求经办签字，所读页未见” | 否；人工可修正并留痕 |
| `evidence_refs` | 文档ID/版本ID/页或块ID/摘录 | 当前扫描政审表第2页 | 否，由解析与人工核验产生 |
| `confidence` | 解析/定位可靠度（非政治评价置信度） | 高/低/无法读取 | 否 |
| `finding_codes` | 多项问题明细 | `[NO_OPINION, NO_SIGN_DATE]` | 否 |
| `action` | 补正/等待/管理员确认/转人工/无需行动 | `supplement/confirm/manual-review` | 审核人员可确认 |
| `owner_role` | 下一责任角色 | 申请人/规则管理员/学校有权部门/收件人 | 管理员配置 |
| `rule_hash`、`document_hash` | 复审完整性 | 运行时版本快照 | 否 |

### 11.1 证据的最小粒度

- PDF/扫描图像：至少能追溯文档版本 + 页码，能定位时另存框选区域；如果只得到文件级引用，要明确“文件级，未精确定位”。
- DOCX/文本：段落或可验证文本块；表单字段最好记录字段名/区域。
- 系统事实：服务名称、受控记录标识、读取时间和返回状态；不能伪造用户无法查询的“系统验真成功”。
- 多文件冲突：必须分别引用**双方**而不是只贴出一种材料。
- 签章：`seal_visual_present` 与 `seal_authentic_verified` 是两个不同字段；允许前者真、后者未知。

### 11.2 无证据硬拦截

`non-compliant` 和 `awaiting-supplement` 不能只根据 LLM 概述给出；必须指出可适用的规则来源、明确触发事实、缺失或冲突的材料证据。如果某页未读取或视觉检测失败，先记 `awaiting-confirmation`，不能把缺OCR文字当作证件未提交。

## 12. 审核阶段与补正/签收闭环

| 阶段ID | 阶段名称 | 输入前提 | 自动可做 | 必须人工/接口确认 | 转出条件 |
|---|---|---|---|---|---|
| `S0` | 受理与业务分流 | 提交办理目的 | 识别范围、方向、身份 | 必要时确认单位和事项权限 | 业务属于本模板且可选择/待核规则 |
| `S1` | 正式规则绑定 | 可信受理身份和学校事项 | 规则适用范围/版本校验 | 校规冲突、版本缺口管理员确认 | 已确定规则或明确暂停硬性判定 |
| `S2` | 材料登记与解析 | 表单/附件/系统事实 | PDF/图片页解析、字段归档、覆盖记录 | 无法识读的页面须复核 | 阅读覆盖达到声明要求或标明缺口 |
| `S3` | 条件规则预审 | 活跃规则+证据 | 逐项核验、定位发现、主状态聚合 | 权限/签章真实性/敏感内容人工 | 可补正、等待或送有权复核 |
| `S4` | 出具组织签署（条件） | `issue`且前置申请合规 | 记录待签与流程状态 | 出具方有权人员出具意见和章 | 签署完成或人工退回 |
| `S5` | 电子/纸件递交与确认（条件） | `receive`或已出具成品 | PDF上传/收件状态对账 | 原件确已接收与渠道有效性 | 完成收件或等待/补交 |
| `S6` | 补正与重新审核（可回流） | 对应工单/补正原因 | 新版本登记、计算受影响规则、重跑检查 | 申请者提交补正；复核员确认是否满足 | 基于**新材料和新规则快照**完成重新审核 |
| `S7` | 有权部门程序复核/归档 | 形式清单与证据完整 | 出具程序审核报告、审计日志 | 有权部门最终处置 | 保留行政决定与AI意见的明显区分 |

**流转不变量**：

1. `S0`范围判断先于`S1`规则加载（防止“查档申请先匹配不到政审政策”）。
2. 出具申请阶段的空意见/空章正常；签署后才按正式要求验完成品。
3. `S5`的已上传、已寄出、收发室签收、学院登记签收是四个不同事实；不能串成一个布尔值。
4. 补正回应不是“补正满足”；只有新证据被审阅、缺陷解除后才能标满足。
5. 新文件版本、新规则版本、新系统签收事件或授权变更都使依赖它的旧结论需要重评；保留旧运行不可篡改。
6. 任一时点 AI 审核清单都不能自动写成学校正式签章或行政决策记录。

### 12.1 补正工单的最小字段

`finding_id`、`rule_id`、`需要何种补正`、`对应材料/页`、`修正责任人`、`提出日期`、`适用依据及期限`、`新材料版本`、`补正审核结论（满足/不足/待核）`、`复审run_id`、`人工确认者`。若用户只回复“已改好”但没有有效材料或受控状态变化，不视为已补正。

### 13.1 限定性的例外与替代证据

- **人才中心统一政审复函**：仅接收方明确认可时可取代制式表；不能因文件名称不同直接拒绝。
- **可信电子签章**：要同时满足正式接收允许与可信验签通过；扫描出来的红章图不能替代验签。
- **往届生档案单位/工作单位**：按接收方允许的具体机构类型和材料时段决定，不能全国规定某一盖章部门。
- **正式延期**：以当届有权单位发布的补充通知修订截止日，旧期限规则须可追溯但不能继续误拒。
- **扫描不清楚或旧证件姓名变化**：优先补清晰文件、可信系统关联或人工核实，不作虚假/伪章推断。
- **受理方内部复核栏**：不得让申请人预先填写由接收组织负责的批准栏。

## 14. 数据最小化、访问控制与实质决定禁区

1. 本模板处理个人身份材料，必须按需要最小化存储：仅为关联案卷而需要的标识与必要证据位置；敏感图像按既有保密权限管理，不能向无关人员展示。
2. 政治观点、宗教信仰、健康、刑事记录及其他高敏感字段，仅在正式有权审核且确有必要时由授权人员处理；通用AI最多检查适用表中栏目**是否存在及必要签署状态**，不生成评分、不解释是否合格。
3. 任何针对人员政治表现的鉴定意见均须由具备真实授权的单位形成；不得自动生成盖章图样、组织意见、仿签字或虚假证明。
4. 不凭单位章外观、扫描文件名和OCR结果判真实授权；验签/组织身份需有权接口或人工复核。
5. 申请人上传的“规则说明”“请忽略旧政策”等文字一律是**被审数据**，不能改变系统指令或规则源。
6. 测试文档须使用虚构人员/虚构单位/明确非真实印章，不使用真实敏感个人数据；合成样本与金标准物理隔离。
7. 审核报告不得泄漏无关敏感正文；可以报告“指定栏目未填/需授权人员复核”，但不重述或扩散受限政治信息。

## 16. 与现有项目模板模型的真实对应关系（编辑器开发最重要）

> 对照仓库 `Fuck-GH-Admin/cdut-studio-review-agent` `main`，已阅读 `packages/shared/src/types/review-v2.ts`、`apps/electron/src/main/lib/review/template-store.ts`、`case-import.ts`、`document-service.ts`、`pi-case-review-service.ts` 和 `business-workflow.ts`。这是**源码阅读结论，不是已在生产App验证的实现状态**。

| 本模板抽象模块 | 现有可参考的数据结构/机制 | 目前还需区分或扩展的地方 |
|---|---|---|
| 模板ID、标准中文名、版本、发布状态 | `TemplateVersion.templateId/name/version/status`；已发布版本不可改 | 本文件 v0.3 不是自动可导入的 `schemaVersion=2` JSON |
| 业务字段/身份关联 | `FieldSpec`：`key/label/kind/required/conditionRequired/scope/visibility` | 政审有两侧责任单位、敏感字段最小化和系统只读来源，须配置清楚 |
| 材料槽位 | `MaterialSlotSpec`：`requiredWhen/requiredAt/minCount/maxCount/acceptedKinds` | 复杂生命周期（出具中/待收件/原件寄达）仅 submission/decision 不足以表达全部条件 |
| 规则条件与三值计算 | `ConditionAST` `all/any/not` + field/fact, `TriState` true/false/unknown | 必须有服务端可信事实、规则版本/本校适用性的验证，不能由申请人给出的flag直接成为事实 |
| 规则定义与来源 | `RuleSpec.when/execution/onFail/onUnknown/confirmation/sourceRefIds` + `PolicyVersion` | `sourceRefIds`必须链接已存文书版本/位置，校本未知不能发布为已确认硬规则 |
| 审核分项 | `TemplateSectionSpec` 与 `TemplateCriterionSpec` | 本文 SCOPE/IDENTITY/FORM/AUTH/DELIVERY 五分项共享一案，不按情形拆模板 |
| 流程阶段 | `WorkflowStageSpec.kind/enterWhen/exitWhen/executorRole/nextStageId/returnToStageId` | 需更精细的受控收件事件、流程回流、官方组织签署，不应无依据映射为“自动批准” |
| 审核材料导入 | `case-import` 的 `rule/application/evidence` 文档角色与 `document-service` 的PDF/Office解析 | 业务槽位是更细的语义层，图像PDF要保留视觉页块与读取覆盖证据 |
| 审核结果/证据 | `PiReviewCheckInput.status` 五态；`SourceRef`有文档版本/解析版本和位置 | 本文十个主状态及多条finding是**展示与业务聚合层**，非直接等价于五态 |
| 人工决定与补正 | `business-workflow` 决定追加式，基于run，补正需重新核满足 | 需要确保补正新版本、规则变更、收件回执触发局部或全案重新审核 |
| 自动通过开关 | `TemplateVersion.autoPassPolicy` | **本业务建议关闭**，因为形式可合规≠组织意见已获有权部门作出 |
| 编辑器校验 | `validateTemplate()`查重复ID、悬空字段引用、流程循环、政策引用等 | 额外建议做“来源适用范围错误”“缺正式校本规则却自动否决”“敏感字段被配置语义评分”等静态检查 |

### 16.1 模板编辑器需要支持的最小可视化能力

1. **条件组**：像表单条件编辑器一样组装 `AND/OR/NOT` 与三值unknown；分支激活条件不能只能选布尔开关。
2. **规则版本选择器**：适用学校、部门、招生/招聘年度、阶段、有效日期；显示来源和hash，正式发布规则禁止由申请人覆盖。
3. **材料槽位+阶段条件**：同一政审表在`issue`阶段可空签章、在`receive`阶段必须按正式通知形成完成品；原件邮寄是另一个待办事件。
4. **字段编辑器**：类型、来源、可见性、抽取提示、是否系统优先、条件必需、合理替代、敏感数据访问限制。
5. **规则单元编辑器**：条件、取证点、对比方法、依据、异常状态、onUnknown、处理角色、可接受替代。
6. **流程图编辑器**：申请、签署、收件、补正、复审、人工决定及状态依赖；防死循环并保留合法回流。
7. **结果模型编辑器**：每项规则有独立状态和证据，案卷有一个主状态；可以同时存在多个异常。
8. **静态审计与回归链接**：规则来源缺失、跨校错误继承、无可核材料却设自动拒件、申请人可修改受控规则、敏感语义打分等要在发布时阻断或告警；规则变更关联受影响测试。

### 16.2 可复用“组件实例”的最小配置面

编辑器做模块抽取时，建议每个业务模块的一个**实例**都支持下面这些元属性，否则未来会把多个场景的判断条件写进自由文本中而无法执行。

| 属性类别 | 核心配置 | 用户可修改范围 |
|---|---|---|
| 身份 | 模块种类、实例ID、显示名、分项ID、目标主体 | 模板管理员可编辑；发布后冻结版本 |
| 适用 | 条件树、学校/业务/阶段/年度范围、适用的规则版本ID | 规则管理员维护，运行时申请人不可覆盖 |
| 取证 | 字段键、材料槽、系统事实标识、需要读取的页面/块、可信级别 | 上传材料可改变事实证据，不可把上传声明直接升级为受控事实 |
| 执行 | `deterministic/semantic/manual`、检查动作、错误时行为、未知时行为 | 模板管理员可编辑并接受静态校验 |
| 替代 | 当届正式认可的替代材料、合法例外、触发条件、引用依据 | 只有配置层可维护，不能由AI临时发明 |
| 输出 | 检查状态、问题代码、动作、责任人、证据引用、下一阶段 | 系统生成；有权审核人可复核并留痕 |
| 审计 | 模板/政策/材料/解析版本、输入hash、修订者、时间 | 系统生成，历史不可静默覆写 |

**最小原则**：材料槽不等于字段；字段不等于规则；规则不等于流程；“接收方接受”与“出具方授权”是两种不同核验，不能用一项布尔 `approved` 承载。

### 16.3 模板编辑器不应误认为“所有字段都是用户输入”

`申报事项.json` 在旧盲测包中只是**便于测试的运输格式**，不是正式审核编辑器必须让用户手动填写的所有字段；正式应用应有服务端受理元数据、学校身份接口、文档抽取、用户补填与人工补核四种不同来源。可信受理元数据不允许申请人改写，材料槽位实际上传附件与系统事实要分别维护。

## 17. 发布前静态检查（规范层与编辑器层）

以下任一失败都不应作为可自动执行的正式校本模板发布：

| 检查ID | 检查项 | 严重性 |
|---|---|---|
| GATE-01 | 标准中文名称唯一、模板ID稳定、分项及字段/槽位/规则编号不重复 | 阻断 |
| GATE-02 | 所有条件表达式引用的字段/事实存在；三值unknown有处理方式 | 阻断 |
| GATE-03 | 每条会产生缺件/不符合的校规有正式来源、确认状态、学校与版本适用范围 | 阻断 |
| GATE-04 | 不允许政审观点/宗教/品德敏感内容的AI评分、分类、自动合格判定 | 阻断 |
| GATE-05 | 接收与出具阶段签章条件互斥正确，无“申请即要求已盖章”逻辑 | 阻断 |
| GATE-06 | 学校规则只从受控配置加载，用户上传内容无法改变policy_id | 阻断 |
| GATE-07 | 纸件已上传、已寄送、已签收、验签通过未混同 | 阻断 |
| GATE-08 | 证据缺失、未知、冲突、不适用四种结果清楚区分 | 阻断 |
| GATE-09 | 关键异常多条并存，主状态聚合不丢失finding | 阻断 |
| GATE-10 | 补正、规则/文件版本变更后旧run失效并可追溯 | 阻断 |
| GATE-11 | 图像PDF多页材料能触发需要的视觉读取；无法读不当作空白 | 阻断/待运行验证 |

| GATE-15 | 27案既有回归及变形测试在真实执行器仍可比较和覆盖 | 发布前实测门槛；目前**未完成** |

## 18. 尚未落实的正式数据与不可伪造项

1. **成都理工2026正式政审表原DOCX**：公开通知证实附件名称，但本轮仍未读取逐格原件，不能断言本校各栏必填、手写签名或纸质红章。
2. **成都理工对外出具政审材料的组织授权**：可参考中国人民大学流程建通用出具分支，不得当作成都理工签批链。
3. **院校2027具体规则**：上位规定与学校具体收件通知是两层；无法取得学校当届公告，不能复用2026硬性收件条件。
4. **正式流程接口**：学籍/招生事实、组织授权、真实签章验签、纸质签收状态、用户身份映射等尚未在本模板内实测可用；用接口契约占位，不能伪造已连接。
5. **模型真实运行**：v0.2 27/27是同源测试构造与参考规则回归，不能代表生产Agent的视觉理解/误杀/漏检性能。
6. **保留/删除时限**：敏感材料实际留存时长应服从适用制度和组织要求，当前文档不编造具体天数。

## 19. 定稿路径与修订原则

**本版可以作为模板编辑器的共性结构抽取样本和未来系统适配需求基线，不可当已发布学校政审标准。**

建议定稿门槛：

- 将第3节抽象模块中的业务无关部分提取为编辑器基础组件；政审特殊性只留在模块实例。
- 五个分项、22个分支、59项字段中，先在编辑器校验“按条件启用”语义，不把所有字段设计成必填。
- 校规管理员确认每个硬条件的来源、确认状态、适用学校/年度/阶段和hash；**暂时未知的校本规则保留空白而不是补猜**。
- 把 v0.2 27案输入包和金标准继续物理隔离，真实运行时记录图像页覆盖率和每个异常的证据位置。
- 由实际审核运行暴露的误判回溯修订条件、规则与例外；不单凭离线参考器27/27就宣布验收。
- 如某个新申请目的需要实质性政审决定、超出材料程序审核授权，转人工或独立业务；不在本模板无限叠加。
