# 专项证明与用印审核｜完整审核模板（单文件 Markdown）v1.4

> **模板标准中文名称**：专项证明与用印审核
>
> **模板类型**：高校材料审核／用印前预审／阶段性权限与执行核验；**一个模板，多种组合条件分支**。
>
> **文档性质**：供模板编辑器建模、审核规则配置、后续实施与审计使用的**单文件业务模板规范**。这份文件不是成都理工大学现行校规的完整复刻，也不是已经部署的机器可执行规则包。
>
> **资料基准**：截至2026-10-10的阶段一业务调研、阶段二 **51项字段／29条候选条件规则**、阶段三 **19项实施风险及执行契约**、v1.3离线测试材料与参考验证器。2026-10-10整合修订。
>
> **适用原则**：两层调研、一套模板目录、按校配置规则；成都理工大学需求优先，其他高校官方业务可支持通用规则先行建模，但不得将外校要求自动视为本校现行强制规则。
>
> **实施状态**：业务结构与运行安全约束达到**设计冻结候选**；现行校本用印批办单原件、真实OA/章权、现场监印与实际电子章接口尚未完成核实和联调。离线模拟通过不等于真实审核系统验收通过。

## 0. 本文怎样用于模板编辑器

**这是实际业务模板，不是介绍性研究报告。** 从上到下提供：唯一模板身份 → 适用范围 → 模块组合 → 输入对象 → 51字段 → 29规则 → 阶段及优先级 → 数据接口 → 输出契约 → 校本配置 → 验收与来源。除链接的官方来源之外，审核所需的定义均在本文件内。

**标识层次**：

- `F01`—`F51`：本模板字段/材料字典的稳定追溯号；每个字段可由用户输入、可信系统提供或根据条件产生，不等于51项都必填。
- `SP-01`—`SP-29`：既有29条候选审核规则的稳定追溯号；即使存在编号，仍须经过适用规则激活才能成为某校的强制补正/驳回依据。
- `M-xx`：下文对**可复用编辑器模块的建议性编号**，用于提炼共性模块；不是新增模板，也不要求你的实际系统使用相同模块名。
- `CDxx`、`EXxx`：学校官方参考来源的文献索引，**不等于某校现行校规配置已生效**。

**编辑器必须区分五件事**：字段显示条件、取证方式、是否当前阶段必需、规则是否在该校被正式激活、模型能得出的结论。不能把一个布尔 `required=true` 同时承担这些语义。

**原文和方案的界线**：下文「51字段」和「29规则」追溯既有v1.2 CSV；新增的对象结构、模块接口、状态约束和建议配置字段是面向实施的设计抽象，不冒充高校官方表单原文字段。

## 1. 模板身份、目的和适用边界

| 属性 | 定义 |
|---|---|
| 唯一标准名称 | 专项证明与用印审核 |
| 核心用户目的 | 为学校、学院或获授权部门将要出具、确认或用印的特定文书，完成其适用阶段的材料和权限预审 |
| 核心审核对象 | **某份明确版本的待审文书及其申请事由、客观证据、签批范围、拟用章种和份数**；有多份则逐份审 |
| 可申请角色 | 学生、教职工、符合学校规定的校友、单位经办人或经授权受托人；**具体可见范围由学校和事项授权确定** |
| 本模板可以作出的结论 | 证据一致性、材料是否缺失、当前节点应填内容是否齐备、主管机关/章权是否待核、文件是否需重新审批、是否有可信执行记录 |
| 不可以作出的结论 | 不可代替学校批准用印、自动生成官方公章、鉴定电子印章真伪、认定主观政审/师德结论、确认真实执行完成而无可信记录 |
| 文书处理方式 | 纸质审批、OA审批、线下核对、可信电子用印，取决于学校开通的受控接口 |
| 与既有服务的关系 | 标准电子证明可满足用途时，优先分流自助；已经由其他实质业务批准的文书可在本模板只做末端用印程序核验 |
| 入口与模板关系 | 前台可以按“获取特殊证明／办理材料用印”等目的导航，后台仍只保留一套「专项证明与用印审核」 |

### 1.1 明确覆盖的四种可组合办理情形

| 情形/条件分支 | 什么时候触发 | 审核重点 | 不应强制的无关材料 |
|---|---|---|---|
| 非标准事实证明 | 待印文书证明在读、任职、奖励或其他有权部门可核事实，现成电子凭证不满足要求 | 证明内容 ↔ 权威事实 ↔ 出具部门权限 | 没有译文时不要求翻译机构、中文对照表和信封 |
| 制式申请材料 | 接收方指定填写申请表、推荐表、就业升学表等，并需要学校的某个节点签字用印 | 当期表版本、当前节点应填栏、前序签批、所需章种 | 申请预审时不要求尚未轮到的学校意见/章位已填 |
| 译文/外文核对 | 申请人请求对中文可信材料的译本进行核对和校方用印 | 人名、日期、课程成绩、数字及注释，译文制作方式和校方权限 | 不统一强制“专业翻译公司”；外校要求按校配置 |
| 原件/复印一致性及密封骑缝 | 办理副本一致性用印、资料密封、信封封口章等 | 原始材料 ↔ 副本、批准清单 ↔ 待封材料、现场工作人员执行 | 预审时不要求已盖完印或已封口的照片 |

**组合方式**：同一案例允许选择若干动作，例如“中文成绩单译文核对 + 复印件一致性 + 密封 + 骑缝章”；动作可以组合，但各动作的核验结论和授权**互不继承**。

### 1.2 不覆盖与应分流

- 标准可信成绩单、在读/在职事实证明的**普通自助下载或打印**，不应额外制造上传材料审批。
- 合同、采购、财务凭证、科研项目等**实质审查与授权**；仅在相应主业务完成后，允许处理本模板有权覆盖的末端用印检查。
- 政审、现实表现、师德师风等需要**组织实质鉴定**的材料；不能由普通事实证明的形式核验代替。
- 与学校无关或学校没有权力确认的外部事实，不能因材料里写了学校名称就允许校方证明。
- 没有章权批准、没有真实OA决定、没有实际执行记录的申请，不能因为AI说“通过”就自动推进至批准或完成。

## 2. 一套模板中的模块划分（供提炼编辑器共性）

**区分**：`通用`表示其他高校审核模板可能复用的基础模块，`专项`表示本用印模板特有的字段与业务规则，`条件复用`表示只有需要该类动作的模板才安装。此分类是**编辑器设计建议**，不是来源文件里已有的程序架构。

| 模块标识 | 模块名称 | 类别 | 输入 | 输出/规则职责 | 启用时机 |
|---|---|---|---|---|---|
| M-01 | 模板身份与版本 | 通用 | 模板名称、业务目的、模板修订号 | 唯一模板定位、兼容标识 | 始终 |
| M-02 | 机构规则与适用范围 | 通用 | 学校、部门、角色、事项、动作、阶段、有效期 | 唯一有效规则包／`HOLD_POLICY` | 始终 |
| M-03 | 办理主体与授权关系 | 通用 | 申请人、事实主体、受托人、经办单位及校方角色 | 主体关系与权限证据 | 按角色或代办条件 |
| M-04 | 动态表单字段 | 通用 | 字段定义、条件、阶段、字段级来源 | 当前应显示／应核／无需核的集合 | 始终，字段按条件展现 |
| M-05 | 材料与证据绑定 | 通用 | 文书、附件、可信系统数据、人工核验记录 | 证据溯源、跨件引用、真值状态 | 任何需要实质核验的字段 |
| M-06 | 条件规则选择与执行 | 通用 | 规则触发、适用校规、证据、异常、例外 | 每条规则的局部结果 | 每轮审核 |
| M-07 | 阶段与审批事件 | 通用 | 当前阶段、可信OA事件与角色 | 合法状态推进或等待 | 跨阶段处理时 |
| M-08 | 多问题合成与转办 | 通用 | 各规则局部结果、优先级、下一处理角色 | 完整`issues[]`及首要下一动作 | 每轮审核 |
| M-09 | 人工复核及合法替代 | 通用 | 授权人工决定、原因、期限、范围 | 按指定范围接受替代/退回，留审计轨迹 | 自动证据不足、主管裁量时 |
| M-10 | 测试与追溯 | 通用 | 规则ID、用例、标准答案、证据位置 | 可验收清单和覆盖说明 | 开发/验收 |
| M-11 | 待用印文书集合 | 专项 | 一份或多份拟印正文、用途及版次 | 文书级审核单元 | 本模板必需 |
| M-12 | 事实证明核验 | 条件复用 | 被证明事实、学校权威事实或主管意见 | `MATCH / CONFLICT / UNKNOWN` | 涉及客观事实证明 |
| M-13 | 制式表栏目责任 | 条件复用 | 当年表单、栏目、负责角色、需要阶段 | 判断合法留白或真正缺填 | 制式表 |
| M-14 | 外文翻译对照 | 条件复用 | 中文事实源、译件、对应项、译者规则 | 具体差异/缺漏定位 | 译文核对 |
| M-15 | 原件/复印/密封处理 | 条件复用 | 原件、复制件、清单、封装方式、现场记录 | 一致性与现场待执行状态 | 原复件、密封、骑缝 |
| M-16 | 印章权限与用印项 | 专项 | 文书ID、印章机关、章种、份数、用途 | 逐项批准范围核验 | 请求任何学校用印 |
| M-17 | 获批稿与送印稿比对 | 专项 | 批准快照、待印版本、实质差异 | 继续、待人工核对、重新审批 | 用印批准后 |
| M-18 | 实际用印及出件记录 | 专项 | 可信执行事件、执行文书、章种、份数 | 逐项已执行／未执行，决定能否完成 | 用印执行后 |

### 2.1 模块必须支持的编辑器能力

1. **可重复实例**：一个申请可以含多份`DocumentItem`，每份有多个`SealItem`；模块支持数组/实例级绑定，而非所有字段只存一份。
2. **条件可组合**：业务事项、处理动作、申请人身份、学校、接收方要求、办理阶段是相互独立的条件轴，不能做成排斥的单选式“模板分支”。
3. **字段生命周期**：区别「可显示」「当前必须获得」「未来节点要求」「只由系统产生」「人工后置记录」。
4. **规则来源标签**：支持 `通用技术安全约束 / 正式校规已核并获校方授权 / 外校候选 / 设计假设 / 历史失效或待核`。
5. **局部结论与整体动作分离**：规则结果不能简单求和或多数投票；必须保留全部局部异常。
6. **可信来源隔离**：用户上传任何材料都不能直接生成`trusted_approval`、`seal_executed`或`policy_verified`。
7. **人工复核要可审计**：授权人可以在规定范围内确认合法替代证据，但不得让AI自行创建“例外批准”。
8. **界面不必等于逻辑单元**：模块化是为了复用录入、解析和审查能力，不意味着每个模块必须显示为单独页面或用户可选模板。

## 3. 条件模型与材料收集门槛

### 3.1 六个动态判定轴

| 轴 | 典型值 | 用途与影响 |
|---|---|---|
| 事项 `business_kind` | `FACT_PROOF`（事实证明）、`FORM_DOCUMENT`（制式材料）、由学校授权的其他个人/制式文书 | 决定事实或栏目检查 |
| 动作 `actions[]` | `SEAL_DOCUMENT`、`TRANSLATION_CHECK`、`ORIGINAL_COPY_CHECK`、`DOCUMENT_ENVELOPE`、`SEAL_ENVELOPE`、`ELECTRONIC_SEAL` | 多选，生成相应条件检查及依赖关系；**取值属于设计建议** |
| 申请者关系 `actor_mode` | `SELF`、`ORG_OPERATOR`、`DELEGATED` | 决定谁有权限提交和需要何种授权 |
| 学校受理范围 | `school_id`、`issuer_department`、`role`、`matter`、有效期 | 决定本校适用规则与章权；不能跨校兜底 |
| 接收单位限制 | 有效表单版本、送达形式、纸电章接受性、是否密封 | 只约束接收要求，**不授予学校印章权限** |
| 办理阶段 | `INTAKE`、`PRECHECK`、`DEPARTMENT_REVIEW`、`APPROVED_FOR_SEAL`、`PRE_SEAL_RECHECK`、`SEAL_EXECUTION`、`COMPLETE` | 决定此时哪个字段应填和哪些凭据才能可信存在 |

### 3.2 字段“必需”必须分三层

- **对象完整性（运行层）**：能识别业务和一份可审核的正文、申请主体、学校上下文等，否则无法开展相应审查；不等于学校要求用户额外上传证件影像。
- **学校正式要求（制度层）**：经学校制度、适用事项及版本确认后，才将所需签字、附件、译件资质、印章等设为可强制补正的条件。
- **阶段到期（流程层）**：签章人尚未轮到的栏目、尚未完成的用印或现场封装，在当前阶段应是`WAIT_FUTURE_STAGE`，不能当作`MISSING_REQUIRED`。

**判别顺序**：先看触发条件是否成立，再核规则是否正式适用、要求是否当前到期、证据是否可由可信系统提供、合法替代是否存在，最后才决定是否缺件。出现适用版本未知或规则重复时不得借用其他学校条款。

### 3.3 规则适用状态与审批配置不得混淆

| 状态（建议） | 可以做什么 | 不能做什么 |
|---|---|---|
| `candidate` | 为模板编辑器提供候选审核点、供研发模拟 | 不得因候选规则直接驳回成都理工申请 |
| `researched` | 表示查得某校官方资料、保留原文链接、时效及适用范围 | 未获学校配置确认前不可假定现行有效 |
| `enforceable` | 经校方/有权配置管理核验正式生效、适用范围唯一，可用于当前阶段条件必需与程序性补正 | 仍不得代替签章批准或组织授权 |
| `unknown_or_conflicted` | 输出`HOLD_POLICY`，允许人工确认与非强制材料建议 | 不可自动套最严格外校要求或判定违反校规 |

上述枚举是**实现建议**，并非官方软件协议；实际编辑器可使用其他字段名，但语义不可丢失。
## 4. 数据对象和可信边界（独立于用户界面）

### 4.1 最小业务对象

| 对象 | 字段/关系（概念性结构） | 可信来源与约束 |
|---|---|---|
| `ReviewCase` | `case_id`、模板名、`school_id`、`matter`、`policy_version`、`business_kind`、`actions[]`、当前阶段、创建时间 | `case_id`与阶段在服务端管理；客户端的学校/版本仅是待核请求 |
| `ActorSet` | `requester`、`subject`、`agent`（可空）、`issuer_org`、`operator`、`reviewer` | 不把申请人、被证明人、经办人、签发组织默认为同一主体 |
| `DocumentItem[]` | 文书ID、类别、用途、收件单位、申请时正文、修订版本、证据引用、批准快照（后置） | 每份文书独立审核并可定位页码/字段区域 |
| `SealItem[]` | 关联文书ID、拟签发机关、章种、份数、用途、执行顺序、已批准范围 | 逐文书×章种×数量绑定批准，不以“审批单通过”自动授权全部文书 |
| `EvidenceRef[]` | 证据ID、来源类型、附件或接口、页码/框选、抽取值、权威性及验证状态 | 附件内容的OCR抽取不是权威学籍/人事事实，也不是政府验章 |
| `PolicyScope` | 颁发学校、部门、事项、角色、动作集、阶段、生效期间、版本、官方依据及发布确认状态 | 有权规则配置端产生；匹配必须唯一且在时效内 |
| `ApprovalEvent[]` | 事件ID、当前阶段、原阶段、批准人角色、批准范围、关联文件快照、操作时间、撤销关系 | **只可信接收服务端OA或有权审批接口数据** |
| `SealExecutionEvent[]` | 执行ID、对应`SealItem`、文书版本、章种、份数、操作员、时间、结果、追踪来源 | **只可信用印系统或有权人员受控登记**；不能由用户上传JSON替代 |
| `ReviewIssue[]` | 局部规则结果、材料定位、具体冲突、适用依据、责任角色、下一动作 | 可被人工复核，不能以总体动作覆盖 |
| `ReviewResult` | 材料检查向量、首要下一动作、全部问题、可信审批状态、可信执行状态 | 不使用单一“通过”表示材料、审批、出件均已完成 |

### 4.2 三层数据来源必须隔离

**用户或文档来源**：用户填写的目的、申请说明、拟印正文、上传附件、扫描件及其OCR结果。它们是**待审核事实或待验材料**，不能作为学校已经批准的证明。

**学校可信系统来源**：登录身份、学籍/任职/奖惩等业务事实接口、正式章权清单、OA审批事件及批准版本、已执行用印日志、受控人工核验记录。这些由可信后端适配器获取，必须记录来源身份、访问权限、时间和数据版本。

**适用规则来源**：学校现行正式文件、内部经授权发布的规则配置、接收单位明确有效的受文要求。规则来源必须说明**谁发布、对谁生效、何时有效、覆盖什么事项**；引用网页并不直接等于校方规则包已签发。

### 4.3 建议供模板编辑器预留的字段/规则属性

| 属性 | 作用 | 适用位置 |
|---|---|---|
| `id`、`semantic_key` | 稳定引用与规则间跨版本迁移 | 字段与规则 |
| `label`、`help_text`、`input_type` | 表单渲染与解释 | 字段 |
| `scope`、`visible_when`、`required_when` | 控制显示与条件必需 | 字段/分支 |
| `required_at_stage`、`responsible_actor` | 防止提前要求未来签批 | 字段/审批节点 |
| `evidence_sources`、`trust_level`、`fallback_sources` | 确定用户上传、系统取证、可替代材料 | 字段/证据 |
| `match_fields`、`comparison_type`、`tolerance` | 精确指定多文书对比方式及合理例外 | 核验规则 |
| `policy_scope`、`source_ref`、`effective_from/to` | 正式规则来源与时效 | 校规/规则 |
| `activation_state`、`version`、`exception_scope` | 确定是否可强制执行、版本及人工例外范围 | 规则 |

**注意**：这些是建议的抽象接口能力，不是既有系统已实现的数据结构或字段命名。对无法直接表达的条件应支持人工挂起，不应偷偷用默认值替代正式审批事实。

| F50 纸质现场用印记录 | 学校实际完成纸章 | 后置记录；监印人、完成时间、留存件、印章份数 | 核真实执行状态、出件数量 | 执行后 | EX03;CD01 | 预审/审批中不能要求已出件 |
| F51 文书是否实质空白 | 提交的实际拟用印材料 | 条件必需；正文内容完整度、尚待校方签章栏目 | 区分空白正文和预留学校签章位 | 预审/执行前 | EX03;EX07 | 合法待签章栏留白不能误杀 |
### 5.7 字段字典中的共性及容易错误合并的地方

- `F01—F17`是定位和主体相关的字段族，但各项`trigger`并不一致；例如是否为代办必须先判断，不能把代办授权书作为人人必交。
- 事实证明、制式表、翻译、原复件/密封与用印五类字段**可同时启用，也可部分不适用**；例如同一英文制式证明会复用多个字段组。
- `F18—F51`中某些字段天然由可信后台或现场才产生，编辑器不得将其放入申请人上传附件清单，例如实际执行日志、批准快照或监印记录。
- 高校官方来源的字典字段是**核验线索的来源说明**，不是已经完成校本表单字段逐格对照；尤其成都理工《用印批办单2025》原表目前仍未核得完整字段。
- 不应通过“有证件影像”推导“身份证真实”，也不应通过“有红色公章像素”推导“已经用印”。

## 6. 完整候选条件规则（29条）

### 6.1 规则生效前置条件

在每条`SP-xx`被用作某校**强制补正、违规结论、拒回**之前，必须检查：

1. 该规则**是否触发**（适用业务、材料类型、动作及当前阶段），未触发即`NOT_APPLICABLE`。
2. 是否存在**学校/签发部门现行有效的制度或经授权的规则配置**；只有外校实例的，针对成都理工仅能给出候选检查建议，不能强制否决。
3. 特定字段是否**已到应填或应完成阶段**；未来校方意见、真正签章或密封可是`WAIT_FUTURE_STAGE`。
4. 权威数据是否可取得，或是否存在正式认可的替代证据；未知事实不能认定为虚假。
5. 签发机构章权与接收方要求是否冲突；接收单位的意见不能授权学校使用无权限的印章。
6. 多个规则命中时，必须各自保留异常和证据位置；整体下一动作不能隐藏其他问题。

### 6.3 29条规则的技术解释（避免过度机械执行）

- `SP-01—03`是**业务路由**，先确定普通自助、实质业务还是本模板内的程序核验；不是“用户选择了本模板就必定进入本模板”。
- `SP-04`要求可审核的**明确正文对象**；如校内系统可可信生成定稿，则不必另行上传PDF。
- `SP-05/08/13/14/18`是多证据一致性检查；**冲突、缺件、来源未知**分别输出，不把OCR低置信度当“伪造”。
- `SP-06/07/09/23`核主体与授权；经办人、文书主体、事实主管部门、签章组织是不同角色，不能通过同名字段自动互认。
- `SP-10/11/12/21/22/28`共同实现**栏目责任人与阶段到期判定**；学校未来意见栏空白是正常状态，但申请人本阶段应填栏缺失可以补正。
- `SP-15—17`的译文资质、中文原件先签章和委托书依赖具体学校正式办理规则；不能变成全国统一三件套。
- `SP-19/20/26/27`要区分**材料清单准备、现场动作、实际用印和完成记录**。申请时没密封照片，不属于通用缺件；用印执行完但没有可信记录，不能自动完成。
- `SP-24/25`的批准稿与送印稿比较：同哈希能证明相同字节；异哈希只说明字节不同，需比较正文、关键数字、签署页、附件、用途与章种，无法证实时`WAIT_VERSION_VERIFICATION`。
- `SP-29`是**缺少适用版本时挂起强制裁决的保护规则**，即使先执行了某些通用形式提示，也不得凭外校要求直接做成都理工强制不通过。

## 7. 审核顺序、阶段及权限控制

### 7.1 端到端审核流程（抽象基线）

| 阶段 | 最重要的输入 | 当期允许检查 | 不得要求的未来证据 | 阶段结束的正确语义 |
|---|---|---|---|---|
| `INTAKE` 入口 | 申请目的、主体关系、办理动作、文书类别 | 识别自助/越界业务、校方办理权限、规则版本 | 获批稿、已经盖章或封口 | 分流／进入预审／待校规确认 |
| `PRECHECK` 材料预审 | 待审文书、申办事实与附件、条件分支 | 当前应填字段、事实一致性、代办、译文与拟封清单 | 未轮到的组织签字、现场核原件、用印完成日志 | 补正／事实待核／提交主管审核 |
| `DEPARTMENT_REVIEW` 部门审批 | 有权单位当前审批记录及前置节点 | 当前到期签批及章权、批准范围 | 尚未出现的后续监印结果 | 等待有权人员审批/退回 |
| `APPROVED_FOR_SEAL` 获批 | 真实批准事件及绑定快照 | 检查批准具体文书、用途、章种、份数及有效期 | 实际完成用印凭据 | 进入送印稿复核 |
| `PRE_SEAL_RECHECK` 用印前 | 现场送印稿、批准快照、原件/清单要求 | 内容和版本一致性、是否需要重批、原件核对 | 已执行记录（尚未盖章） | 进入现场／重新审批／待版本核实 |
| `SEAL_EXECUTION` 用印执行 | 用印责任人、具体执行项、现场要求 | 原件核验、实际盖章/电子章、封装和封口顺序 | 尚未完成的后续动作 | 记录局部执行/待补执行凭据 |
| `COMPLETE` 出件完成 | 受信用印/交付事件覆盖全部批准项目 | 逐项核全，登记出件与范围 | 不再让申请人重交系统已掌握证据 | 全部实际执行完成 |

**注意**：这是一条正常办理的**参考正向路径**，并非生产系统全部状态图。退回补正、取消、部分用印、审批撤销、授权失效、审批后重新递交，须由校内OA配置合法的回退/重新审批迁移；模型不能只靠更改`stage`字段跨越节点。

### 7.2 可信阶段迁移条件

- 每条OA流程事件必须具有唯一事件标识、case归属、签发服务来源、前后阶段、操作人角色与权限、发生时间及生效/撤销状态。
- 事件的状态迁移必须遵循当前学校配置的审批流程；前序签批被撤销时，不得沿用原批准范围直接用印。
- 用户自己上传的“领导已经同意”“已审批通过”文字、截图、模拟JSON一律不能作为**已批准事实**。
- 用印完成只能依赖真实授权的执行事件；允许一单多文书、多章多份**部分完成**，但不能称整个申请已完成。

### 7.3 多动作依赖与执行顺序

同一模板的动作应形成**无环依赖图**：例如学校要求“中文先盖章→译文核对→批准英文稿→现场核原件→英语材料用印→信封密封→骑缝章登记”时，才按此顺序执行。其他学校可有不同合法顺序，因此不能把该例固定成全国通用流程。

**每个动作实例至少记录**：`action_id`、动作种类、关联文书ID、前置依赖、何时要求、应执行角色、证据来源、局部状态和有权执行/确认事件。

依赖有环、引用不存在的文书或审批快照、多个动作互相给予越权授权时，应作为模板配置错误或程序异常挂起，不得由模型任意选顺序。

## 8. 文件批准版本与用印执行项绑定（关键安全约束）

### 8.1 一次批准必须绑定什么

对每一项批准，明确记录：`case_id`、可信审批事件ID、受控文书ID、批准时文书版本或完整快照、批准时关键正文/附件、文书用途、收件对象（若适用）、应使用的章种及签发机构、批准份数、批准期限、批准操作者及角色。

- **不可只批准一个文件名**：同名不同正文的文件不共享批准结论。
- **不可只批准整个申请单**：一个申请包含多份不同证明时，未在批准范围内的另一份文书不能搭便车。
- **不可忽略份数/章种变化**：新增份数、改章种、增加收件单位或正文实质修改，均可能越过原批准范围，需按正式校规重新审批或有权人员确认。
- **不可通过“文件哈希不变”替代权限检查**：字节一致不证明该份文件被正确授权使用某一枚章。

### 8.2 文件版本核对步骤

1. 取得**可信获批快照**与**现场实际待盖章稿**，关联同一文书对象。
2. 两份文件哈希一致时可以确认字节级一致；仍需核对章种、份数、用途及批准有效期。
3. 哈希不同先比较**正文关键字段、金额和日期（若有）、姓名、接受/送达单位、签署页、附件页及印章位置**，不要只用文本字符串或OCR粗略相似度。
4. **实质内容或批准范围变化**：`REAPPROVAL_REQUIRED`，不可将“申请人改动PDF元数据”一律等同实质变化。
5. **只是重新导出/分页/元数据差异且有可信核验结论**：可继续；缺少足够可核证据时`WAIT_VERSION_VERIFICATION`，由有权人员复核。
6. 对已盖电子章而产生的文件字节变化，必须由可信签章校验服务判断签署与文档完整性，不能用原始哈希相异直接判错。

### 8.3 每一个执行项逐条确认

每个`SealItem`要关联**明确文书版本 + 印章签发机构/章种 + 数量 + 实际执行动作**。真实执行日志至少需记录相应文书与批准ID、执行人员/服务、实际份数、操作时间、执行文件版本/签署校验结果、执行状态和撤销/作废情况。

`COMPLETE`条件：**所有当前应完成的执行项被有效可信记录覆盖**，不存在批准撤销、文书改稿、错章、超份数、缺现场验核等阻断。一个文书只盖了一部分章、3份仅盖2份，均只能记为部分完成或待执行，不能整体完成。

## 9. 规则检查结果、问题对象与整体处理动作

### 9.1 字段或规则的局部结果

| 局部状态 | 含义 | 典型处理 |
|---|---|---|
| `NOT_APPLICABLE` | 条件未触发、不属于此业务/阶段 | 不要求材料，不视为缺件 |
| `SATISFIED` | 在适用、当前到期和可信证据条件下核验满足 | 保留依据与证据位置 |
| `MISSING_REQUIRED` | 该校正式适用且当前应提供的材料缺失 | `NEED_CORRECTION` |
| `CONTRADICTED` | 可定位的两项适用证据之间存在实质矛盾 | 补正或有权事实复核，不能直接指称伪造 |
| `UNVERIFIED` | 数据源不可用、证据效力不能核定或事实未证实 | `HOLD_FACT_VERIFICATION`/`HOLD_AUTHORITY` |
| `WAIT_FUTURE_STAGE` | 该材料、签名或操作属于后续节点 | 当前不应阻断为缺件；等待阶段推进 |

### 9.2 本模板统一的整体下一动作

| 下一动作 | 何时选用 | 核心防误判 |
|---|---|---|
| `ROUTE_SELF_SERVICE` | 可直接从可信学校服务取得符合用途的成品，且无额外用印要求 | 自助可用前先核用途和可使用范围 |
| `ROUTE_OUT` | 合同/财务/科研实质审批、组织政审等已超出本模板 | 不是“材料审核拒绝” |
| `HOLD_POLICY` | 找不到唯一有效规则包；规则已过期或互相冲突 | 不能默认套外校规定判本校不通过 |
| `HOLD_AUTHORITY` | 代办、事实主管部门或章权不明/冲突 | 接收方不能代签发方授权印章 |
| `NEED_CORRECTION` | 当前正式规则明确要求且确实缺件，或应修正文书实质内容 | 保留具体缺失/冲突定位 |
| `HOLD_FACT_VERIFICATION` | 可信事实来源不可得或冲突不能确定真值 | 不得以“未联网”判个人材料虚假 |
| `REAPPROVAL_REQUIRED` | 已批准后关键正文、用途、章种或份数被实质改变 | 保留原审批与送印稿差异证据 |
| `WAIT_VERSION_VERIFICATION` | 哈希不同但无法证明是否实质变化 | 不机械判篡改、不默认放行 |
| `READY_FOR_REVIEW` | 当前可执行材料检查通过，可送主管审核 | **不是最终批准** |
| `WAIT_APPROVAL` | 已进入当前学校要求的审批节点，尚无有效有权批准 | **不能自行推进批准状态** |
| `WAIT_ONSITE` | 当前已批准，需要现场核原件、密封或人工确认 | 不提前要求申请人盖章/封口 |
| `READY_FOR_SEAL` | 送印前复核及必要现场条件均已满足，等待有权监印 | 仍未实际执行用印 |
| `WAIT_EXECUTION_RECORD` | 用印执行中或完成但尚无完整可信执行记录 | 不能因图像有红章宣称完成 |
| `COMPLETE` | 所有应完成事项都有有效可信执行记录 | 批准了≠已盖章，部分完成≠全部完成 |

### 9.3 每条问题应输出的证据链

一条`Issue`应能够回答：

- `rule_id`（例如SP-24）与是否已正式激活；`policy_id`、签发学校、部门、版次、生效区间；当前办理阶段。
- 触发了什么条件，在哪份文书／哪一页／哪一区域／哪个字段观察到了什么。
- 哪个系统或附件支持观察值，信任状态为何；与哪个批准快照或权威记录比对。
- 发现的是缺件、实质冲突、未知、权限不足还是未来节点，不能笼统都叫“拒绝”。
- 建议下一动作及谁负责（申请人补正、事实主管部门核验、校内章权管理员、院系审批人、监印人员）。
- 哪种合法替代证明、人工复核或例外可在该校适用；不展示多余敏感信息。

### 9.4 整体动作聚合规则

先保留**全部局部issues**，再选择一个**当前最需要处理的下一动作**。可供编辑器实现的建议先后顺序：

1. 真正应分流的自助或其他实质业务先排除；若同一批申请中不同文书分别可自助与专项，需要**逐文书分流**，不能丢掉其余待审文书。
2. 已批准后出现实质改稿→`REAPPROVAL_REQUIRED`。
3. 规则包不唯一、失效、无权激活→`HOLD_POLICY`。
4. 印章或代办授权冲突→`HOLD_AUTHORITY`。
5. 当前明确应交材料缺失、可核实的事实内容不一致→`NEED_CORRECTION`（必要时也保留`HOLD_FACT_VERIFICATION`）。
6. 可信事实或版本未核明→`HOLD_FACT_VERIFICATION`或`WAIT_VERSION_VERIFICATION`；后者可在用印前复核场景单独优先。
7. 无权批准、未达现场或没有执行记录→对应`WAIT_APPROVAL / WAIT_ONSITE / WAIT_EXECUTION_RECORD`。
8. 只有全部应执行动作已得到可信事件覆盖时，才可能进入`COMPLETE`。

这只是**产品工作流合成优先级建议，不是高校行政裁决先后顺序**。多文书混合申请应保留逐文书的`next_action`及汇总，不允许一个通过项掩盖另一个阻断项。

## 10. 学校规则、收件要求和例外裁量

### 10.1 规则匹配器的七个核心键

匹配规则包必须至少考虑**签发学校、主管部门、办理事项、申请者身份/角色、处理动作集、当前办理阶段、有效制度版本及时间**（最后一组同时校验时间范围）。候选规则先核授权来源与生效区间，再做**唯一性匹配**；无命中、两个互不兼容的命中或已过期，一律`HOLD_POLICY`。不通过任意“最新文件优先”或“谁要求更严格”进行自动覆盖。

**签发方权限**与**收件方具体要求**是两个可共存但不互相授权的约束域：接收方可以限定格式、纸电章接受方式、收件时间和表单版本；是否有权使用某枚学校章，由签发学校的正式章权与流程决定。二者冲突时应转有权人员沟通，不自动改章、不让模型“补授权”。

### 10.2 合法替代材料与人工覆盖

人工复核记录至少需要：操作人及权限、关联案件与文书、被替代的规则或证据、接受/不接受决定、理由、依据、适用范围、记录时间、有效期及后续撤销关联。**这不是模型可自行创建的审批事件**；人工接受替代证明也不能直接跳过必要章权、最终批准与执行凭据。

### 10.3 敏感材料最小化

在不同办理情形下只收集该场景需要的字段。优先从学校授权系统读取必要事实状态；不需要为了验证奖学金证明就获取整份人事/家庭/健康档案。证据日志只存必要定位与脱敏摘要；保存时长、访问角色与删除/审计机制由学校授权规定及适用法律落实，不能在模板里虚构统一期限。

## 11. 一份组合申请的完整审核路径示例（仅作为模型运行示意）

> 以下为**合成案例**，不代表成都理工大学2026年规则，也不包含学校真实公章。目的只是展示各模块如何装配，不向材料内写入“这里有错误/预期拒绝”等答案提示。

**申请目标**：学生请求英文奖学金证明、对应中文凭据、两份学校行政用印文件，并将文件由有权人员密封后盖信封封口章。

**动作与模块**：`FACT_PROOF` → `TRANSLATION_CHECK` + `SEAL_DOCUMENT` + `DOCUMENT_ENVELOPE` + `SEAL_ENVELOPE`；启用主体身份（M-03）、文书（M-11）、事实源（M-12）、译文（M-14）、密封（M-15）、章权（M-16）、审批版本（M-17）及执行记录（M-18），不启用无关的科研/财务合同审核。

| 步骤 | 观察或事实 | 模板应当做的事 | 不可提前做的事 |
|---|---|---|---|
| 1. 受理 | 申请人声明就读学校、具体证明用途、需要英文和密封 | 确定唯一合法规则包，查有无现成可满足需求的可信英文证明 | 未确认学校具体规则就设专业翻译公司必交 |
| 2. 取证 | 中文可信记录显示某学年奖学金，与英文稿学年不符 | 通过SP-08、SP-13、SP-14定位不同字段，提示补正 | 把不一致直接指控为“造假” |
| 3. 修订 | 申请人补正译文，学校签字盖章位仍空白 | 检查当前应填内容，允许未来学校签署栏合法空白 | 因尚未见红章就判材料不通过 |
| 4. 主管审批 | 有权学校人员审阅每份文件及章种份数 | 等待可信OA批准事件，绑定文件版本和批准范围 | AI自行写入“已批准” |
| 5. 用印前重核 | 提交送印稿，PDF字节变化，正文尚需核对 | 先语义比对；有实质新内容就要求重新批准，无证据时待人工核对 | 异哈希一概认定篡改或一致 |
| 6. 现场核验 | 学校规定工作人员核原件、进行材料密封 | 等待受控现场人员核验/封装并记载事件 | 要求预审时用户提供已密封照片 |
| 7. 用印记录 | 校内执行服务记录两份材料和信封用印项目 | 按文书/章种/份数逐项核对，未执行全时维持等待 | 凭上传的盖章照片宣布完成 |
| 8. 出件 | 全部项目有受信执行记录且未撤销 | 仅此时可表示完成所有授权用印动作 | 把“材料预审符合要求”混作真实出件完成 |

**示例输出语义**：在第3步，整体结论应是`READY_FOR_REVIEW`或`WAIT_APPROVAL`（取决于真实流程阶段），而不是`COMPLETE`；第5步如果正文改变应是`REAPPROVAL_REQUIRED`；第7步若缺一份执行记录，整体仍非`COMPLETE`。

## 12. 异常与合理例外清单（编辑器建议支持）

| 异常/例外 | 应如何处理 | 为什么不能一刀切 |
|---|---|---|
| 学校可自助获取现成证明，但接收方还要求另行密封 | 不强制分流；判断额外用印/密封是否合法必要 | 自助证明不能替代全部动作 |
| 申请人为单位经办而非证明主体 | 先核是否有单位授权和适用代理范围 | 不一定是个人委托书，也不能假定本人可直接审批 |
| 本人应填栏完整，学校以后盖章栏空白 | `WAIT_FUTURE_STAGE`；不能按缺件拒绝 | 批准/签章尚未发生 |
| 拟用印正文几乎空白，但仅落款待盖章 | 分清正文与待签栏；正文空白才提示补正 | 用印前申请的签章处天然空白 |
| 翻译机构、原件查验要求校际不同 | 仅命中该校该事项有效规则才强制 | 外校规定不可交叉套用 |
| 中文原件需先用印但该校未配置 | 不触发缺件，标记规则待核或不适用 | 不能把EX05变成成都理工的统一要求 |
| 学校事实接口超时或无数据 | `UNVERIFIED`，转有权核实 | 未核实不等于错误，也不等于自动通过 |
| 文件哈希变化但只是PDF元数据不同 | 受信正文比对后允许继续 | 哈希只能证明字节差异，不能证明内容差异 |
| 获批后文书正文或份数实质改变 | `REAPPROVAL_REQUIRED` | 不能用旧批准包覆盖新版本 |
| 纸质原件、信封现场才会出现 | `WAIT_ONSITE` | 预审不应要求未来执行凭据 |
| 印章影像很像学校红章 | 只能记录图像特征，不能当真实执行日志 | 图像不等于学校正式章务事件 |
| 多份文书中一份已经用印、一份尚未完成 | 分文书记录状态，整单不能完成 | 部分通过不等于全部完成 |
| 成都理工2025批办单仅有下载目录但原文栏位未核对 | 校本字段保留待核，通用模板照常建模 | 不能靠标题猜测本校必填字段 |

## 13. 测试、追溯和实际接入验收

### 13.1 现有试验成果的正确表述

已有**51个候选字段、29条条件规则、19项设计/接入问题**；v1.2离线参考审核器有**70项预设断言**，后续为11条此前缺专项测试的规则增加**33项逐条断言及5项组合断言**，合计**108项结构化参考断言**。另外已构造**38个合成案例、231份图像型PDF**作为可送解析器的试验输入；金标答案与申请材料分离。

**它们不是**真实OCR准确率、学校签章真实性测试、生产章权验证、学校OA集成成功证明。29条规则有定向测试点不意味着每种组合、例外、真实材料路径均已测完。

### 13.2 不同测试层必须拆开

| 层次 | 输入 | 评估重点 | 当前状态 |
|---|---|---|---|
| 规则结构一致性 | 已抽取好的结构化事实/虚构规则包 | 触发、适用、不适用、局部状态、整体动作 | 已有离线参考断言，不是外部盲测 |
| 文件解析层 | 原始扫描图片、PDF、制式表及译文 | OCR/表格/文本定位与跨页对应 | 已有合成文件，实际系统OCR效果未验收 |
| 规则解释与审核层 | 来自解析器的客观证据 + 学校适用规则 | 模型是否真正识别证据、给出正确局部结论和依据 | 未在实际用户审核系统跑通 |
| 可信工作流层 | 学校OA、章权、审批快照、现场和用印日志 | 是否越权、是否能正确重审、是否能分辨部分完成 | 学校真实接口尚未接入 |

### 13.3 验收检查表

## 17. 本模板可抽取的跨模板共性（供编辑器研发总结）

下表不是另外设立模板，而是帮助研发阶段确认**共性模块切分边界**：

| 候选共性能力 | 为什么值得抽象 | 哪些一定不能共享成一个结论 |
|---|---|---|
| 条件字段显示与强制性 | 几乎所有材料审核都有“特定角色/事项才需要某项材料” | 必交材料不能在不同学校直接继承 |
| 证据引用与跨文书一致性 | OCR/表格/图片及可信系统字段可以复用解析与定位 | “内容一致”不等于事实真实，也不等于审批被授权 |
| 学校规则包适用性选择 | 同一审核目的随学校和版本变化 | 不能依据“严格程度”合并冲突规则 |
| 主体关系与代办授权 | 申请人、材料主体、经办人、审核人普遍可能分离 | 委托代办不等于授予受限档案、用印、政审权限 |
| 申请流程/审批事件 | 多阶段任务都要区分预审、审批与执行 | 审核建议不可直接升级为OA官方批准 |
| 规则局部状态与异常聚合 | 同时有缺件、冲突、权限待核时需完整反馈 | 不可用整体通过率掩盖阻断规则 |
| 合法例外与人工复核 | 非标准材料、系统数据缺失都有合理转人工情形 | 人工替代材料不是任意越权批准 |
| 材料版本和对象绑定 | 文书修改、审批撤回、材料替换跨领域存在 | 用印的章种/份数/文书一一绑定属于专项模块 |
| 测试材料与独立金标 | 所有模板均可建立输入、正确输出和检查器分离的测试方法 | 不应将答案或trusted_context放入申请人可见材料 |
