# CDUT Studio Review R02｜统一质量审核标准

## 1. 审核对象与底线

本轮审核的是研究性交接模板，不是学校正式制度、正式表单或授权决定。审查范围为已纳入的 128 份正式 Markdown，并须同时登记预期 144 项中的 16 个缺失源文件。不得把缺失文件用相邻模板代替。

**已核验的原件/清单换行差异（2026-10-24）**：当前 `feat/v3-r02-template-library` 的 `research-original/` 目录恰有 128 份 Markdown，文件名与清单 ID 一一匹配，无额外或缺失文件。清单 `bytes` 对全部 128 份均比 GitHub 当前 blob `size` 大 1 字节；对全部 128 份，`SHA256(当前 blob 原始字节 + 一个 LF)` 与清单 `sha256` 匹配，而当前 blob 原始字节的 SHA-256 不匹配。当前 blob 中 115 份没有终端 LF，13 份有一个终端 LF；清单哈希对应每份当前 blob 再增加一个 LF 的字节流。这是已确认的终端换行差异，不是已证实的正文内容损坏。不得修改原件或清单来掩盖差异；记录为 `LINE_ENDING_DRIFT_ONE_LF`。若追加一个 LF 后仍不匹配，才需继续调查编码、版本或实质内容差异。此差异不阻塞研究和 V3 实现。

**另有已核实的清单元数据问题（不在本次修订中改写原件或清单）**：`S08-T04`、`T02-T14` 的 `version` 字段为空，但各自原件标题与 `archive_path` 均表明版本为 `v1.0`；`T04-T06`、`T08-T05` 的 `source_snapshot` 为 `2026-10-22`，原件研究日期为 `2026-10-23`；`S02-T05` 的 `policy_status` 值在原件与清单中均含一个多余反引号。分别记录为 `MANIFEST_VERSION_MISSING`、`SOURCE_SNAPSHOT_DATE_DRIFT`、`METADATA_MARKUP_TYPO`。这三类问题不改变模板 ID、正式名称或正文内容，也不得成为停止研究/实现的理由。

**学校授权未确认不构成停止审查的理由。** 将其记录为 `AUTHORITY_CONFIRMATION_PENDING` 或政策证据缺口；继续审查模板的结构、逻辑、材料与风险控制。不得虚构授权，也不得因此停止交付。无法确认的实质规则应转人工有权决定，不得写成自动批准规则。

## 2. 每份模板必须审查的维度

1. **身份与结构**：`template_id`、名称、版本、领域、范围、政策状态、撰写状态及文件名一致；引用的 ID/来源存在；正文无相互矛盾的版本声明。
2. **业务边界与路由**：唯一决定对象清楚；适用/排除情形明确；与相邻模板边界清楚；不重复作出其他模板/岗位的实体决定。
3. **政策依据与时效**：优先核对国家/部委、省级、学校官网及正式文件原文；记录发布主体、标题、文号、日期、条款、URL、施行/废止/修订状态、适用对象/学段/批次。搜索摘要、转载或历史文件不能单独证明现行效力。
4. **权责与决定链**：申请、事实核验、专业审查、正式决定、记录/通知、异议/复核角色分离；不得从部门职责推断具体批准权，不得把技术字段或材料齐全等同于授权。
5. **材料与证据**：每项材料有用途、对应规则/事实、必需/条件性/可替代标记；区分申请时材料与后置记录；避免过度收集个人信息；不得声称仅凭文件存在即可验证真伪。
6. **规则与判定逻辑**：硬门槛/软提示分开；阈值、公式、期限有确切适用来源；规则覆盖身份、时点、例外、冲突、缺失、矛盾、过期、不可验证、撤回和复核；禁止以推测阈值自动批准或拒绝。
7. **结果与可追溯性**：每项结论可追溯到材料/证据、具体规则、来源及不确定性；明确缺失项、风险、建议动作和人工决定位置；不把模型建议伪装成正式决定。
8. **隐私、安全与敏感事项**：最小必要信息、访问与保留边界；涉密科研、健康/困难等敏感信息应按适用制度谨慎处理，不得默认进入普通联网系统或公开输出。
9. **异常与人工兜底**：缺资料、证据矛盾、制度冲突、权限未知、边界不明时有明确保守路线；不得简单写“联系学校后停止”，必须完成能完成的模板质量审查并指出需要确认的具体问题。
10. **跨模板一致性与覆盖**：核查相邻模板是否重叠、互相冲突、漏掉关键分支；同一上位规则、材料名称、角色、状态和结果字段应保持一致；登记缺失 ID 和错误清单。

## 3. 问题严重级别

- **P0 严重/安全关键**：错误或虚构政策、虚构决定权、未经授权的自动批准/拒绝、重大隐私/保密风险、模板身份/路由导致错误决定。
- **P1 重大**：核心流程/决定链断裂；核心规则没有依据；材料与判断不匹配；关键例外缺失；会导致错误处理或不可审计的设计。
- **P2 中等**：可追溯性、来源时效、例外、跨模板边界、可操作性存在重要缺口，但有人工兜底。
- **P3 轻微**：命名、排版、措辞、元数据或非实质一致性问题。

## 4. 两条状态轴，禁止用 BLOCKED

`quality_status` 只允许：`PASS`、`PASS_WITH_WARNINGS`、`REVISE`。

- `PASS`：无 P0/P1，核心流程可理解且未发现实质性逻辑缺陷。
- `PASS_WITH_WARNINGS`：无未解决 P0/P1，但存在 P2/P3 或明确的政策证据待确认；模板已用人工复核/保守路径避免把不确定性变成硬规则。
- `REVISE`：存在未解决 P0/P1，或核心范围/规则/权责不可安全使用。

`policy_evidence_status` 独立记录：`VERIFIED`、`PARTIAL`、`UNCONFIRMED`。可出现 `PASS_WITH_WARNINGS + UNCONFIRMED`。**不得使用 `BLOCKED`，不得把学校授权未确认作为不交付的理由。**

## 5. 每个问题必须能复核

每条问题包含：模板 ID、问题 ID、严重级别、类别、所在章节/表格/字段、具体发现、为什么重要、证据/来源（含 URL 和条款，若有）、建议动作、是否需要政策核实、是否涉及跨模板、修订状态。区分“已证实错误”“缺少证据”“建议改进”，不要混为一谈。

## 6. 修订边界

- 不从头重写模板，不擅自更改 `template_id`、正式业务名称或业务边界。
- 只对有明确依据、低歧义的修正生成完整修订版 Markdown；原件只读保留。
- 需要学校解释、授权、当期制度或业务决策的部分，不得猜测补齐。可增加明确的待核说明、人工复核门禁或保守提示，但不能伪造最终规则。
- 修订版沿用原文件规范文件名，放入单独的 `patches/` 目录；不能覆盖原件。

## 7. 输出质量要求

所有报告用中文。政策事实必须给出可点击 URL 与具体文件/条款；找不到原文时记录已尝试的检索范围和剩余不确定性。不得声称已检查未实际读取的内容。不得只给总体印象；必须逐份模板给出状态和问题计数。


## 8. 本轮新增：V3 代码实现与仓库提交是强制交付

质量审查后必须直接落到 V3 原生实现，不接受“只有报告/只有修订 Markdown”。每批需提交：
- 审阅后来源 MD：`docs/design/review-agent/business-templates/R02/{ID}.md`
- `TemplateVersion` 模块：`apps/electron/src/main/lib/review/r02-template-catalog/definitions/{ID}.ts`
- 批次测试：`apps/electron/src/main/lib/review/r02-template-catalog/definitions/{BATCH_ID}.test.ts`
- 审查报告和问题 TSV：`docs/design/review-agent/business-templates/R02/audits/`
- 仓库分支 + 指向 `feat/v3-r02-template-library` 的 PR URL。

模块须关闭自动通过，保留非官方研究模板标识；政策不确定项可继续作为语义审查建议，但不得成为自动正式决定。每个 criterion 必须接入 V3 Plan/Run 检查计划。模板内 criterion 不是学校政策，严禁伪造 PolicyVersion/policyVersionId/确认人。

批次分支命名 `feat/v3-r02/templates-{BATCH_ID}`；子批次不得修改共享注册器、`builtin-templates.ts`、`template-store.ts`、shared 类型、Main/IPC/preload/renderer；这些统一交给集成 Owner，避免并行冲突。子批次执行专项测试、typecheck、boundaries；全量测试只在集成阶段运行一次。
