## 2. 原件/清单一致性结果

| 核验项 | 结果 | 解释 |
|---|---|---|
| GitHub `research-original/` 文件 | 128 份 Markdown | 目录 API 枚举验证 |
| `00_模板清单_128.tsv` | 128 数据行、128 唯一 ID | 无重复 ID |
| 清单 ID ↔ 真实文件名 | 128/128 | 无遗漏或额外文件 |
| GitHub 原件实际字节 ↔ 清单 `bytes` | 严格匹配 0/128 | 每份 blob 比清单少 1 字节 |
| GitHub blob 的原始 SHA-256 ↔ 清单 `sha256` | 严格匹配 0/128 | 不能把原件未经说明地宣称为散列一致 |
| 追加一个 LF 后的 SHA-256 ↔ 清单 | 128/128，按前序逐文件比对及已提交核验记录 | 已定位为统一终端换行差异；不是已证实正文丢失 |

**已确认问题：`LINE_ENDING_DRIFT_ONE_LF`。** 清单 `bytes` 和 `sha256` 与当前 GitHub blob 的*原始字节*并不严格一致；它们对应给当前 blob 追加一字节 `0A` 后的字节流。不得在报告中把“追加 LF 后一致”写成“原始 SHA-256 一致”，也不能暗中改动原件或清单来掩盖差异。该差异不妨碍读取和审查正文，但严格文件完整性门禁应标为“已定位差异，尚未消除”。

## 5. 精确复核命令（不改变工作分支或原件）

在已配置 `origin` 的仓库中：

```bash
git fetch origin refs/heads/feat/v3-r02-template-library
git rev-parse FETCH_HEAD
git show FETCH_HEAD:docs/design/review-agent/business-templates/R02/dispatch/00_模板清单_128.tsv
git show FETCH_HEAD:docs/design/review-agent/business-templates/R02/research-original/S01-T01.md > /tmp/r02-S01-T01.md
wc -c /tmp/r02-S01-T01.md
sha256sum /tmp/r02-S01-T01.md
{ cat /tmp/r02-S01-T01.md; printf '\n'; } | sha256sum
```

最后两项分别为当前 blob 原始 SHA-256 与“追加单个 LF 后”SHA-256，必须分开记录。不能用 `echo`（会添加自己的换行）或经过文本渲染器处理的内容代替原始字节。
