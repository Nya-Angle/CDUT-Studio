## 01 唯一审核目的、申请人和负责机构

### 1.1 唯一决定对象

本模板对应**学校承接横向科研任务时，拟立项基础事实与拟签订研究／技术合同文本的科研业务实质审核**：核对是否涉及真实的研究、开发、技术咨询或技术服务任务，拟约定的技术内容、阶段与可交付成果、双方职责、履约计划、验收与技术风险安排，以及知识产权和保密条款是否清晰、有权处置疑点是否被暴露。它回答“送交学校有权审核人前，哪些事实一致、哪里欠缺证据、哪里存在冲突／需人工判断”，不回答“合同已批准、学校已授权签字、可登记技术合同或可以支付经费”。依据 SRC-005/007/012。

### 1.3 最终有效决定的归属

- **校内科研业务审查／项目登记结果**：由学校当期授权的科研归口／业务审批链在学校可信系统内形成；具体最终岗位未取得原始流程，必须保持 `POLICY_UNCONFIRMED`。
- **合同审批和学校对外签署**：由 2024 校合同管理办法及 2026 年有效授权文件约束的有权人员执行。AI 预审、材料齐全或项目登记状态均不能替代书面或可信电子审批、签字、印章与合同生效事实。
- **外部技术合同认定登记**：由依法受委托的登记机构作出；若有异议，按工信部 2026 办法第 16 条走登记机构及省级主管部门途径，而非用本模板私设复核结论。

## 02 适用、排除与邻接模板路由

### 2.1 本模板纳入的业务事实

- 作为横向科研项目立项前提的拟承担任务、发起主体、相对方、技术方案／技术问题、合同草案版本、合同拟约定金额／付款节点与科研任务之间的可追踪关系；是否应先取得校内审批或论证，由校本政策和具体案情触发（SRC-005/012）。
- 对研究／技术合同内容的**风险提示与事实核验**：技术目标、范围、成果形式、履约计划、交付验收、技术资料与保密、成果权利与利益安排、研究失败风险等（SRC-012）；任何“条款合理性／风险大小／学校利益是否可接受”均待有权人员裁量。
- 已经发生的相关前置事实（如委托意向、有效审批、相对方资料）可以引用；合同尚未生效时不得要求合同生效后才产生的登记证、入账凭证或验收报告。

### 2.3 去重原则

对混合合同以“科研技术标的与项目实质”决定是否进入 T03-T03；同时保留`T07-T02`、`T04-T03`、G06/G07 的跨域引用，不复写其审批状态。纯商品买卖、租赁、非技术劳务、单纯成果转让／许可而不含新研究任务的业务不因为合同标题出现“技术”而强行路由；具体分类仍须校方及法律专业复核（SRC-012/013）。G50 的确切技术键值待读取所给 `catalog.json` 后填充，不能编造。

1. **身份来源**：Main 端通过已验证的学校身份会话与 RBAC／授权登记获取 `subjectId`、组织、实际权限及有效期；Renderer 仅提交意图和材料引用，不能决定 Actor。任何代理关系应有签发者、范围、期限与可追溯撤销状态。
2. **一次案卷一个权威业务对象**：`caseId` 对应 T03-T03 的单个拟签约科研项目／合同业务，合同附件保留 `sourceVersion`、哈希与页位、当事方和审查阶段；新增草案版本不可覆盖旧版审批证据。不得把技术预审当成真实 `ReviewRun` 或自动构造学校业务决定。
3. **决定引用要绑定对象与版本**：审批证据至少应能核验决定来源、真实发起者及审签者、业务权限、所审合同版本、时点、有效／撤销状态；有审批记录却针对别的合同或旧版，输出 `CONFLICT` 并退人工。
4. **后续审查不得回写历史结论**：补件、条款修改或撤回产生新事件和影响项重审；保存证据链与操作者，杜绝同名材料替换后继续显示旧 `PASS_FACT`。
5. **受限材料与最小权限**：对涉密／未公开技术秘密、敏感价格、身份资料，先确认允许进入该处理环境与谁可查看；没有合法处理通道时停止 AI 解析，记录 `NEEDS_HUMAN_DECISION`，不得向普通模型或不受控第三方泄露。
6. **结论语言约束**：事实型核验可输出 `PASS_FACT`、`NOT_APPLICABLE`、`NEEDS_MATERIAL`、`CONFLICT`、`UNREADABLE`、`SOURCE_UNAVAILABLE`、`POLICY_UNCONFIRMED`；对法律判断、IP 处分、合同风险接受、科研资质及正式审批统一保留 `NEEDS_HUMAN_DECISION`。`PASS_FACT` 不代表合同获学校批准。

### 5.4 证据优先级、冲突及数据隔离

1. **同对象同时间同版本**：校方有效业务决定／受托外部机关证明优于草案陈述；正式有效人事／授权记录优于个人填写；原件或签章可验证文本优于 OCR 摘录；但不同职责的来源**不得相互覆盖**，例如学校合同“同意签署”不等于技术合同登记结果。
2. **主体匹配**：采用可信工号／授权 subjectId 绑定发起人和负责人；姓名只用作显示与人工复核，不以“同名”自动合并。外部机构优先核对统一社会信用代码／登记信息，名称变更要保留旧名与变更证明；OCR 错字不得自动改写主体。
3. **版本对齐**：`caseId + contractInstanceId + sourceVersion + contentHash + evidenceLocator` 确定证据对象。合同改版后，受影响的 F、关联 M 和派生结果标记 `STALE_REVIEW`（内部重审标记，不是新的最终审核枚举），保留旧审查历史；新版本的 `PASS_FACT` 须重新产生。
4. **冲突升级**：金额大写小写不一、主体不同、合同与技术方案指标不符、IP 归属声明与权威决定不符、审批记录所审合同哈希不符时输出 `CONFLICT`；若只是读不清则 `UNREADABLE`，来源不可达则 `SOURCE_UNAVAILABLE`，现行性未确认则 `POLICY_UNCONFIRMED`，不得都混成“缺材料”。
5. **隐私与保密分层**：P0 公开政策／法定公开登记，P1 校内普通业务，P2 身份／商业秘密／非公开合同，P3 涉国家秘密或经学校认定必须隔离的载体。P3 只允许经专门批准的元数据路由，普通模型不得访问内容；P2 遵循目的限定与角色隔离。
6. **可信系统优先而非接口臆测**：人事、授权、审批、财务和 G50 权威数据应由已配置的合法可信读取通道获得；若尚无接口，待办给授权经办人做安全核验，不应将“上传截图”作为等价自动替代。

## 06 业务对象与字段字典

### 6.1 对象及字段口径

数据对象：`Case`（单一拟横向科研合同业务）、`Party`（人员／委托方）、`DraftContract`（版本化合同文本）、`ResearchPlan`（技术方案）、`AuthorityEvidence`（主管机关或系统决定）、`Event`（补撤复核／签署／登记）及 `MaterialSource`（文件和权威记录）。同一 Case 可有多个草案版本，但只有按 P5 可信决定生成的有效签约事实；不在本模板另建第二套批准状态。

字段类型记为 `id/text/enum/date/time/decimal/flag/ref/list/hash`；条件未满足时是**不适用或尚未生成**，不等于缺件。来源中“草案陈述”代表可核对但尚不可信的内容，“权威”须真实校内或法定来源。证据位置记 `Mx:部位`，实际运行时还必须保存具体文件版本、页码、段落／单元格；自动推算不到位置则不能输出无定位的 `PASS_FACT`。下表隐私级别 P0–P3 按 05.4，**仅用于数据敏感度**，与 03 节同名的办理阶段 P0–P7 是两个独立维度。

## 07 材料槽与证据目的

### 7.1 槽位与证明责任的统一口径

- `当前必需`：**仅指在该阶段开展所声明的事实预审时，必须获得相应事实**。不表示学校已规定申请人上传某份附件；可以直接由获授权校方系统提供。单一文件可满足多个槽，一份槽内资料也可覆盖若干 F。
- `条件必需`：仅触发特定业务事实、代理关系或独立程序时检查；触发条件为未知时先核情形，不创设默认必交清单。`后续才产生`：从时间逻辑上不得在 P0/P1 主合同预审当作缺件。
- 持有人分为**发起人／项目组**、**相对方**、**校内有权机关**、**第三方权威登记机关**和**系统事件账本**。合同草案只能证明双方拟议文本，不能证明学校已经同意。`页／条／签章页` 为提取位置目标，需在每次上传生成真实文档定位，不制造固定页码。
- 槽位封套必须包含 `caseId、sourceId、sourceVersion、contentHash、owner/issuer、issuedAt/observedAt、evidenceLocator、securityLevel、supersedes、verificationState`；缺项时仅影响其实际依赖核验，不因附件重命名消灭历史。

## 08 审核规则逐条清单

### 8.1 规则可执行性与共同判定公约

本轮规则是**可实现的事实预审设计**，不是成都理工大学认可的自动行政审批规则。R 的“对比一致”只是证据间的可核事实成立；对实际技术水平、合同风险可承受性、IP 处分、校内签约权限和复核结论，一律待现行校本制度与有权人认定。`SRC-002/003/004/006` 只代表待核依据，**不能**支持硬阈值。无可信校本依据的年限、金额、签字人数、截止日期、资格条件，一律不给 `PASS_FACT` 作为资格或程序合格结论。

- 每次判定输入：`ruleId, caseId, scenario, stage, planId/fingerprint（若系统已有）, contractInstanceId, sourceVersion, evidenceIds+hashes+locators, actorTrustedRef, policySnapshot, decisionRefs`。不依赖前端伪造的审批角色，旧 `run@rev` 不能等同有权学校决定。
- 通用**触发三值**：`true` 进入本行比对；`false` 对条件分支或阶段未到给 `NOT_APPLICABLE`（常规必核核心事实不能以“用户自称不适用”绕过）；`unknown` 按造成不确定的根因分类：校规→`POLICY_UNCONFIRMED`，专业性质→`NEEDS_HUMAN_DECISION`，权限数据源离线→`SOURCE_UNAVAILABLE`，证据未提交→`NEEDS_MATERIAL`。未知绝不按真或假默许。
- 通用**证据层级**：A＝受权校方系统／法定登记机关的有效原始记录及签发身份；B＝可信电子原件或可验证纸质原件；C＝项目组草案、对方声明、扫描件；D＝OCR／AI 抽取。A/B 可用于其法定或业务权属范围内的事实验证，C 用于拟议内容定位，D 只辅助提取，不能自行形成授权。每行的“来源”指定应比较哪个层级，**不存在跨业务的一条万能优先序**。
- 通用**版本有效性**：所有引用绑定 `caseId + contractInstanceId + sourceVersion/hash + issuer/scope + evidenceLocator + effectiveAt/revokedAt`。条件为真但同一事实的两个可信来源实质冲突时给 `CONFLICT`；材料存在无法辨读给 `UNREADABLE`；权威通道失联给 `SOURCE_UNAVAILABLE`；法律／技术可接受性无自动标准给 `NEEDS_HUMAN_DECISION`。
- 下表中 `T/F/U` 分别表示条件真／假／未知；一行中列出的状态是**互斥的单项事实结果候选**，一次规则执行只选一个，具体选择顺序见 10.1。SRC 采用文档 04 的实际可见范围，不把通用法律当作校内审批依据。

### 8.3 判定层级与审查输出边界

1. **一条 R 只表达一个核验对象**；同一 R 可以关联多 F/M，但一次执行只给一个规范结果码和一组有定位的问题。R013 核背景 IP 的权源与条款一致性，不独立审批知识产权；R015、R025 只读邻接结果。
2. **事实可核但政策无法证实的分拆**：例如 R002 可信身份一致可为 `PASS_FACT`，R003 负责人主持资格仍是 `POLICY_UNCONFIRMED`；R012 金额算术可通过，但审批金额分档未查得，R019 不能由前者自动通过。
3. **P5 有权决定外置**：任何 R 都没有 `APPROVED_BY_SCHOOL` 输出码。学校审批事件仅以受权系统原件及可验证权限被引用；模型不签字、不在 Renderer 接受 `approverId` 自填、不伪造 `ReviewRun`。
4. **不可达材料不得误判缺失**：R020–R022 对 P1 为 `NOT_APPLICABLE`，R016–R018 对未到条件节点且无必经制度证据的 P1 不强制索取；R026 仅 SRC-015 特定平台适用。

### 9.3 复合案件的“主任务＋权威引用”策略

1. **先识别科研承接主法律关系**：单案主要承接研发或技术咨询服务的，其研究任务和合同草案仍是 T03-T03；如另有采购、科研外协、成果处分、伦理、财务事项，分别创建／引用其独立权威决定，不把某个附件视为这些事项全部通过。
2. **并存责任不合并签发**：科研业务预审可以指出与学校合同管理、G06/IP、T04/采购、T07/一般合同、G07/财务的接口要求，但不能签发其审查意见；不同 Owner 结果即使同名“通过”也不能互相替代。
3. **严格版本失效扩散**：修改 `M007` 的技术标的、双方、金额、交付、验收、IP、保密任一内容，则映射受影响的 `F` 与 `M008/M009/M010/M011/M012/M013/M014/M019`，把旧事实结论仅保留为历史；当前有权人须判断是否需要重新会签。未变材料不得重复索取。
4. **信任与裁量分开**：对照真实文档页／条、来源哈希、有效签发人、当前生效性核事实；技术可行性、合同风险分担、专利处置、保密等级和复杂主体的法律有效性都交有权人。不以自动比对的 `PASS_FACT` 代替其判断。
5. **状态与业务结果不混同**：证据齐全只能对其具体事实给出 `PASS_FACT`；规则不适用 `NOT_APPLICABLE`；来源丢失、文档不可读、政策现行性无法证实、利益冲突需专家判断分别采用各自状态；不存在“事实全过→学校批准”的隐式迁移。

**本节证据限制**：上表是利用 SRC-005/007/009–015 可见内容推导的材料逻辑和安全边界，不是现行校方逐条审核规则。第 3 轮的 R001–R026 已表达有依据的事实预审与人工阻断，**仍不能当校方正式执行的准入／批准规则**；金额门槛、经办资格、实际前置会签单位、复核期限须在第 4 轮依据 SRC-002/003/006/008 原文补核。

| 待办 `Task` | `taskId`、`caseId`、`issueIds`、`assigneeAuthorityRef` 或经认证 `applicantSubjectId`、`action=补充／澄清／查权威系统／人工判断／有权审批／复核`、`notBeforeStage`、`dueAt?`（未证不得自行填法定期限）、`dependencyRuleIds`、`consumedDecisionRefs`、`taskStatus`；允许一人处理多问题但每项可追溯 |

### 10.3 前端可读状态与正式审批结果隔离

- 案卷首页／工作区可显示“事实预审完成待人工决定”“有 3 项补件”“2 项来源不可达”“1 项政策未确认”等**汇总提示**，这些是由 `FactCheck` 与 `Issue` 推导的 UI 状态，不是学校审批结论枚举。
- 同案卷材料→方案→运行→问题→待办的跳转以 `caseId + issueId + sourceVersion + evidenceLocator` 定位；点击问题能够打开该材料的对应条款或跳到有权决定引用，不另造第二份案卷数据。
- 一条问题必须由其 R 直接指明“谁能解决”：项目组处理草案缺漏；校方身份／科研业务部门处理资格与归口；合同授权与法务部门处理签章、法律风险；G06/G07/T04/T07 的决定由各自 Owner；校方保密专责处理受限状态；外部登记机关负责其登记复核。
- **对外审查结论边界**：本模板的任何 `PASS_FACT` 都不得触发 `Approved`、自动用印、自动合同生效、税费优惠、科研成果处分或自动资金拨付；只接受另一个真实业务系统返回的可验证有效决定。

### 11.2 材料变化的定向重审依赖图

`impactedR = rulesDependingOn(changedF ∪ changedMaterialSlot ∪ revokedPolicyOrDecision)`；按本轮规则实际 F/M 依赖而非简单文件名匹配。首先重新评估 R001（事件绑定）和 R023（改版及影响分析）这两个**事件元规则**；然后只把受影响事实 R 置 `RECHECK_REQUIRED`，保留未命中规则的有效结果。政策源或授权记录更替视为**依赖变化**，即使文件内容没变，也要复核相关 R。主要映射：

| 变化／主从材料 | 常见影响 R；界线与保留策略 |
| --- | --- |
| 校内身份或组织 M002、代理 M003 | R002–R004；跨单位影响 R009，承诺主体影响 R016。未涉及任职事实的合同价款 R012 不重审 |
| 相对方登记 M005、签署权 M006 | R005/R006；若已签，连带 R020；不因对方法人更名而自动重测技术方法 R010，但合同主文当事方修改会另触发 R007/R008 |
| 草案 M007 的技术目标／内容／参与人 | R007–R011，按具体变动 F018–F026 再确定；若现有 M014 批准绑定**全文哈希**，必须检查 R019/R020 失效，不允许“只是小改不重审授权” |
| 草案 M007 的金额／付款 | R007/R012；已进入有权审批／签署节点的 M014/M015 必核 R019/R020；经费已到账的 R022 不回写历史，只检查新旧合同关联 |
| 草案 M007 的 IP／保密／下游外协条款 | R007/R013–R015，并更新相关 G06/保密/T04 等决定引用 R025；受限等级变化触发 R014 并可能停止其他普通解析 |
| 技术附件 M008 或背景 IP M009 | R008–R011（按受影响技术字段）；M009 主要 R013/R025。未触及报价，不重跑 R012 |
| 科研承诺 M004、单位／专家意见 M012/M013 | R016–R018；改变前置批准关联才连带 R019；不自动重读所有原始合同内容 |
| 学校授权／批准 M014 或正式签署 M015 | R019/R020 及实际发生的后置 R021/R024；旧签署合法性争议转有权人，不能自动撤销已生效合同 |
| 登记 M016、财务 M017 | 分别 R021、R022；不得回写旧 P1 事实核验或另造新的合同批准 |
| 撤回复核／版本事件 M018 | R023/R024，按事件指向的合同 F/M 再扩散；保持新旧决定的权威引用与历史 |
| G/T 权威决定 M011/M019 或涉密状态 M010 | R015/R025 或 R014；按生效／撤销、对象和版本刷新引用；停止在普通模式处理已被划为受限的资料 |
| 特定平台记录 M020 | 只影响 R026（身份变更时再检 R002/R003）；不因为钱包数据变化重跑一般合同的 R010/R012 |

如果只知道“整个 PDF hash 变了”而无法安全、可靠比较具体条款，就不能假称精准：对依赖该文档的所有当前 R 置待重审；**以更少范围重审的前提**是有可审计、定位到 F 的变更差异。被替换材料与旧结论只读归档，不删改；前后审批是否继续有效由原批准机关按学校制度判断。

### 11.3 补件、撤回、复核与独立权威决定的请求闭环

1. **补件**：问题 `Issue` 指向 R/M/F/SRC、具体页／条、当前允许的替代和受领角色；项目组上传新版后重新赋 `sourceVersion/hash`；将受影响旧问题 `superseded`，新审查产生新 `Issue`，不直接覆盖历史。
2. **签前撤回**：`WITHDRAWAL_REQUESTED` 是申请行为；只有核实原办理机关有权签发的处置才写 `WITHDRAWAL_DECIDED`。原文缺失时人工确认是否存在撤回期限、是否已越过不可撤回节点；不得以不可信前端身份删除案卷。
3. **重提／再审**：同一合同拟议事项只更新同一案卷的版本和尝试关系；已有 G50/T04/T07 决定若仍与对象、版本、条件匹配才复用；政策或合同实质改变时原权威人重新决定其效力。
4. **校内复核与外部登记复核**：校内审批异议程序当前无确证，保持 `POLICY_UNCONFIRMED`+人工；已生效技术合同的登记复核按 SRC-013 第 16 条，由原登记机构／上级主管办理，不由本模板执行。
5. **正式决定**：最终校内项目／合同审批与签约、成果处分、财务动作及登记分别属于其有权 Owner；本案只存 `AuthorityDecisionRef`，用来源身份+权限+时点+合同哈希校验真实性。离线导入只交换可审核的文件与证据引用，不把无签发权的导入文本升格为校方真实批准。

### 12.2 高风险的不可自动裁决集合

- 科研技术性质认定、合同类型法律定性、研究可行性和能否承担技术失败风险；R008/R010 只能提供条款事实，法律或专家判断转 `NEEDS_HUMAN_DECISION`。
- 学校签约代表的现行权限、合同审批效力、重大合同决定、撤回后法律效力、变更或解除合同的权力和后果；SRC-006/008 还缺原件，不得把读取到截图当正式决策。
- 技术成果权属、共同开发知识产权分配、已授权专利是否可对外许可或转让、伦理以及境内外技术资料提供；只引用 G06 或对应有权机关决定，不从 R013 推导批准。
- 涉国家秘密、未公开的受限技术／商业秘密的处理通道、安全等级及跨境披露。普通模型即使能读取，也不意味着合法处理；条件未知先停读，等保密专责核定。
- 归口／金额／资格／时限：若当前学校原件不支持，一律 `POLICY_UNCONFIRMED`，配置状态记 `UNVERIFIED`，不以其他高校通行做法、社交媒体、旧表单或者 2026 专项通知填补。
