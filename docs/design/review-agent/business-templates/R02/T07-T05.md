## 01 唯一审核目的、申请人和负责机构

### 1.1 决定对象

**对象是“某个明确学校组织所主办的某个平台账号”的校内开设、信息/责任关系变更或注销意向与事实，不是单篇内容。** 一个案卷以 `机构主体 + 平台 + 账号平台唯一标识（既有账号）/拟使用标识（新账号） + 本次操作` 固定目标。账号尚不存在时不可要求真实账号 UID 或平台认证完成证明。

国家网信部门《互联网用户账号信息管理规定》第7–11、13条要求机构账号身份、名称标识一致性、注册/变更信息核验，并将真实身份认证与教育领域资质核验职责置于互联网信息服务提供者；它**不授予本软件学校审批权**（SRC-007）。公众账号跨主体转让及停用还涉及 SRC-008 **第11条**的平台申请、核验或服务协议处置，不能只按普通昵称修改对待。

### 1.2 申请、代办和决定角色（校本权限待确认）

| 角色 | 有证据的事实/合理的待核分工 | 本模板能接受的身份依据 | 权限结论 |
| --- | --- | --- | --- |
| 申请主体 | 拟以学校、学院/职能部门、经校方认可的组织名义运营的机构/组织；官网确有不同层次已备案账号（SRC-003） | 校方组织机构目录和机构授权文件；若没有可信接口，则来源可核的公文/证明 | **单位是否具备申请资格，待校本规则核定** |
| 发起人/代理人 | 实际录入材料的教职工或组织受托人员；学生可参与运营不等于有权代表单位申请 | 可信登录 Actor + 单位书面代理/授权事实（如要求）；不能靠本人填写“审批人” | 发起权与代理权分开核验；学段不是默认审批权限 |
| 主管/主办单位负责人 | 可能对账号归属、运维责任、人员变动作事实确认 | 校方人事/组织关系及正式签批记录 | 是否需书记、负责人、分管领导、层级签字均未知，不能固化 |

| 技术/网信职能部门 | 当账号涉及小程序、APP、平台数据接口、域名时可能另有网络安全/信息化审查 | 相邻有权部门真实结论 | 不推定每个普通社媒账号都必须信息化部门审批 |

| 复核/申诉有权人 | 待校本程序确认 | 可信机构与角色授权、实际复核决定记录 | 不能以申请人或 Renderer 字段推断 |

### 1.3 审核范围与高风险动作

1. 核对机构是否存在、申请是否由有权代表提出、账号是否归属所称单位、平台账号唯一标识是否对应证据、变更前后事实是否连续。
2. 对拟用校名、校徽、机构名、教育内容类别等进行事实提示，校方授权合法性由有权人员决定；平台主体认证由平台决定（SRC-007 第7–11条）。
3. 在变更管理员、主体转移、控制权丢失或注销时，关注责任交接、现存内容处置及凭据安全。涉及公众账号转让/自行停止运营时，须引用平台真实办理轨迹（SRC-008 第11条）；本轮**没有成都理工大学正式交接清单或注销期限依据**。
4. 账号密码、短信/邮箱验证码、恢复密钥、会话 Cookie、私钥、平台绑定的完整身份证号等**不得进入普通材料仓、OCR、LLM 提示词、搜索索引、导出件**；只允许记录“已由受控凭据渠道办理”这一非秘密状态引用（SRC-009 第5、6、51条的最小化与安全义务）。

## 05 角色、权限与可信数据边界

### 5.1 Actor、主体、平台三重身份

- **Actor 可信源**：只信 Main/Host 已认证会话 + 服务端权威身份/机构角色查询 + 受控权限检查结果；Renderer 表单、拖入文件、截图里声称“部门领导/宣传部审批人”，一律只是待核主张。无权威校内接口时，`SOURCE_UNAVAILABLE` 或 `NEEDS_HUMAN_DECISION`，不得伪造 teacher/approver。
- **账号主体可信源**：学校组织机构权威登记与学校真实授权文件；外部账号的“蓝 V/机构认证”由平台验证，但只证明平台维度的认证。多平台相同昵称不能互作唯一标识。
- **签发权**：单位事实确认、党委宣传归口审查、上级领导最终同意、平台执行四种动作需分开存储 `actor_id / org_id / mandate_scope / decision_type / authority_basis / timestamp / source_version`。本校未核实谁有哪一级签发权前，正式节点禁止自动推进。
- **三份不互替的权威**：`ORG/DEC` 是学校主体与正式权限；`PLAT` 是平台账号认证、转让、暂停/终止服务；`CASE` 是案件版本/处理轨迹。平台完成转让不能补造校内同意，校内同意也不能使平台已执行。SRC-008 第11条的转让申请及受让主体核验由**平台**负责。
- **主案唯一写权**：ReviewRun 仅给出事实预审及问题；CurrentCase/Decision/Outbox 的正式状态通过 Main 可信领域服务写入，并绑定当前案卷及当前 Run/Plan 版本。申请文本、Renderer Actor、旧 run@rev 不得转成正式决定。

### 5.2 授权来源优先级与材料归属

1. 高：校方在线权威组织、人事、审批、账号台账记录，前提是接口确实存在且有可审计查询；没有接口就标不存在，**不要求申请人重复上传能依法调取的事实**。
2. 次高：有签章/可验证文号/受控系统导出的正式单位决定；仅在签发人权限、文件版本、具体账号和操作范围一致时可引用。
3. 中：平台官方管理后台可验证认证/变更/注销记录；敏感信息在受控渠道核验，普通材料只存脱敏摘要与校验结果。
4. 低：截图、电子邮件、网页缓存、申请人自述；可辅助定位但不能单独替代校内授权。
5. 一份证据必须带 `source_owner、case_id、account_identity、stage、source_version、observed_at、verification_method`；重复引用 G50/S/T 已有结果须带其**权威决定 ID/签发主体/生效状态/撤销状态**，绝不复制“通过”字样。

### 5.3 安全与缺失语义

| 问题 | 本模板行为 |

### 5.4 秘密与个人信息边界

- 本模板永不索要密码、二次验证、密保答案、令牌、助记词、后台 Cookie、完整身份证明影像及管理后台全量导出。若证明需要看管理员控制权，优先“平台权威只读核验结果/内部受控保管凭证已核状态”。
- 联系方式与管理员姓名为个人信息，普通工作区仅开放给办理所需角色；对外报告按需脱敏、设置保留期，由学校信息治理规则确定，不能自定永久留存。依据 SRC-009。
- 平台注销后可能涉及内容、访问记录及投诉记录保留义务：不得“一键清库”；保存期限、档案部门决定和清理授权都待学校与平台规则核实。
- 发现账号盗用、会话劫持、凭据泄露时，普通材料通道只允许**脱敏事件号/风险类别/处置状态**；涉及个人信息泄露的通知与补救适用 SRC-009 第57条并由真正信息处理者执行，不得让模型自发给第三方发送通知或模拟通知完成。

## 06 业务对象与字段字典

### 6.1 业务实体及关系

- `AccountReviewCase`：一案卷对应一个平台账号的一次开设/变更/注销申请。单案多次修订不重开身份。

## 08 审核规则逐条清单

### 8.1 规则适用与证据前提

本节是**待校本确认的事实核验契约**，不是成都理工大学现行审批规程。每条 R 只管一个独立事实对象；涉及 `SRC-005` 时，它只能证明「有待寻找的制度线索」，不能提供任何实质许可条件。`SRC-010` **不得充当规则的有效校本依据**。

- 触发 `T/F/U` 分别为 **true/false/unknown**：`F` 必须是已知事实明确不适用，输出 `NOT_APPLICABLE`；不能因为材料缺失把 `U` 当 `F`。`U` 若由现行校本规则不明导致，输出 `POLICY_UNCONFIRMED`；若由证据缺失、不可读、权威源故障导致，按 10.1 的单一原因分类。
- 规则的 `PASS_FACT` 必须同时满足：触发 `T`，本阶段相关字段可读且归属正确，必需事实由足够等级且有效的来源支持，无未解决冲突，比较条件确定。它**只证明列明的事实**；不能把 R 的全通过提升成 `SchoolDecision=APPROVED`。
- 来源强弱：针对校内身份/授权以 `HOST/ORG/DEC` 为主、针对平台账号效果以 `PLAT` 为主、对陈述以 `APPL` 为主；截图、OCR、旧缓存只能提供待核主张。来源失联时无权替它造“可信事实”。证据时效使用来源实际查询时刻、有效区间、撤销状态和材料版本；不存在统一默认“30天有效”之类阈值。
- 每个 R 继承统一异常处理：缺**当前事实输入**=`NEEDS_MATERIAL`；文件本身无法可靠读取=`UNREADABLE`；必须查询的权威记录无法取得=`SOURCE_UNAVAILABLE`；两项足够明确且指向同一事实的来源矛盾=`CONFLICT`；事实可核但需要资格/裁量/签发权解释=`NEEDS_HUMAN_DECISION`。仅政策未知时不强制出缺件。

## 09 触发条件、冲突和复合场景

### 9.1 条件与分支优先级

### 9.2 反例与临界案例（字段/材料层）

1. **截图冒用机构**：M003 页面头像和名称写“成都理工大学”，F009 对应的 UID 经平台查为个人主体。F011 一致不抵销 F013 冲突；不能判正式账号。

## 10 结果状态、问题与待办输出契约

### 10.1 互斥的单规则事实状态

每个 `ruleId × targetId × runId × sourceSnapshot` **恰有一个主结果码**。同时存在多个问题时，输出独立 `Issue` 或拆成实际不同 R，不能同一 R 同时写 `PASS_FACT` 与 `NEEDS_MATERIAL`。以下是规则主结果的严格含义：

| 主结果码 | 唯一含义与判定前提 | 不能误作 | 典型责任人 |
| --- | --- | --- | --- |
| `PASS_FACT` | 触发真，当前阶段可核的**具体事实**有足够可信、可读、匹配且有效证据，无冲突 | 校方同意、平台已注册、无需人审 | 下一环节经办人 |
| `NOT_APPLICABLE` | 有充分事实证明本 R 此阶段/此类型**不触发**，如新开号 P0 的平台回执 | 缺件、已豁免校本要求 | 规则作者/经办人（通常无待办） |
| `NEEDS_MATERIAL` | 触发真，**当前阶段**证明某具体事实所需的可合法替代证据都缺且有确定缺口 | 未来阶段文件未生成、制度不清 | 发起人或材料持有人 |
| `CONFLICT` | 至少两份指向同一事实、可定位的证据或权威字段相互抵触，且无法按版本/时效解释 | 模型低置信度、材料不清 | 两方证据 Owner/归口核验人 |
| `UNREADABLE` | 材料存在但关键字段/页无法可靠提取或人工辨识，未获得有效替代读数 | 无材料、无制度、来源宕机 | 材料持有人或人工读件员 |
| `SOURCE_UNAVAILABLE` | 必需的可信外部源、台账、接口或文书原件无法访问/不返回；尚不能判事实 | 材料缺失、校本制度本来不确定 | 源系统 Owner/归口部门 |
| `POLICY_UNCONFIRMED` | 事实可能可见，但**适用校本政策/版本、条件、期限或有权角色制度**未核实 | 自动不通过、借外校条款判不合规 | 党委宣传部/有权制度解释人 |
| `NEEDS_HUMAN_DECISION` | 证据可核或争议已呈现，但需要真实资格授权、裁量、例外处置、复核/签发决定 | AI 准予/拒绝、当前技术故障 | 经可信权限核验的有权人 |

**单一原因路由**：先判阶段/触发。明确不适用→N/A；触发未知则定位未知原因（无校本有效依据→政策未核，权威源不可达→来源不可得，材料存在但不可读→不可读，当前事实槽全无→缺材料）。触发真时依序作来源读取、版本/归属、比对及人工权限判断。若并发存在证据冲突与技术读取失败，分别由不同事实 R 发出问题；同一 R 暂只保留决定其当前可评价性的主阻断原因，其余异常进入非决定性的 diagnostics，不把未观察的冲突当已证实。

`PASS_FACT` 与 `NOT_APPLICABLE` 之外均为未闭合事实/行政节点；它们**不是同一种不通过**。规则组全为这两个码，只能得 `FACT_PRECHECK_COMPLETE`，不得得 `SCHOOL_APPROVED`。

### 11.2 补件、材料替换与选择性重审

1. 每次提交形成 `EvidenceVersion={caseId,materialSlotId,sourceOwner,accountKey,versionId,receivedAt,contentHash,stage}`；不覆盖原版本字节或其 Run 记录。普通材料不得含敏感凭据。
2. 构建 `F ← M/source` 与 `R ← F/M/SRC` 显式依赖。M 的新版本仅将读取该 M 或其变化 F 的 R 标记 `STALE`；若上游 R 的已验证事实发生变化，再沿依赖链扩散。绝不靠旧 Run 文本“仍通过”。
3. `STALE` 的规则在当前冻结 Plan/SourceManifest 上不可作为现行 `PASS_FACT`；新 Run/plan 修订产生新的证据定位。未变化的 R 允许引用**不可变输入 hash、policyVersion 和 ruleVersion 均相同**的旧发现，标明 `reusedFromRunId`，不伪作重新运行。
4. 补件回到具体 Issue：申请人提交新 M003 中 UID 页，可重算 R005/R006/R009/R017/R021，不强迫重传 M009 注销计划，**M013 不是替换 M003 的代用品**。若当事人改动了账号 UID，属于目标身份变化，R001 触发冲突/需改案，不直接沿旧案批准。
5. 校本政策变动与材料变动独立：新的政策版本触发 R014 及依赖的行政规则重评；历史已签决定的法律效力必须由有权部门解释，系统不能自动撤销。

### 11.3 撤回、重提、复核

| 情形 | 处理原则 | 不可自动进行的动作 |
| --- | --- | --- |
| P0/P1/P2 发起撤回 | R019 核本人/代理权限、案卷 ID、当前阶段；登记 `WITHDRAWAL_REQUESTED`；实际撤回受理与效果待校本规定 | 单纯勾选 UI 就删除案卷/撤销他人已签意见 |
| P3 已有正式决定后申请撤回 | 把原 Decision 与撤回请求分别保留；有权机关决定是否更正/撤销 | 用撤回单覆盖 Decision 或将其设为未曾存在 |
| P4 平台已执行后要求撤回 | 记录平台操作结果；若需恢复账户/更改资料，须判断平台是否允许和是否需要新授权 | 直接回滚外部平台、恢复被注销账号 |
| 撤回后重新提交 | 优先新 `applicationAttempt` 版本，绑定原 `caseId/target` 与撤回结果；若目标或权限变化需新案/有权判断 | 把撤回的旧 Run 作为新申请的现行通过记录 |
| 校内正式决定异议/复核 | R020 区分原决定、复核请求、权限；校本受理与有权复核角色、时限待核；新决定独立记录 | AI 自行改判、把平台申诉当校内复核 |
| 平台服务/认证申诉 | 平台申诉证据与回执单列，与学校 R015 正式决定相互引用但不混同（SRC-008 第20条） | 平台客服回复直接变成学校批准或撤销 |

### 11.4 人工决定的最小可信门禁

须同时具备：`Main/Host trustedActor`、可核真实组织/角色与授权范围、适用且当前有效校本权限规则、目标 `AccountKey`、对应操作、冻结的 `planId/fingerprint` 与当前 `entryRunId`、有效材料及政策版本、无影响决定对象的未闭合高风险冲突。任何一项未知只能进入人工核权限/政策队列，**不能自动调用 Finalizer**。事实审查员可以提出建议，但无权伪造校方授权或修改 `Decision`。技术 Owner/CaseAggregate 对这些写操作须服务端约束，不能仅凭 Renderer 字段。

### 12.2 四个禁止自动裁量区

1. **校方是否准许开设/变更/注销**：没有当前有效制度和有权签发，`PASS_FACT` 不能成为行政决定。
2. **申请人/组织有无特殊例外资格**：学生、临聘、外包代理或团学组织身份不能靠模型类推授权。
3. **涉及校徽、官方名称、主体迁移及账号失控的责任归属**：事实冲突可标，处罚、整改、账号权益归属与紧急止损由真正有权人处理。
4. **信息保留及平台不可逆操作**：保存期、删除权限、身份凭据移交方式及平台申诉结果不得由模型设定；公众账号转让须区分平台核验与校方真正授权。

### 12.3 证据优先与未来核实动作

按 `CDUT-VERIFIED 实际制度全文及权威办事系统` → `本校正式部门决定/台账` → `适用全国法规` → `平台记录` → `申请人证据` 的**事项权威范围**使用证据；这不是所有事实的一条机械优先序（平台 UID 当然以 PLAT 为主，校内许可当然以 DEC 为主）。`SRC-010` 外校来源只帮助发现候选字段，不进入校本规则的阈值/期限/决定权限。取得校本来源后，需记录版本、条款、施行范围、废止替代关系及校方可解释联系人。
